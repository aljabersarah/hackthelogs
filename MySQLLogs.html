MySQL and MariaDB Logs

MySQL Log Overview

MySQL and MariaDB provide five distinct logs, and only one of them is enabled by default. The error log records server startup and shutdown, plugin loading, replication problems, and, depending on verbosity, aborted connections. The general query log captures every statement the server receives, the slow query log captures statements exceeding a duration threshold, and the binary log records every data-modifying statement for replication and point-in-time recovery. Security auditing proper comes from a plugin: MySQL Enterprise Audit on Oracle's commercial edition, or the freely available server_audit plugin bundled with MariaDB and packaged by Percona for MySQL.

This split creates a well-known blind spot. The general query log is the only built-in source that shows what an attacker actually ran, but it logs everything from every client with no filtering, writes credentials in cleartext when a user runs SET PASSWORD, and imposes real overhead. As a result it is almost never enabled in production, and most MySQL estates have no record of executed statements at all. The audit plugin exists precisely to close that gap: it can be scoped to connections, queries, and table access, filtered by user, and written in a structured format suitable for a SIEM.

MySQL is also unusual in how directly the database maps to operating system compromise. SELECT ... INTO OUTFILE writes attacker-controlled content anywhere the mysql user can write, which is the classic route from SQL injection to a web shell. LOAD DATA LOCAL INFILE can be turned against the client to read files from the connecting host. User-defined functions loaded from a shared library grant direct command execution. Every one of these leaves a trace, but only if the general query log or the audit plugin is capturing statements. Enabling one of them is the single highest-value logging change you can make to a MySQL server.

Key MySQL Log Types

Each MySQL log answers a different question. Understanding the trade-off between coverage and overhead determines which combination is realistic for your environment:

Log Type Description
Error Log The only log enabled by default. Records server startup and shutdown, plugin initialisation, InnoDB recovery, replication errors, and aborted connections. At verbosity level 3 it also logs access denied messages, making it a usable authentication failure source without the cost of the general log.
Audit Plugin Log Produced by MariaDB server_audit, Percona Audit Log, or MySQL Enterprise Audit. Records connections, disconnections, executed queries, and table access as structured JSON, XML, or CSV. The only production-appropriate way to get full statement visibility with filtering.
General Query Log Logs every client connection and every statement received, in the order received, regardless of whether it succeeds. Complete but unfiltered and expensive. Useful for short, targeted investigation windows rather than continuous operation.
Slow Query Log Records statements exceeding long_query_time and, optionally, those not using indexes. Primarily a performance tool, but valuable in security because bulk extraction queries and time-based blind SQL injection are both inherently slow.
Binary Log The replication and recovery stream containing every data-modifying statement or row change. Readable with mysqlbinlog. Frequently the only surviving evidence of an UPDATE or DELETE when no audit plugin was installed.
Relay Log On replicas, the local copy of events received from the source server. Relevant when investigating whether malicious changes originated locally or were replicated in from a compromised primary.
Pro Tip: If you cannot deploy an audit plugin, set log_error_verbosity = 3 and log_slow_extra = ON. The combination gives you authentication failures and slow bulk queries at almost no cost, which covers two of the three most common database attack signals.

Log File Locations

Paths differ between distributions. Debian and Ubuntu packages use /var/log/mysql/, while Red Hat family packages default to /var/log/ and the data directory.

Log Default Location
Error Log /var/log/mysql/error.log (Debian) or /var/log/mysqld.log (RHEL)
General Query Log /var/log/mysql/mysql.log or <datadir>/<hostname>.log
Slow Query Log /var/log/mysql/mysql-slow.log or <datadir>/<hostname>-slow.log
Binary Logs /var/lib/mysql/binlog.000001 (MySQL 8) or /var/log/mysql/mysql-bin.000001 (Debian)
Audit Plugin Log <datadir>/server_audit.log (MariaDB) or <datadir>/audit.log (Percona / Enterprise)
Configuration File /etc/mysql/my.cnf, /etc/my.cnf, or /etc/mysql/mysql.conf.d/mysqld.cnf
Windows Data Directory C:\ProgramData\MySQL\MySQL Server 8.0\Data\
Pro Tip: Never trust the packaged default. Run SHOW VARIABLES WHERE Variable_name IN ('log_error','general_log_file','slow_query_log_file','log_bin_basename','datadir'); to get the live paths from the running server.

Enabling MySQL Logging and Auditing

Most logging can be switched on at runtime with SET GLOBAL, but the settings must also be written to the configuration file to survive a restart. The audit plugin must be installed before it can be configured.

Step 1: Configure the Error Log for Full Verbosity

[mysqld] log_error = /var/log/mysql/error.log log_error_verbosity = 3 # 1=errors, 2=+warnings, 3=+notes (includes access denied) log_timestamps = UTC # normalise timestamps for SIEM correlation log_error_services = 'log_filter_internal; log_sink_internal'
Verbosity 3 is what makes failed connection attempts appear in the error log. UTC timestamps prevent correlation errors when the server is in a non-UTC timezone.

Step 2: Install and Configure the MariaDB Audit Plugin

-- Install the plugin (MariaDB, or Percona build of MySQL) INSTALL PLUGIN server_audit SONAME 'server_audit.so'; -- Verify it loaded SELECT plugin_name, plugin_status FROM information_schema.plugins WHERE plugin_name = 'SERVER_AUDIT';
The plugin must be present in the plugin_dir. Confirm with SHOW VARIABLES LIKE 'plugin_dir' if the INSTALL statement fails to find the shared object.

Step 3: Set the Audit Plugin Parameters

[mysqld] plugin_load_add = server_audit server_audit_logging = ON server_audit_events = CONNECT,QUERY_DDL,QUERY_DML,QUERY_DCL,TABLE server_audit_output_type = FILE server_audit_file_path = /var/log/mysql/server_audit.log server_audit_file_rotate_size = 1000000000 server_audit_file_rotations = 30 server_audit_excl_users = app_readonly # suppress high-volume app noise server_audit_query_log_limit = 1024
Capturing CONNECT, DDL, DML, DCL, and TABLE events gives authentication, schema change, data change, and privilege change coverage. Excluding a single read-only application account removes most of the volume without losing security signal.

Step 4: Enable the Slow Query Log

[mysqld] slow_query_log = ON slow_query_log_file = /var/log/mysql/mysql-slow.log long_query_time = 2 log_queries_not_using_indexes = ON log_slow_extra = ON # MySQL 8.0.14+: adds rows_examined, errors, bytes sent
log_slow_extra adds the rows examined and bytes sent counters, which turn the slow log into a practical bulk-extraction detector rather than a pure performance tool.

Step 5: Enable the General Query Log Temporarily

-- Runtime only, no restart, no persistence across restart SET GLOBAL general_log_file = '/var/log/mysql/investigation.log'; SET GLOBAL general_log = 'ON'; -- ... capture the window you need, then ... SET GLOBAL general_log = 'OFF';
The correct pattern for incident response: turn it on for a bounded window, collect, turn it off. Leaving it on in production degrades throughput and writes sensitive values in cleartext.

Step 6: Harden File Access Privileges

[mysqld] secure_file_priv = /var/lib/mysql-files # restrict OUTFILE/INFILE to one directory local_infile = OFF # block LOAD DATA LOCAL INFILE log_bin = /var/lib/mysql/binlog binlog_expire_logs_seconds = 2592000 # 30 days of binary log retention
secure_file_priv is the control that prevents SELECT INTO OUTFILE from dropping a web shell into the document root. Setting it to an empty value disables the restriction entirely and should be treated as a finding.
Security Note: The general query log records statements before they are parsed, which means SET PASSWORD, CREATE USER ... IDENTIFIED BY, and application connection strings appear in cleartext. Treat the file as a credential store: restrict it to mode 0600, exclude it from general log shipping, and purge it after the investigation.

Recommended Audit Event Classes

The server_audit plugin groups events into classes controlled by the server_audit_events variable. This baseline balances coverage against volume on a typical production server.

CONNECT

Logs successful connections, failed connections, and disconnections with source host and username. The foundation for brute force detection and session reconstruction.
Enable Critical

QUERY_DCL

Captures GRANT, REVOKE, CREATE USER, DROP USER, and SET PASSWORD. Every privilege escalation and backdoor account creation passes through this class.
Enable Critical

QUERY_DDL

Records CREATE, ALTER, and DROP of databases, tables, functions, and triggers. Detects malicious UDF creation and destructive schema changes.
Enable High Risk

TABLE

Emits a record naming each table touched by a statement, without the full query text. A compact way to monitor access to sensitive tables at manageable volume.
Enable High Risk

QUERY_DML

Logs INSERT, UPDATE, DELETE, and optionally SELECT. High volume on transactional systems, so consider QUERY_DML_NO_SELECT to keep writes without the read flood.
Tune Medium Risk

server_audit_excl_users

Excludes named accounts from auditing. Use it for a single high-volume read-only application user, never for administrative or write-capable accounts.
Tune Medium Risk
Security Note: An attacker with SUPER privilege can disable auditing at runtime with SET GLOBAL server_audit_logging = OFF. The plugin records this change as its final entry, so alert on any audit configuration event rather than assuming a quiet log means a quiet server.

MySQL Audit Log Format

The server_audit plugin writes comma-separated records with a fixed field order. Mapping these positions correctly is the first step in any MySQL SIEM integration.

Field Description Category Example Value
timestamp Event time in server timezone Timestamp 20250714 09:41:22
serverhost Hostname of the database server Metadata db-prod-01
username Account used for the connection Identity app_rw
host Client hostname or IP address Source 10.30.2.61
connectionid Server-assigned connection identifier Session 84213
queryid Sequential query identifier within the session Session 91744
operation Event class of the record Action QUERY / CONNECT / TABLE
database Default schema for the statement Target shopdb
object Statement text, or table name for TABLE events Action SELECT * FROM customers
retcode MySQL error code, 0 on success Result 1045
Pro Tip: Return code 1045 is access denied, 1044 is access denied for a database, and 1142 is a missing table-level privilege. Alerting on 1142 catches an authenticated attacker probing tables their account cannot reach.

Critical MySQL Attack Patterns

These are the statements and errors most worth building detections around. Each maps to a specific stage of a MySQL compromise.

Pattern Technique Why It Matters
SELECT ... INTO OUTFILE File write Writes arbitrary content to any path the mysql user can reach. The standard route from SQL injection to a web shell in the document root
LOAD DATA LOCAL INFILE File read A malicious server can request arbitrary files from the connecting client, turning a database connection into client-side file theft
CREATE FUNCTION ... SONAME Command execution Loads a user-defined function from a shared library, giving direct operating system command execution as the mysql user
GRANT ALL ... WITH GRANT OPTION Privilege escalation Full privilege grant, frequently to a newly created account with an innocuous name such as backup or monitor
SELECT ... FROM mysql.user Credential access Reads password hashes directly from the system schema for offline cracking
Error 1045 bursts Brute force Access denied for user, repeated from one source. The core authentication attack signal
UNION SELECT / information_schema SQL injection Schema enumeration through injected queries, usually visible in the general or audit log even when the application logs nothing
SLEEP() / BENCHMARK() Blind SQL injection Time-based inference. Appears in the slow query log by definition because the attack works by making queries slow
DROP DATABASE / TRUNCATE Destruction Ransom and wiper activity. Also seen as the cleanup stage after exfiltration completes

MySQL Log Analysis Queries

Use these shell and SQL commands to extract authentication attacks, file operations, privilege changes, and bulk extraction from MySQL logs.

Failed Logins by Source
bash> grep "Access denied for user" /var/log/mysql/error.log | grep -oP "@'\K[^']+" | sort | uniq -c | sort -rn | head -20
Counts access-denied events per source host. Requires log_error_verbosity set to 3.
Web Shell Drop Attempts
bash> grep -iE "into (outfile|dumpfile)" /var/log/mysql/server_audit.log
Any hit deserves immediate investigation. Legitimate applications almost never write files through the database engine.
UDF Command Execution
bash> grep -iE "create function.*soname|sys_exec|sys_eval" /var/log/mysql/server_audit.log
Detects loading of a user-defined function library, the standard MySQL-to-shell escalation. sys_exec and sys_eval are the canonical function names.
Privilege and Account Changes
bash> grep -iE "grant |create user|drop user|set password|alter user" /var/log/mysql/server_audit.log | grep -v "app_deploy"
Filters out the known deployment account so only unexpected privilege changes remain.
Password Hash Theft
bash> grep -iE "from mysql\.(user|global_priv)" /var/log/mysql/server_audit.log
Direct reads of the system credential tables. Only monitoring tools and DBAs should ever appear here.
SQL Injection Indicators
bash> grep -iE "union.+select|information_schema\.(tables|columns)|sleep\([0-9]|benchmark\(" /var/log/mysql/server_audit.log
Catches schema enumeration and time-based blind injection reaching the database even when the web tier logs nothing useful.
Bulk Extraction via Slow Log
bash> mysqldumpslow -s c -t 20 /var/log/mysql/mysql-slow.log
Aggregates the slow log by normalised query. With log_slow_extra enabled, look for high Rows_sent values against customer tables.
Reconstruct Changes from Binlog
bash> mysqlbinlog --base64-output=DECODE-ROWS --verbose --start-datetime="2025-07-14 09:00:00" /var/lib/mysql/binlog.000042 | grep -iE "^### (DELETE|UPDATE)" -A 5
Recovers row-level changes when no audit plugin was running. Often the only way to prove what an attacker modified.
Audit Account Privileges
SQL> SELECT user, host, plugin, account_locked, password_expired FROM mysql.user WHERE Super_priv='Y' OR File_priv='Y' OR Create_user_priv='Y';
Lists every account holding SUPER, FILE, or CREATE USER. FILE privilege is what makes INTO OUTFILE possible and should be held by nobody.
Audit Plugin Disabled
SIEM> source="mysql:audit" object IN ("SET GLOBAL server_audit_logging=OFF","UNINSTALL PLUGIN server_audit") OR object="*server_audit_events*" | table _time, username, host, object
The plugin logs its own shutdown as the last record written. Treat any gap in audit records as an incident until proven otherwise.

Best Practices for MySQL Logging

Apply these practices to get real security visibility from MySQL without crippling performance:

01

Deploy an Audit Plugin

The built-in logs were designed for troubleshooting, not security. server_audit or an equivalent plugin is the only way to get filtered, structured statement visibility that a production server can sustain.

02

Set Error Log Verbosity to 3

At the default verbosity, failed authentication is not recorded at all. This one-line change gives you brute force detection at effectively zero cost.

03

Restrict secure_file_priv

Point it at a single dedicated directory and never leave it empty. This is the control that stops SELECT INTO OUTFILE from writing a web shell into a web-accessible path.

04

Keep the General Log for Investigations Only

Enable it at runtime for a bounded window, collect what you need, then disable it. It writes credentials in cleartext and measurably reduces throughput when left running.

05

Retain Binary Logs for at Least 30 Days

The binary log is frequently the only record of what data an attacker changed. Set binlog_expire_logs_seconds deliberately rather than accepting whatever the distribution shipped.

06

Ship Logs Off the Host Immediately

MySQL log files are owned by the mysql user and are trivially deleted by anyone who compromises the service. Forward with rsyslog or a log agent so a local wipe does not destroy the evidence.

07

Normalise Timestamps to UTC

Set log_timestamps to UTC. MySQL defaults vary between versions and distributions, and mixed timezones across a replica set make timeline reconstruction unreliable.

08

Exclude Only Read-Only Accounts

When tuning audit volume, exclude a single read-only application user at most. Excluding an account that can write, grant, or administer defeats the purpose of auditing entirely.

Common MySQL Log Examples

Real output from the error log, the audit plugin, and the slow query log, showing how a MySQL compromise unfolds across sources.

Error Log: Brute Force Against root

2025-07-14T09:41:22.481203Z 84210 [Note] [MY-010926] [Server] Access denied for user 'root'@'203.0.113.44' (using password: YES) 2025-07-14T09:41:22.902118Z 84211 [Note] [MY-010926] [Server] Access denied for user 'root'@'203.0.113.44' (using password: YES) 2025-07-14T09:41:23.334902Z 84212 [Note] [MY-010926] [Server] Access denied for user 'root'@'203.0.113.44' (using password: YES)
Three failures in under two seconds from one external address. "using password: YES" confirms a password was supplied, distinguishing an attack from a misconfigured client connecting with no credentials.

Audit Log: Successful Connection After Brute Force

20250714 09:44:07,db-prod-01,root,203.0.113.44,84219,0,CONNECT,,,0 20250714 09:44:11,db-prod-01,root,203.0.113.44,84219,91740,QUERY,,'SELECT @@version, @@datadir, @@secure_file_priv',0 20250714 09:44:15,db-prod-01,root,203.0.113.44,84219,91741,QUERY,mysql,'SELECT user,host,authentication_string FROM mysql.user',0
Return code 0 on CONNECT means the brute force succeeded. The immediate follow-up queries fingerprint the server and dump password hashes: textbook post-authentication reconnaissance.

Audit Log: Web Shell Written via INTO OUTFILE

20250714 09:47:33,db-prod-01,root,203.0.113.44,84219,91746,QUERY,shopdb,'SELECT 0x3C3F70687020737973... INTO OUTFILE \'/var/www/html/uploads/config.php\'',0 20250714 09:47:33,db-prod-01,root,203.0.113.44,84219,91746,TABLE,shopdb,,0
Hex-encoded PHP written directly into the web root. This succeeds only when secure_file_priv is empty and the account holds FILE privilege: two configuration failures combining into remote code execution.

Audit Log: Backdoor Account Created

20250714 09:52:10,db-prod-01,root,203.0.113.44,84219,91751,QUERY,,'CREATE USER \'mysqlbackup\'@\'%\' IDENTIFIED BY \'***\'',0 20250714 09:52:10,db-prod-01,root,203.0.113.44,84219,91752,QUERY,,'GRANT ALL PRIVILEGES ON *.* TO \'mysqlbackup\'@\'%\' WITH GRANT OPTION',0 20250714 09:52:11,db-prod-01,root,203.0.113.44,84219,91753,QUERY,,'FLUSH PRIVILEGES',0
A plausible-sounding account granted everything from any host. The wildcard host and GRANT OPTION together make this a durable backdoor that survives a root password reset.

Slow Query Log: Bulk Customer Extraction

# Time: 2025-07-14T09:58:02.114923Z # User@Host: root[root] @ [203.0.113.44] Id: 84219 # Query_time: 41.882301 Lock_time: 0.000188 Rows_sent: 2841776 Rows_examined: 2841776 # Bytes_sent: 402883104 SET timestamp=1752487082; SELECT * FROM shopdb.customers;
2.8 million rows and 400 MB returned in a single unfiltered SELECT. Rows_sent equalling Rows_examined with no WHERE clause is the clearest possible bulk exfiltration signature.

Audit Log: SQL Injection Reaching the Database

20250714 10:03:41,db-prod-01,app_rw,10.30.2.61,84240,91802,QUERY,shopdb,'SELECT name,price FROM products WHERE id = 7 UNION SELECT table_name,column_name FROM information_schema.columns-- ',0 20250714 10:03:52,db-prod-01,app_rw,10.30.2.61,84241,91805,QUERY,shopdb,'SELECT name,price FROM products WHERE id = 7 AND SLEEP(5)-- ',0
The application account issuing UNION SELECT against information_schema followed by a SLEEP payload. Note the source is the legitimate app server: the injection is in the application, not the database.

Audit Log: Auditing Disabled

20250714 10:07:19,db-prod-01,root,203.0.113.44,84219,91811,QUERY,,'SET GLOBAL server_audit_logging=OFF',0 20250714 10:07:19,db-prod-01,root,203.0.113.44,84219,0,AUDIT,,'STOPPED',0
The plugin writes STOPPED as its final record. Any gap in the audit log with this as the last line should be treated as active compromise, not as a maintenance event.
