VMware vSphere Logs

vSphere Log Overview

A vSphere environment concentrates enormous risk into a small number of hosts. Compromise a single ESXi server and every virtual machine on it becomes accessible at the disk level, bypassing every guest operating system control, endpoint agent, and disk encryption scheme that depends on the guest being running. Compromise vCenter and the same applies across the entire estate. This is why ransomware groups shifted to targeting hypervisors directly: encrypting a datastore takes out hundreds of servers at once, and the guest agents that would have detected it are inside the machines being encrypted.

Logging spans two layers. Each ESXi host writes a set of plain text logs under /var/log, with hostd.log recording host agent operations and authentication, vmkernel.log recording kernel and storage events, auth.log recording SSH and shell authentication, and shell.log recording every command typed in the ESXi shell. Above that, vCenter Server maintains vpxd.log plus a structured events and tasks database that records every administrative action performed through the management interface, attributed to a named user.

The critical operational weakness is retention. ESXi logs live on a small local scratch partition and rotate aggressively, and on hosts booting from SD card or USB the logs may be held in a RAM disk that is lost entirely on reboot. An attacker who reboots a host after acting on it destroys the evidence without needing any anti-forensic tooling. Configuring a remote syslog target is therefore not a refinement but the precondition for any hypervisor investigation being possible at all.

Key vSphere Log Types

ESXi and vCenter produce complementary streams. Host logs show what happened on the hypervisor, vCenter events show who requested it:

Log Type Description
hostd.log The ESXi host agent log, recording virtual machine power operations, configuration changes, datastore activity, and local authentication. The primary host-level security log and the first place to look after a host compromise.
auth.log Authentication to the host itself over SSH, the Direct Console interface, and the shell. Where brute force against ESXi and successful attacker logins appear.
shell.log Every command executed in the ESXi shell, with timestamps and the invoking user. The single most valuable forensic artifact on a compromised host, since ransomware operators work almost entirely through the shell.
vpxd.log The vCenter Server daemon log, covering all management operations, host connectivity, and API sessions. Correlates administrative intent with the host-level actions that resulted.
vCenter Events and Tasks Structured records in the vCenter database exposed through the UI and API. Every virtual machine creation, clone, deletion, permission change, and login is recorded here with the responsible user. The most queryable vSphere source.
vmkernel.log VMkernel messages covering storage paths, device events, and resource conditions. Mostly operational, but datastore access errors during mass encryption surface here first.
vpxa.log The vCenter agent running on each ESXi host, showing tasks pushed down from vCenter. Useful for distinguishing actions taken through vCenter from actions taken directly on the host.
SSO and Identity Logs vmware-sts-idmd.log and related files recording Single Sign-On authentication against vCenter, including failures. Where credential attacks against the management plane appear.
Virtual Machine Logs A vmware.log file alongside each virtual machine on the datastore, recording power events, snapshot operations, and device changes for that specific machine.
Pro Tip: Actions taken directly on an ESXi host through SSH do not appear in vCenter events at all. An attacker who bypasses vCenter and works on the host leaves traces only in shell.log and auth.log, which is precisely why those two files must be forwarded off the host.

Pro Tip: Check whether the host has persistent scratch storage with vim-cmd hostsvc/advopt/view ScratchConfig.CurrentScratchLocation. If it points at /tmp or a RAM disk, all host logs are lost on every reboot and remote syslog is your only source of history.

Configuring vSphere Logging

These commands establish remote syslog from every host and raise the retention of the vCenter events database beyond its defaults.

Step 1: Configure ESXi Remote Syslog

esxcli system syslog config set --loghost='tcp://10.50.9.20:1514' \ --logdir-unique=true \ --default-rotate=20 \ --default-size=10240 esxcli system syslog reload # Verify esxcli system syslog config get
Use TCP rather than UDP so that log loss under load is detectable. The logdir-unique flag gives each host its own directory, which matters when several hosts share a scratch datastore.

Step 2: Open the Firewall for Syslog

esxcli network firewall ruleset set --ruleset-id=syslog --enabled=true esxcli network firewall refresh esxcli network firewall ruleset list --ruleset-id=syslog
The ESXi firewall blocks outbound syslog by default. Configuring a loghost without opening this ruleset produces a configuration that looks correct and delivers nothing.

Step 3: Apply Syslog Settings Across the Cluster

# PowerCLI, applied to every host at once Get-VMHost | Foreach-Object { Set-VMHostAdvancedConfiguration -VMHost $_ -Name Syslog.global.logHost ` -Value "tcp://10.50.9.20:1514" Get-VMHostFirewallException -VMHost $_ -Name "syslog" | Set-VMHostFirewallException -Enabled $true } # Confirm none were missed Get-VMHost | Select Name, @{N="LogHost";E={ ($_ | Get-AdvancedSetting -Name Syslog.global.logHost).Value }}
Host profiles or PowerCLI loops are essential. A single host added to the cluster without syslog configured becomes a blind spot an attacker can operate from freely.

Step 4: Increase vCenter Event Retention

# vCenter UI: Configure, Settings, General, Database # Event retention : 365 days (default 30) # Task retention : 365 days (default 30) # Equivalent via PowerCLI advanced settings Get-AdvancedSetting -Entity $vcenter -Name event.maxAge | Set-AdvancedSetting -Value 365 Get-AdvancedSetting -Entity $vcenter -Name event.maxAgeEnabled | Set-AdvancedSetting -Value $true
Thirty days of event retention is the default and is shorter than typical time to detection. Raising it costs only database storage.

Step 5: Enforce Lockdown Mode and Restrict Shell Access

# Strict lockdown blocks all direct host access including DCUI vim-cmd hostsvc/advopt/update UserVars.SuppressShellWarning long 0 esxcli system settings advanced set -o /UserVars/ESXiShellTimeOut -i 600 esxcli system settings advanced set -o /UserVars/ESXiShellInteractiveTimeOut -i 600 # PowerCLI: enable lockdown across the cluster Get-VMHost | ForEach-Object { ($_ | Get-View).EnterLockdownMode() } Get-VMHost | Get-VMHostService | Where-Object {$_.Key -eq "TSM-SSH"} | Stop-VMHostService
Lockdown mode forces all administration through vCenter, which means all administration is logged and attributed. SSH left enabled is the most common finding on compromised ESXi hosts.

Step 6: Forward vCenter Appliance Logs

# vCenter UI: Administration, System Configuration, Syslog Configuration # Add up to three remote syslog targets # Or via the appliance shell /opt/vmware/share/vami/vami_set_syslog 10.50.9.20 1514 tcp systemctl restart rsyslog # Confirm vpxd and SSO logs are included grep -E "vpxd|sso" /etc/vmware-syslog/syslog.conf
vCenter is a Photon OS appliance running rsyslog. Forwarding its own logs is separate from forwarding ESXi host logs and is frequently overlooked.
Security Note: On hosts booting from SD card or USB, ESXi places logs on a RAM disk unless persistent scratch is configured. Every log is lost on reboot, and a reboot is trivially disguised as maintenance. Verify persistent scratch on every host, then forward remotely regardless.

vSphere Threat Patterns

Hypervisor attacks bypass every guest control at once. These are the patterns that define real vSphere incidents.

Datastore Ransomware

Encrypting VMDK files directly on the datastore after powering off every virtual machine. Signature: mass power-off events, SSH enabled, and shell commands iterating over /vmfs/volumes.
Detect Critical

SSH and Shell Enablement

Starting the TSM-SSH service or disabling lockdown mode to gain direct host access. Almost always the first step, because actions taken on the host bypass vCenter logging entirely.
Detect Critical

Virtual Machine Cloning and Export

Cloning a domain controller or database server and exporting it as OVF. Copies an entire system including its disk contents without any guest-side agent noticing.
Detect Critical

Datastore Browsing and Download

Downloading VMDK files through the datastore browser or HTTPS file API. Extracts a full disk image that can be mounted offline, defeating guest access controls entirely.
Detect High Risk

Malicious VIB Installation

Installing an unsigned installation bundle to persist on the hypervisor across reboots and updates. Requires the acceptance level to be lowered, which is itself logged.
Detect High Risk

vCenter Permission Escalation

Granting the Administrator role at the root folder, or adding an account to the SSO administrators group. Yields control of every host and virtual machine in the inventory.
Detect Critical
Security Note: Encrypting a datastore defeats guest disk encryption because BitLocker and LUKS protect data at rest inside a powered-off machine, not the VMDK container itself. Hypervisor-level backup and immutable snapshots are the only controls that meaningfully address this.

Critical vCenter Events

vCenter event types are stable identifiers, making them precise detection anchors in a SIEM.

Event Type Meaning Why It Matters
UserLoginSessionEvent A user authenticated to vCenter Baseline for detecting logins from unexpected addresses, at unusual hours, or with scripted user agents
BadUsernameSessionEvent Failed authentication to vCenter Bursts against the SSO administrator account are brute force against the entire virtual estate
PermissionAddedEvent A role was granted on an inventory object Administrator role at the root folder is total control. Every occurrence needs a matching change ticket
VmClonedEvent A virtual machine was cloned Cloning a domain controller copies the entire directory database including every credential hash
DatastoreFileDownloadEvent A file was downloaded from a datastore VMDK download is full disk exfiltration that no guest agent will observe
VmPoweredOffEvent A virtual machine was powered off Individually routine. Dozens within minutes is the opening move of datastore ransomware
VmRemovedEvent A virtual machine was deleted from inventory Destructive action, and also used to hide a cloned machine after its disks have been copied
HostServiceStartedEvent A host service such as SSH was started TSM-SSH starting is the precursor to direct host access that bypasses vCenter logging
LockdownModeDisabledEvent Lockdown mode was turned off on a host Re-opens direct host administration. Effectively never legitimate outside a documented break-glass procedure
VmAcquiredTicketEvent A console or MKS ticket was acquired Someone opened the virtual console of a machine, which provides keyboard access with no guest authentication logging
HostEsxAdminsGrantedEvent A group was granted host admin rights Adding a group named ESX Admins in Active Directory historically granted automatic host administrator access
Pro Tip: VmAcquiredTicketEvent is heavily underused. Console access means an attacker can interact with a machine at the keyboard level, and nothing inside the guest records how that session arrived. Alert on console access to tier zero systems.

vSphere Log Analysis Queries

These PowerCLI, shell, and SIEM queries cover hypervisor compromise from host access through to mass encryption.

SSH Enabled on a Host
PowerCLI> Get-VMHost | Get-VMHostService | Where-Object {$_.Key -eq "TSM-SSH" -and $_.Running -eq $true} | Select-Object VMHost, Label, Running, Policy
SSH running on a production host is either a forgotten troubleshooting session or an attacker. Both need closing.
Mass Power-Off (Ransomware Precursor)
SIEM> source="vcenter" eventType="VmPoweredOffEvent" | bucket _time span=10m | stats dc(vm_name) as vms, values(user) by _time, host_name | where vms > 10
More than ten machines powered off in ten minutes is either a major outage or the opening move of datastore encryption. Both warrant an immediate page.
Shell Commands on the Host
bash> grep -iE "esxcli|vim-cmd|vmkfstools|find /vmfs|chmod \+x|wget|curl|python" /var/log/shell.log
shell.log records every command typed on the host. Ransomware operators work almost entirely here, so this file is the highest value forensic artifact on a compromised ESXi server.
Host Authentication Failures
bash> grep -iE "authentication failed|Failed password|Cannot login" /var/log/auth.log | awk '{print $NF}' | sort | uniq -c | sort -rn
Brute force against the root account of an ESXi host. Since ESXi root has no lockout by default, this can continue indefinitely.
Virtual Machine Cloning and Export
PowerCLI> Get-VIEvent -MaxSamples 100000 -Start (Get-Date).AddDays(-30) | Where-Object {$_ -is [VMware.Vim.VmClonedEvent] -or $_ -is [VMware.Vim.VmBeingDeployedEvent]} | Select-Object CreatedTime, UserName, @{N="Source";E={$_.SourceVm.Name}}, @{N="Clone";E={$_.Vm.Name}}
Cloning a domain controller copies the entire Active Directory database. Reconcile every clone against a change request.
Datastore File Downloads
SIEM> source="vcenter" eventType="DatastoreFileDownloadEvent" | search datastore="*.vmdk" OR datastore="*.vmx" | table _time, user, ipAddress, datastore
Downloading a VMDK extracts a complete disk image that can be mounted offline, bypassing every access control inside the guest.
Permission Grants
PowerCLI> Get-VIEvent -MaxSamples 100000 -Start (Get-Date).AddDays(-30) | Where-Object {$_ -is [VMware.Vim.PermissionAddedEvent]} | Select-Object CreatedTime, UserName, @{N="Grantee";E={$_.Principal}}, @{N="Role";E={$_.Role.Name}}, @{N="On";E={$_.Entity.Name}}
Administrator role granted at the root folder is control of the entire virtual estate in a single action.
Lockdown Mode Changes
PowerCLI> Get-VMHost | Select-Object Name, @{N="Lockdown";E={(Get-View $_).Config.LockdownMode}}, ConnectionState | Where-Object {$_.Lockdown -eq "lockdownDisabled"}
Any host with lockdown disabled permits direct administration that never reaches vCenter events. Track this as a configuration drift metric.
Unsigned VIB Installation
bash> esxcli software acceptance get ; esxcli software vib list | grep -viE "VMware|VMwareCertified|VMwareAccepted"
An acceptance level of CommunitySupported combined with an unrecognised VIB is hypervisor-level persistence surviving reboots and patches.
Syslog Configuration Drift
PowerCLI> Get-VMHost | Select Name, @{N="LogHost";E={($_ | Get-AdvancedSetting -Name Syslog.global.logHost).Value}} | Where-Object {[string]::IsNullOrEmpty($_.LogHost)}
Any host returned here keeps its logs only locally, where a reboot destroys them. Run this as a scheduled control check.

Best Practices for vSphere Logging

Apply these practices so hypervisor evidence survives the incident it is meant to document:

01

Configure Remote Syslog on Every Host

ESXi logs rotate quickly and may live on a RAM disk. Without remote syslog, a reboot erases the entire history and an attacker needs no anti-forensic tooling at all.

02

Open the Syslog Firewall Ruleset

ESXi blocks outbound syslog by default. Setting a loghost without enabling the ruleset produces a configuration that appears correct and delivers nothing.

03

Collect shell.log and auth.log Specifically

Direct host activity never appears in vCenter events. These two files are the only record of an attacker who bypassed the management plane.

04

Enable Lockdown Mode and Disable SSH

Forcing administration through vCenter means every action is attributed to a named user. SSH left running is the single most common finding on compromised hosts.

05

Raise vCenter Event Retention

Thirty days is the default and is shorter than typical dwell time. Increasing it to a year costs only database storage and preserves the attribution layer.

06

Alert on Mass Power-Off

Bulk power-off precedes datastore encryption. It is one of the few detections that can catch hypervisor ransomware in the window before damage becomes irreversible.

07

Treat vCenter as a Tier Zero Asset

It controls every virtual machine including domain controllers. Separate administrative accounts, require MFA, and never join it to the domain it manages.

08

Verify Persistent Scratch Storage

Hosts booting from SD or USB may keep logs in memory only. Check ScratchConfig on every host, because the failure is silent and total.

Common vSphere Log Examples

A hypervisor ransomware incident traced from stolen vCenter credentials to encrypted datastores.

vCenter Brute Force

2025-07-14T09:12:04.117Z info vpxd[07412] [Originator@6876 sub=Vimsvc.ha-eventmgr] Event 84210 : Cannot login administrator@vsphere.local@10.99.4.117 2025-07-14T09:12:09.882Z info vpxd[07412] [Originator@6876 sub=Vimsvc.ha-eventmgr] Event 84211 : Cannot login administrator@vsphere.local@10.99.4.117 2025-07-14T09:12:15.229Z info vpxd[07412] [Originator@6876 sub=Vimsvc.ha-eventmgr] Event 84212 : Cannot login root@10.99.4.117
Repeated failures against the SSO administrator from a VPN pool address. Cross-referencing the VPN session log identifies whose credentials were used to reach this point.

Successful Login from a Scripted Client

2025-07-14T09:40:53.221Z info vpxd[07412] [Originator@6876 sub=Vimsvc.ha-eventmgr] Event 84290 : User administrator@VSPHERE.LOCAL@10.99.4.117 logged in as pyvmomi Python/3.11.6 (Linux; x86_64) 2025-07-14T09:40:54.118Z info vpxd[07412] [Originator@6876 sub=Vimsvc] [Auth]: User VSPHERE.LOCAL\administrator
The user agent is the tell. Administrators use the HTML5 client or PowerCLI, so a raw pyvmomi session against the SSO administrator account is scripted tooling.

SSH Enabled to Bypass vCenter Logging

2025-07-14T09:44:07.229Z info vpxd[07412] [Originator@6876 sub=Vimsvc.ha-eventmgr] Event 84302 : The service TSM-SSH has been started on esxi-prod-04.corp.local 2025-07-14T09:44:12.881Z info vpxd[07412] [Originator@6876 sub=Vimsvc.ha-eventmgr] Event 84303 : Lockdown mode disabled for host esxi-prod-04.corp.local
Two events that together mean everything after this point happens directly on the host and will not appear in vCenter. From here only shell.log tells the story.

Host Login and Reconnaissance in shell.log

2025-07-14T09:47:33Z auth.log: SSH login for 'root' from 10.99.4.117 2025-07-14T09:47:41Z shell[2104881]: [root]: esxcli vm process list 2025-07-14T09:47:52Z shell[2104881]: [root]: df -h 2025-07-14T09:48:04Z shell[2104881]: [root]: ls -lah /vmfs/volumes/ 2025-07-14T09:48:19Z shell[2104881]: [root]: find /vmfs/volumes/ -name "*.vmdk" | wc -l
Enumerating running machines, storage capacity, and counting VMDK files. This is target assessment: the attacker is measuring how much damage a single command can do.

Domain Controller Cloned for Credential Theft

2025-07-14T09:52:10.774Z info vpxd[07412] [Originator@6876 sub=Vimsvc.ha-eventmgr] Event 84350 : Task: Clone virtual machine Source: DC01-PROD on esxi-prod-04.corp.local Target: temp-restore-01 in datastore [SAN-VOL-02] Initiated by: VSPHERE.LOCAL\administrator from 10.99.4.117 2025-07-14T09:58:02.114Z info vpxd[07412] Event 84361 : DatastoreFileDownloadEvent: [SAN-VOL-02] temp-restore-01/temp-restore-01-flat.vmdk downloaded from 10.99.4.117
A domain controller cloned then its flat disk downloaded. That file contains NTDS.dit and every credential hash in the domain. No agent inside DC01-PROD observed any of this.

Mass Power-Off Preceding Encryption

2025-07-14T10:02:44Z shell[2104881]: [root]: esxcli vm process list | grep 'World ID' | awk '{print $3}' > /tmp/w 2025-07-14T10:02:51Z shell[2104881]: [root]: for w in $(cat /tmp/w); do esxcli vm process kill -t=force -w=$w; done 2025-07-14T10:02:58.229Z info hostd[2098412] Event: VmPoweredOffEvent DC01-PROD 2025-07-14T10:02:58.441Z info hostd[2098412] Event: VmPoweredOffEvent SQL-PROD-01 2025-07-14T10:02:58.662Z info hostd[2098412] Event: VmPoweredOffEvent APP-PROD-03 2025-07-14T10:02:59.118Z info hostd[2098412] Event: VmPoweredOffEvent FILE-PROD-02
Forced termination of every running machine in under a second. Machines must be powered off before their VMDK files can be encrypted, which is what makes bulk power-off the last useful warning.

Datastore Encryption

2025-07-14T10:04:55Z shell[2104881]: [root]: chmod +x /tmp/.x/encrypt 2025-07-14T10:04:58Z shell[2104881]: [root]: /tmp/.x/encrypt -p /vmfs/volumes/SAN-VOL-02 -t 40 2025-07-14T10:05:31.882Z warning vmkernel: WARNING: FS3J: Failed to lock file /vmfs/volumes/SAN-VOL-02/DC01-PROD/DC01-PROD-flat.vmdk 2025-07-14T10:06:14.229Z info shell[2104881]: [root]: echo 'READ_ME.txt' > /vmfs/volumes/SAN-VOL-02/READ_ME.txt
An unsigned binary staged in a hidden temp directory encrypting the datastore with 40 parallel threads. Guest disk encryption offers no protection here, because the VMDK container itself is what gets encrypted.

Evidence Destruction: Log Clearing and Reboot

2025-07-14T10:11:03Z shell[2104881]: [root]: esxcli system syslog config set --loghost='' 2025-07-14T10:11:09Z shell[2104881]: [root]: > /var/log/shell.log 2025-07-14T10:11:12Z shell[2104881]: [root]: > /var/log/auth.log 2025-07-14T10:11:18Z shell[2104881]: [root]: reboot
The loghost is cleared, local logs truncated, and the host rebooted. Everything above survived only because it had already been forwarded to the syslog collector before line one of this block executed.
