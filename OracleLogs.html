Oracle Database Logs

Oracle Log Overview

Oracle Database separates diagnostic logging from security auditing, and the two live in completely different places. Diagnostic output (instance startup, ORA- errors, structural changes, and background process messages) is written to the alert log and trace files inside the Automatic Diagnostic Repository (ADR). Security auditing is written to the database itself, either to the modern UNIFIED_AUDIT_TRAIL introduced in Oracle 12c or to the legacy AUD$ table used by earlier releases. A third stream, the listener log, sits outside the database entirely and records every connection request that reaches the instance, including those that never authenticate successfully.

Unified Auditing consolidated what used to be at least six separate audit trails into a single read-only view. It is enabled in mixed mode by default from 12c onward, which means a small set of predefined policies is active but most security-relevant activity is not captured until an administrator explicitly enables the right policies. Oracle ships several ready-made policies (ORA_SECURECONFIG, ORA_LOGON_FAILURES, ORA_ACCOUNT_MGMT, and ORA_DATABASE_PARAMETER), and enabling them takes a single statement each, yet they remain switched off on a large proportion of production estates.

For sensitive data, Unified Auditing alone can be too coarse. Fine-Grained Auditing (FGA) allows a policy to fire only when a specific column is selected or when a boolean condition is met, so you can audit access to a salary column without generating a record for every query against the employee table. Combined with the alert log for structural events and the listener log for connection-level reconnaissance, these sources give a complete picture that satisfies the privileged-activity and sensitive-data monitoring requirements in NIST SP 800-92 and the Saudi NCA controls.

Key Oracle Log Types

Oracle produces several log streams with very different retention, format, and access models. Knowing which one answers which question saves critical time during an investigation:

Log Type Description
Alert Log The chronological diagnostic log for the instance, available as plain text (alert_<SID>.log) and as structured XML (log.xml). Records startup and shutdown, ORA- errors, tablespace and datafile changes, redo log switches, and ALTER SYSTEM operations. Always the first artifact to review.
Unified Audit Trail The consolidated security audit trail exposed through the UNIFIED_AUDIT_TRAIL view. Captures logon and logoff, privilege use, DDL, DML, Data Pump and RMAN activity, and Database Vault events in a single read-only stream. Cannot be modified with DML, even by SYS.
Listener Log Written by the TNS listener process outside the database. Records every connection request with source host, program name, and service name, including attempts that fail before authentication. The primary source for detecting service enumeration and TNS-level attacks.
Fine-Grained Audit Trail Policy-driven auditing at column and row granularity, queried through DBA_FGA_AUDIT_TRAIL or the unified trail. Fires only when a defined condition matches, which makes it the practical way to audit access to sensitive columns without overwhelming volume.
Traditional Audit Trail (AUD$) The pre-12c audit trail stored in SYS.AUD$ and surfaced through DBA_AUDIT_TRAIL, plus optional OS-file and XML destinations. Still present in mixed-mode deployments. Unlike the unified trail it lives in a normal table, so a privileged attacker can delete rows from it.
Trace Files and Incident Dumps Per-process trace files and ADR incident packages generated on serious errors. Contain SQL text, bind variables, and call stacks. Highly sensitive because bind data can include cleartext credentials and personal data.
Redo and Archive Logs The change stream used for recovery and replication. Not a security log, but with LogMiner it can reconstruct DML that no audit policy captured, provided the relevant archive logs are still retained.
Pro Tip: The unified audit trail is protected against DML, but records are still purgeable through DBMS_AUDIT_MGMT.CLEAN_AUDIT_TRAIL. Audit that package explicitly, otherwise a privileged attacker can erase the trail through a supported interface without ever issuing a DELETE.

Log File Locations

Oracle 11g and later organise diagnostic output under the ADR base, whose root is normally $ORACLE_BASE. Resolve the exact paths for a running instance rather than assuming defaults.

Log Default Location
Alert Log (text) $ORACLE_BASE/diag/rdbms/<db_name>/<instance>/trace/alert_<SID>.log
Alert Log (XML) $ORACLE_BASE/diag/rdbms/<db_name>/<instance>/alert/log.xml
Listener Log $ORACLE_BASE/diag/tnslsnr/<hostname>/listener/trace/listener.log
Unified Audit Trail AUDSYS schema in the database; spillover files in $ORACLE_BASE/audit/<instance>/ when the database is unavailable
Mandatory SYSDBA Audit $ORACLE_BASE/admin/<db_name>/adump/ (controlled by AUDIT_FILE_DEST)
User and Background Traces $ORACLE_BASE/diag/rdbms/<db_name>/<instance>/trace/
Incident Dumps $ORACLE_BASE/diag/rdbms/<db_name>/<instance>/incident/
Pro Tip: Run SELECT value FROM v$diag_info WHERE name = 'Diag Trace'; to get the exact trace directory, or use adrci with show alert -tail -f to follow the alert log live without hunting for the path.

Enabling Unified Auditing

Unified Auditing works through named policies. You create a policy describing what to capture, then enable it, optionally scoped to specific users or excluding noisy service accounts. All statements require the AUDIT_ADMIN role.

Step 1: Confirm the Auditing Mode

SELECT value FROM v$option WHERE parameter = 'Unified Auditing'; -- TRUE = pure unified auditing -- FALSE = mixed mode (traditional AUD$ still active alongside unified) SELECT policy_name, enabled_option, entity_name, success, failure FROM audit_unified_enabled_policies ORDER BY policy_name;
Establishes which mode the database runs in and which policies are already enabled. On a default 19c installation expect only ORA_SECURECONFIG and ORA_LOGON_FAILURES.

Step 2: Enable the Oracle-Supplied Baseline Policies

AUDIT POLICY ORA_SECURECONFIG; AUDIT POLICY ORA_LOGON_FAILURES; AUDIT POLICY ORA_ACCOUNT_MGMT; AUDIT POLICY ORA_DATABASE_PARAMETER; AUDIT POLICY ORA_DV_AUDPOL; -- only if Database Vault is licensed AUDIT POLICY ORA_RAS_POLICY_MGMT; -- Real Application Security policy changes
Covers privilege and role grants, security configuration changes, account creation and modification, and failed logons with almost no tuning effort. This is the minimum viable audit baseline.

Step 3: Create a Custom Policy for Privileged Activity

CREATE AUDIT POLICY htl_privileged_activity PRIVILEGES CREATE ANY TABLE, DROP ANY TABLE, SELECT ANY TABLE, ALTER ANY TABLE, CREATE ANY PROCEDURE, EXECUTE ANY PROCEDURE, GRANT ANY PRIVILEGE, GRANT ANY ROLE, BECOME USER ACTIONS LOGON, LOGOFF, CREATE USER, ALTER USER, DROP USER, CREATE ROLE, GRANT, REVOKE, ALTER SYSTEM, ALTER DATABASE ACTIONS COMPONENT = DATAPUMP EXPORT, IMPORT CONTAINER = CURRENT; AUDIT POLICY htl_privileged_activity;
Combines system privilege use, security-relevant actions, and Data Pump component auditing in one policy. Data Pump coverage matters because expdp is the most convenient bulk exfiltration tool on any Oracle host.

Step 4: Audit Sensitive Objects Only

CREATE AUDIT POLICY htl_pii_access ACTIONS SELECT, INSERT, UPDATE, DELETE ON hr.employees, SELECT ON finance.payment_cards, SELECT ON hr.salaries; AUDIT POLICY htl_pii_access EXCEPT app_service_user;
Object-level auditing scoped to regulated tables. The EXCEPT clause suppresses the high-volume application account while still recording every human and every other identity that touches the data.

Step 5: Add Fine-Grained Auditing for Column-Level Sensitivity

BEGIN DBMS_FGA.ADD_POLICY( object_schema => 'HR', object_name => 'EMPLOYEES', policy_name => 'FGA_SALARY_ACCESS', audit_column => 'SALARY, NATIONAL_ID', audit_condition => NULL, statement_types => 'SELECT,UPDATE', audit_trail => DBMS_FGA.DB + DBMS_FGA.EXTENDED); END; /
Fires only when the SALARY or NATIONAL_ID column is referenced. The EXTENDED trail additionally records the full SQL text and bind variables, which is what makes the record actionable.

Step 6: Configure Audit Trail Retention and Purging

BEGIN DBMS_AUDIT_MGMT.INIT_CLEANUP( audit_trail_type => DBMS_AUDIT_MGMT.AUDIT_TRAIL_UNIFIED, default_cleanup_interval => 24); DBMS_AUDIT_MGMT.SET_LAST_ARCHIVE_TIMESTAMP( audit_trail_type => DBMS_AUDIT_MGMT.AUDIT_TRAIL_UNIFIED, last_archive_time => SYSTIMESTAMP - 180); DBMS_AUDIT_MGMT.CREATE_PURGE_JOB( audit_trail_type => DBMS_AUDIT_MGMT.AUDIT_TRAIL_UNIFIED, audit_trail_purge_interval => 24, audit_trail_purge_name => 'HTL_UNIFIED_PURGE', use_last_arch_timestamp => TRUE); END; /
Purges only records older than the archive timestamp, guaranteeing that 180 days remain queryable. Without a purge job the AUDSYS tablespace grows until the database stops accepting connections.
Security Note: Auditing of SYSDBA and SYSOPER connections is mandatory and cannot be disabled, but those records are written as operating system files in AUDIT_FILE_DEST, not into the database. Anyone with OS-level access to the Oracle account can delete them, so forward that directory to a remote collector.

Recommended Audit Policies

Oracle ships a set of predefined unified audit policies that cover the majority of regulatory requirements. Enabling them costs nothing and requires no tuning, yet they are frequently left disabled.

ORA_SECURECONFIG

Audits security-critical configuration: ALTER SYSTEM, privilege and role grants, user creation, audit policy changes, and Data Pump activity. The single most valuable policy on the instance.
Enable Critical

ORA_LOGON_FAILURES

Records every unsuccessful logon with the originating host and program. The basis for brute force, password spraying, and default-credential detection.
Enable Critical

ORA_ACCOUNT_MGMT

Captures CREATE USER, ALTER USER, DROP USER, CREATE ROLE, and profile changes. Detects backdoor accounts and password resets on dormant identities.
Enable Critical

ORA_DATABASE_PARAMETER

Audits changes to initialization parameters through ALTER SYSTEM and ALTER DATABASE. Catches attempts to weaken security settings such as O7_DICTIONARY_ACCESSIBILITY or REMOTE_OS_AUTHENT.
Enable High Risk

Data Pump Component Auditing

ACTIONS COMPONENT = DATAPUMP records export and import operations. An unscheduled expdp of a full schema is one of the clearest bulk exfiltration signals Oracle produces.
Enable High Risk

Fine-Grained Audit Policies

Column and condition scoped auditing through DBMS_FGA. The only practical way to monitor access to a sensitive column on a high-traffic table without unusable volume.
Enable Medium Risk
Security Note: Enabling a policy with AUDIT POLICY p BY user restricts it to that user, while EXCEPT user excludes them. Using BY on a policy intended for whole-instance coverage is a common misconfiguration that silently leaves everyone else unaudited.

Critical Oracle Error Codes

These ORA codes appear in the alert log, the listener log, and the RETURN_CODE column of the unified audit trail. They are the highest-signal values to alert on.

Code Meaning Why It Matters
ORA-01017 Invalid username or password The core failed-authentication code. Repetition against one account is brute force; across many accounts it is password spraying
ORA-28000 The account is locked Confirms a brute force attempt reached the FAILED_LOGIN_ATTEMPTS profile limit, or that an attacker locked out a legitimate account
ORA-28001 The password has expired Frequently reveals dormant or forgotten service accounts being probed with old credentials
ORA-01031 Insufficient privileges A valid session attempting actions beyond its grants, a strong indicator of post-compromise privilege probing
ORA-00942 Table or view does not exist In bursts this is object enumeration or blind SQL injection rather than an application defect
ORA-12514 Listener does not know of the requested service Service name enumeration against the listener, a standard first step in Oracle reconnaissance
ORA-12541 No listener Port scanning or an attempt to reach a listener that has been stopped, possibly by an attacker
ORA-01578 Data block corrupted Storage failure or deliberate tampering with datafiles at the operating system level
ORA-00600 / ORA-07445 Internal error / core dump Engine-level faults that can result from exploitation attempts against the database process itself
Pro Tip: ORA-01017 events reach the unified audit trail only if ORA_LOGON_FAILURES or an equivalent policy is enabled. If your instance shows zero failed logons over a long period, assume the policy is missing rather than concluding nobody is attacking you.

Oracle Log Analysis Queries

Run these against the unified audit trail and the listener log to detect authentication attacks, privilege abuse, bulk exports, and audit tampering.

Failed Logon Bursts
SQL> SELECT dbusername, userhost, client_program_name, COUNT(*) AS fails FROM unified_audit_trail WHERE action_name = 'LOGON' AND return_code = 1017 AND event_timestamp > SYSTIMESTAMP - INTERVAL '1' HOUR GROUP BY dbusername, userhost, client_program_name HAVING COUNT(*) > 5 ORDER BY fails DESC;
Groups ORA-01017 failures by account and source host to separate a mistyped password from a sustained attack.
Privilege and Role Grants
SQL> SELECT event_timestamp, dbusername, action_name, object_name, sql_text FROM unified_audit_trail WHERE action_name IN ('GRANT','REVOKE','CREATE USER','ALTER USER') ORDER BY event_timestamp DESC FETCH FIRST 100 ROWS ONLY;
Every grant of DBA, SYSDBA, or ANY privileges should be reconciled against a change ticket.
Data Pump Export Activity
SQL> SELECT event_timestamp, dbusername, userhost, dp_text_parameters1, dp_boolean_parameters1 FROM unified_audit_trail WHERE audit_type = 'Datapump' ORDER BY event_timestamp DESC;
Reveals expdp jobs including the schemas and dump file paths requested. Unscheduled full-schema exports are prime exfiltration candidates.
SYSDBA Connections
SQL> SELECT event_timestamp, dbusername, os_username, userhost, client_program_name FROM unified_audit_trail WHERE dbusername = 'SYS' OR system_privilege_used LIKE '%SYSDBA%' ORDER BY event_timestamp DESC;
SYSDBA sessions bypass most access control. Every one should map to a named human and an approved maintenance window.
Audit Trail Purging
SQL> SELECT event_timestamp, dbusername, action_name, object_name, sql_text FROM unified_audit_trail WHERE object_name = 'DBMS_AUDIT_MGMT' OR sql_text LIKE '%CLEAN_AUDIT_TRAIL%' OR action_name = 'NOAUDIT' ORDER BY event_timestamp DESC;
Detects both supported purging of the audit trail and NOAUDIT statements disabling policies. Alert on these in real time.
Listener Service Enumeration
bash> grep "TNS-12514" $ORACLE_BASE/diag/tnslsnr/$(hostname)/listener/trace/listener.log | awk -F'HOST=' '{print $2}' | cut -d')' -f1 | sort | uniq -c | sort -rn | head
Counts unknown-service errors per source host in the listener log, exposing hosts brute forcing SID and service names.
Fine-Grained Audit Hits
SQL> SELECT event_timestamp, dbusername, object_schema, object_name, fga_policy_name, sql_text FROM unified_audit_trail WHERE audit_type = 'FineGrainedAudit' ORDER BY event_timestamp DESC;
Returns only the queries that actually touched an audited sensitive column, with full SQL text when the EXTENDED trail is used.
Alert Log Errors
bash> adrci exec="set home diag/rdbms/orcl/orcl; show alert -p \"message_text like '%ORA-%'\" -term" | tail -50
Extracts recent ORA- errors from the alert log through adrci without needing to locate the file manually.
Verify Enabled Policies
SQL> SELECT policy_name, enabled_option, entity_name, entity_type, success, failure FROM audit_unified_enabled_policies ORDER BY policy_name;
Run this as a scheduled control check. A policy silently disappearing from this list means someone issued NOAUDIT.
Off-Hours Sensitive Access
SIEM> source="oracle:unified_audit" object_schema="HR" action_name="SELECT" | eval hr=strftime(_time,"%H") | where hr<6 OR hr>20 | stats count values(sql_text) by dbusername, userhost
Correlates access to HR data outside working hours with the originating workstation, a high fidelity insider threat signal.

Best Practices for Oracle Logging

Follow these practices to keep Oracle audit data complete, performant, and trustworthy:

01

Move AUDSYS to Its Own Tablespace

By default the unified audit trail lives in SYSAUX. A busy audit policy can fill SYSAUX and take the database down. Relocate AUDSYS with DBMS_AUDIT_MGMT.SET_AUDIT_TRAIL_LOCATION and monitor its growth separately.

02

Enable the Predefined Policies First

ORA_SECURECONFIG, ORA_LOGON_FAILURES, and ORA_ACCOUNT_MGMT deliver the majority of required coverage with no tuning and negligible overhead. Turn them on before designing anything custom.

03

Forward the Trail Off the Database

An attacker with AUDIT_ADMIN can purge records through supported interfaces. Continuously export the unified audit trail to a SIEM so the evidence exists somewhere the database administrator cannot reach.

04

Collect the Listener Log

The listener log records connection attempts that never become sessions and therefore never appear in any audit trail. It is the only place service enumeration and pre-authentication attacks are visible.

05

Use FGA Instead of Blanket Object Auditing

Auditing every SELECT on a high-traffic table produces volume nobody reads. A fine-grained policy on the sensitive columns delivers the same compliance outcome at a fraction of the cost.

06

Protect Trace Files and Incident Dumps

Trace files can contain bind variable values including credentials and personal data. Restrict directory permissions, include them in data classification, and purge them on a defined schedule.

07

Schedule Purging, Never Manual Deletion

Create a DBMS_AUDIT_MGMT purge job tied to an archive timestamp. Ad hoc purging is indistinguishable from anti-forensics and destroys the retention guarantee auditors rely on.

08

Alert on NOAUDIT Immediately

Legitimate policy changes are rare and planned. Treat any NOAUDIT statement or audit policy drop as a potential incident and page on it rather than reviewing it in the next audit cycle.

Common Oracle Log Examples

These entries show how the same attack chain surfaces across the listener log, the alert log, and the unified audit trail.

Listener Log: Service Name Enumeration

14-JUL-2025 06:12:44 * (CONNECT_DATA=(SID=ORCL)(CID=(PROGRAM=)(HOST=__jdbc__)(USER=))) * (ADDRESS=(PROTOCOL=tcp)(HOST=203.0.113.44)(PORT=51884)) * establish * ORCL * 12514 TNS-12514: TNS:listener does not currently know of service requested in connect descriptor
An empty PROGRAM field and a generic __jdbc__ host, repeated with different SID values from one address, is automated service name brute forcing rather than a misconfigured client.

Unified Audit Trail: Failed Logon (ORA-01017)

EVENT_TIMESTAMP_UTC : 2025-07-14 06:41:22.481 DBUSERNAME : SYSTEM ACTION_NAME : LOGON RETURN_CODE : 1017 USERHOST : kali OS_USERNAME : root CLIENT_PROGRAM_NAME : sqlplus@kali (TNS V1-V3) AUTHENTICATION_TYPE : (TYPE=(DATABASE));(CLIENT ADDRESS=((PROTOCOL=tcp)(HOST=203.0.113.44)(PORT=51902)))
Return code 1017 against the SYSTEM account, from an OS user named root on a host called kali. The client metadata alone is enough to justify immediate containment.

Account Lockout After Brute Force (ORA-28000)

EVENT_TIMESTAMP_UTC : 2025-07-14 06:44:10.229 DBUSERNAME : SYSTEM ACTION_NAME : LOGON RETURN_CODE : 28000 USERHOST : kali UNIFIED_AUDIT_POLICIES : ORA_LOGON_FAILURES
The profile's FAILED_LOGIN_ATTEMPTS limit has been reached and the account is now locked. This also means a denial of service against a real account is trivially achievable.

Privilege Escalation: DBA Role Granted

EVENT_TIMESTAMP_UTC : 2025-07-14 07:02:18.774 DBUSERNAME : APP_ADMIN ACTION_NAME : GRANT OBJECT_NAME : DBA SQL_TEXT : GRANT DBA TO batch_svc SYSTEM_PRIVILEGE_USED : GRANT ANY ROLE USERHOST : appsrv01 CLIENT_PROGRAM_NAME : sqlplus.exe UNIFIED_AUDIT_POLICIES : ORA_SECURECONFIG
An application account granting the DBA role to a batch service account. Application identities should never hold GRANT ANY ROLE, and this grant reaches full database control in one statement.

Bulk Exfiltration: Unscheduled Data Pump Export

EVENT_TIMESTAMP_UTC : 2025-07-14 07:19:53.006 AUDIT_TYPE : Datapump DBUSERNAME : BATCH_SVC DP_TEXT_PARAMETERS1 : MASTER TABLE: "BATCH_SVC"."SYS_EXPORT_SCHEMA_01" JOB_TYPE: EXPORT SCHEMAS: HR,FINANCE DUMPFILE: /tmp/.cache/exp01.dmp USERHOST : appsrv01
A full export of the HR and FINANCE schemas written to a hidden directory under /tmp. The dump file path is the strongest indicator here: legitimate exports go to a registered directory object.

Fine-Grained Audit: Salary Column Access

EVENT_TIMESTAMP_UTC : 2025-07-14 02:31:09.118 AUDIT_TYPE : FineGrainedAudit FGA_POLICY_NAME : FGA_SALARY_ACCESS DBUSERNAME : R_ALMUTAIRI OBJECT_SCHEMA : HR OBJECT_NAME : EMPLOYEES SQL_TEXT : SELECT employee_id, national_id, salary FROM hr.employees CLIENT_PROGRAM_NAME : Toad.exe USERHOST : WKS-HR-22
A full extract of national ID and salary columns at 02:31 using an ad hoc query tool. The FGA policy fired precisely because the protected columns were referenced.

Alert Log: Security Parameter Weakened

2025-07-14T07:26:41.882110+03:00 ALTER SYSTEM SET remote_os_authent=TRUE SCOPE=SPFILE; 2025-07-14T07:27:03.441207+03:00 Shutting down instance (immediate) (OS id: 44219) Stopping background process SMON
Setting REMOTE_OS_AUTHENT to TRUE allows a client to assert its own operating system identity for authentication. Followed immediately by a restart to apply it, this is a deliberate backdoor.
