DHCP Logs

DHCP Log Overview

DHCP logs answer a question that almost every other log implicitly assumes has already been answered: which physical device was using this IP address at this moment. Firewall logs, proxy logs, IDS alerts, and DNS queries all identify actors by address, and on any network using dynamic addressing those addresses move between devices constantly. Without DHCP records, an alert saying that 10.30.2.61 contacted a command and control server identifies a lease, not a laptop, and the investigation stops there.

The protocol itself is a four-message exchange: the client broadcasts a DHCPDISCOVER, servers respond with a DHCPOFFER, the client requests a specific offer with DHCPREQUEST, and the server confirms with DHCPACK. Each message carries the client hardware address, and most clients also supply a hostname and a vendor class identifier. That combination of MAC address, hostname, and vendor string is what makes DHCP logs valuable beyond simple attribution: it is effectively a passive asset inventory, recording every device that joins the network including the ones nobody registered.

DHCP is also an attack surface in its own right. Because the protocol has no authentication, any host on a segment can answer a discover broadcast. A rogue DHCP server that wins the race supplies its own address as the default gateway and DNS server, placing the attacker in the middle of the victim's traffic. Related techniques include starvation attacks that exhaust the address pool to force clients onto a rogue server, and DHCP-based DNS redirection. Windows Server mitigates the rogue server problem within a domain through authorisation in Active Directory, and switches can enforce DHCP snooping, but both controls need their logs collected to be useful.

Key DHCP Log Types

DHCP visibility comes from the server, from the switch infrastructure, and from the lease database itself:

Log Type Description
Server Audit Log The primary record, written by Windows DHCP Server or ISC dhcpd. Contains one entry per protocol message with the event code, address, MAC, and hostname. Windows rotates these into seven daily files named by weekday, which is a critical retention limitation.
Lease Database The current state of all allocations rather than a chronological log. Windows stores this in a JET database, ISC dhcpd in a plain text leases file. Shows what is assigned right now, including lease start and expiry times.
DHCP Snooping Log Produced by switches enforcing trusted and untrusted ports. Records offers seen on untrusted ports, which is the definitive rogue DHCP server detection, plus binding table entries mapping MAC to address to physical port.
Server Authorisation Events Windows-specific records showing whether the DHCP service is authorised in Active Directory. An unauthorised server refusing to start is a strong signal that someone attempted to stand up a rogue server inside the domain.
Dynamic DNS Update Log Records the server registering or removing DNS records on behalf of clients. Failures here explain stale DNS entries, and unexpected updates can indicate name-based redirection attempts.
Relay Agent Log Router or switch records of DHCP requests forwarded between subnets, including Option 82 circuit and remote identifiers. Option 82 adds the physical port to the record, which is the strongest form of device attribution available.
Pro Tip: Windows DHCP audit logs rotate on a seven day cycle by weekday name, so Monday's file is overwritten the following Monday. An investigation into activity from ten days ago will find the evidence already gone unless the logs are forwarded off the server.

Pro Tip: The Windows audit log file is written with a header block repeated at the top of each file listing every event ID and its meaning. When parsing, skip the first 30 or so lines or your ingestion pipeline will create events out of the documentation.

Configuring DHCP Logging

Audit logging is on by default on Windows but with restrictive size limits, and ISC dhcpd needs an explicit syslog facility to separate its output from everything else.

Step 1: Verify and Tune Windows DHCP Audit Logging

# Check current state Get-DhcpServerAuditLog # Raise the size cap and relocate to a dedicated volume Set-DhcpServerAuditLog -Enable $true ` -Path "D:\DHCPLogs" ` -MaxMBFileSize 500 ` -DiskCheckInterval 50 ` -MinMBDiskSpace 100 Restart-Service DHCPServer
The default cap is 70 MB shared across all seven files. On a large network that fills within hours, and the server silently stops logging when MinMBDiskSpace is reached.

Step 2: Enable the Windows Operational Channel

wevtutil sl "Microsoft-Windows-Dhcp-Server/Operational" /e:true /ms:268435456 wevtutil sl "Microsoft-Windows-Dhcp-Server/FilterNotifications" /e:true # Confirm Get-WinEvent -ListLog "Microsoft-Windows-Dhcp-Server/*" | Select-Object LogName, IsEnabled, MaximumSizeInBytes
The operational channel carries service state, scope changes, and authorisation events in proper event log format, which forwards far more cleanly than the text audit file.

Step 3: Configure ISC dhcpd Logging

# /etc/dhcp/dhcpd.conf log-facility local7; # Record the vendor class and hostname for asset identification option space vendor; set vendor-string = option vendor-class-identifier; on commit { log(info, concat("COMMIT lease=", binary-to-ascii(10,8,".",leased-address), " mac=", binary-to-ascii(16,8,":",substring(hardware,1,6)), " host=", pick-first-value(option host-name, "unknown"), " vendor=", pick-first-value(vendor-string, "unknown"))); }
The on commit block produces a single enriched line per lease containing everything needed for attribution and asset inventory in one record.

Step 4: Separate DHCP from General Syslog

# /etc/rsyslog.d/40-dhcpd.conf local7.* /var/log/dhcpd.log local7.* @@siem-collector.corp.local:6514 & stop # /etc/logrotate.d/dhcpd /var/log/dhcpd.log { daily rotate 90 compress missingok postrotate systemctl reload rsyslog > /dev/null 2>&1 || true endscript }
Ninety days of retention is the practical minimum. Attribution questions routinely arrive weeks after the activity they concern.

Step 5: Enable DHCP Snooping on Switches

! Cisco IOS ip dhcp snooping ip dhcp snooping vlan 10,20,30 no ip dhcp snooping information option ! unless the relay expects Option 82 interface GigabitEthernet1/0/1 description Uplink to distribution ip dhcp snooping trust ! interface range GigabitEthernet1/0/2 - 48 ip dhcp snooping limit rate 15 ! mitigate starvation attacks ! ip dhcp snooping database flash:snooping.db
Only uplinks toward the legitimate DHCP server should be trusted. Any offer arriving on an untrusted access port is dropped and logged, which is the definitive rogue server detection.

Step 6: Add Option 82 for Port-Level Attribution

! On the relay agent ip dhcp relay information option ip dhcp relay information policy replace ! ISC dhcpd side, log the circuit ID on commit { log(info, concat("PORT circuit=", binary-to-ascii(16,8,":",option agent.circuit-id), " remote=", binary-to-ascii(16,8,":",option agent.remote-id))); }
Option 82 records the switch and physical port a request arrived on. This upgrades attribution from an address to a wall socket, which is decisive when tracking an unregistered device.
Security Note: Windows DHCP audit logging stops entirely when free disk space drops below the MinMBDiskSpace threshold, and the service keeps issuing leases while silently logging nothing. Monitor both the free space on that volume and the age of the newest log entry.

DHCP Threat Patterns

DHCP abuse is limited in variety but high in impact, because success places the attacker in the path of all victim traffic.

Rogue DHCP Server

An unauthorised server answering discover broadcasts, supplying itself as gateway and DNS. Achieves a machine in the middle position for every client that accepts its offer.
Detect Critical

Pool Starvation

Flooding requests with spoofed MAC addresses to exhaust the scope. Denies service to legitimate clients and is usually the setup phase for a rogue server attack.
Detect Critical

MAC Spoofing

Cloning an authorised device's hardware address to inherit its network access and reservations. Signature: the same MAC appearing on two switch ports, or an abrupt hostname change for one MAC.
Detect High Risk

Unauthorised Devices

Personal laptops, unmanaged IoT, and attacker hardware requesting leases. The vendor class identifier and hostname frequently identify these immediately.
Detect High Risk

Address Conflicts

Event 13 on Windows means the server found an address already in use before offering it. Sustained conflicts can indicate a rogue server issuing overlapping addresses or manual static assignment inside the pool.
Investigate Medium Risk

MAC Randomisation Noise

Modern phones and laptops randomise their hardware address per network by default. Not an attack, but it inflates apparent device counts and breaks MAC-based tracking if not accounted for.
Baseline Medium Risk
Security Note: Locally administered MAC addresses have the second least significant bit of the first octet set, which shows as a second character of 2, 6, A, or E. This distinguishes randomised or spoofed addresses from real vendor-assigned ones and is a useful first filter when triaging unknown devices.

Critical DHCP Event IDs

Windows DHCP audit event codes are stable and well documented, which makes them precise detection anchors.

Event ID Meaning Why It Matters
10 A new IP address was leased to a client The core attribution record. Every new device joining the network appears here first
11 A lease was renewed by a client Confirms continued presence. Useful for building device dwell time on the network
12 A lease was released by a client Marks the end of an address to device binding, closing the attribution window
13 An IP address was found in use on the network Address conflict. Sustained occurrences suggest a rogue server or unauthorised static addressing
14 A lease request could not be satisfied, scope exhausted Pool exhaustion, which may be organic growth or an active starvation attack
15 A lease was denied (NAK) Frequently seen when a client presents a lease from a different, possibly rogue, server
20 A BOOTP address was leased to a client Legacy protocol usage. Unexpected BOOTP can indicate network boot attacks or old embedded devices
31 DNS dynamic update failed Leaves stale DNS entries that cause misattribution in every DNS-derived investigation
51 The server was authorised to start Normal service start within the domain, and the baseline for spotting the failure case below
54 Authorisation failed, server not authorised in Active Directory Someone stood up a DHCP server inside the domain without approval. Investigate the host immediately
Pro Tip: Active Directory authorisation only restrains Windows DHCP servers that are domain members. A Linux host, a consumer router plugged into a wall port, or an attacker's laptop will happily serve DHCP with no authorisation check at all. Switch-level snooping is the control that actually stops those.

DHCP Log Analysis Queries

Use these to resolve addresses to devices, find rogue servers, and spot unmanaged hardware on the network.

Resolve an Address to a Device
SIEM> source="dhcp" ip_address="10.30.2.61" earliest=-7d | table _time, event_id, description, mac_address, host_name, vendor_class | sort _time
The fundamental DHCP query. Always bound it by time, because the same address may have served a dozen devices in a week.
Rogue DHCP Server
bash> grep -iE "DHCP_SNOOPING_DENY|DHCP_SNOOPING_UNTRUSTED_PORT|dhcp server.*not authorized" /var/log/network/switches.log | awk '{print $1, $2, $NF}' | sort | uniq -c
DHCP snooping denials name the exact switch port the rogue offer came from, which is enough to physically locate the device.
Pool Starvation Attack
SIEM> source="dhcp" event_id=10 | bucket _time span=5m | stats dc(mac_address) as new_devices by _time, scope | where new_devices > 50
Fifty new hardware addresses in five minutes on one scope is not organic. Compare against event 14 to confirm the pool was exhausted.
MAC Address Conflict
SIEM> source="dhcp" event_id IN (10,11) | stats dc(host_name) as names, values(host_name), dc(ip_address) as addrs by mac_address | where names > 1
One hardware address presenting two different hostnames is either MAC spoofing or a rebuilt machine. Both warrant a look.
Unmanaged Devices
SIEM> source="dhcp" event_id=10 | lookup asset_inventory mac_address OUTPUT owner, asset_tag | where isnull(asset_tag) | stats count, values(host_name), values(vendor_class) by mac_address
Joining leases against the asset inventory turns DHCP into continuous rogue device detection.
Randomised or Spoofed MACs
bash> grep -oP '^10,.*?,\K[0-9A-F]{12}' /var/log/dhcp/DhcpSrvLog-Mon.log | grep -iE '^.[26AE]' | sort -u | wc -l
Filters for locally administered addresses, the marker of randomised or manually set MACs. A rising count usually reflects modern device defaults rather than attack.
Address Conflicts and Denials
SIEM> source="dhcp" event_id IN (13,14,15) | timechart span=1h count by event_id
A sudden rise in conflicts and NAKs is the fingerprint of a second DHCP server operating on the segment.
Snooping Binding Table
IOS> show ip dhcp snooping binding | include 10.30.2.61
Returns the MAC, address, lease time, VLAN, and physical interface in one line. The most direct route from an address to a wall port.
Current Windows Leases
PS> Get-DhcpServerv4Scope | Get-DhcpServerv4Lease | Where-Object { $_.AddressState -ne 'Active' } | Select-Object IPAddress, ClientId, HostName, AddressState, LeaseExpiryTime
Non-active lease states such as ActiveReservation or Declined often mark conflicts and devices behaving unexpectedly.
Logging Continuity
SIEM> source="dhcp" | timechart span=1h count | where count < 10
Windows silently stops audit logging when disk space runs low while continuing to issue leases. Volume monitoring is the only way to notice.

Best Practices for DHCP Logging

Apply these practices so that every other log on the network remains attributable:

01

Forward Logs Off the Server Immediately

Windows overwrites each audit file on a seven day weekday cycle. Any investigation reaching back further than a week finds nothing unless the logs were shipped elsewhere.

02

Retain for at Least Ninety Days

Attribution requests arrive long after the event. Retention shorter than the rest of your log estate makes every other network log unattributable for the same period.

03

Enable DHCP Snooping Everywhere

Active Directory authorisation only restrains domain-joined Windows servers. Snooping is what stops a Linux host or consumer router from serving addresses on an access port.

04

Capture Vendor Class and Hostname

These fields turn the lease log into a passive asset inventory, identifying device type and operating system without any agent or scan.

05

Add Option 82 Where Possible

Circuit and remote identifiers record the switch and port a request arrived on, upgrading attribution from an address to a physical location.

06

Join Leases to the Asset Inventory

Enriching each lease with the registered owner at ingest means unknown devices surface automatically instead of requiring someone to go looking.

07

Monitor Free Disk Space on the Server

Windows DHCP stops logging when free space falls below the configured minimum, yet continues issuing leases normally. Nothing alerts you that visibility has been lost.

08

Account for MAC Randomisation

Phones and modern laptops randomise hardware addresses by default. Track devices by certificate or 802.1X identity where accuracy matters, and expect inflated device counts otherwise.

Common DHCP Log Examples

Normal allocation, attribution, and the two attacks DHCP logs are best at revealing.

Windows Audit Log: Normal Lease Assignment

ID,Date,Time,Description,IP Address,Host Name,MAC Address,User Name,TransactionID,QResult,Probationtime,CorrelationID,Dhcid,VendorClass(Hex),VendorClass(ASCII),UserClass(Hex),UserClass(ASCII),RelayAgentInformation,DnsRegError 10,07/14/25,09:41:22,Assign,10.30.2.61,WKS-FIN-014,00155D8A4C12,,1874203911,0,6,,,4D53465420352E30,MSFT 5.0,,,0108000600040101,0
Event 10 binds address 10.30.2.61 to MAC 00155D8A4C12 and hostname WKS-FIN-014. The MSFT 5.0 vendor class confirms Windows, and Option 82 records the originating port.

ISC dhcpd: The Full Four-Message Exchange

Jul 14 09:41:21 dhcp01 dhcpd[1284]: DHCPDISCOVER from 00:15:5d:8a:4c:12 via eth0 Jul 14 09:41:21 dhcp01 dhcpd[1284]: DHCPOFFER on 10.30.2.61 to 00:15:5d:8a:4c:12 (WKS-FIN-014) via eth0 Jul 14 09:41:22 dhcp01 dhcpd[1284]: DHCPREQUEST for 10.30.2.61 (10.10.0.5) from 00:15:5d:8a:4c:12 (WKS-FIN-014) via eth0 Jul 14 09:41:22 dhcp01 dhcpd[1284]: DHCPACK on 10.30.2.61 to 00:15:5d:8a:4c:12 (WKS-FIN-014) via eth0
The complete handshake. The DHCPACK is the authoritative record: the address is now bound to that hardware address until the lease expires or is released.

Rogue DHCP Server Detected by Snooping

Jul 14 09:52:10 sw-access-03 %DHCP_SNOOPING-5-DHCP_SNOOPING_UNTRUSTED_PORT: DHCP_SNOOPING drop message on untrusted port, message type: DHCPOFFER, MAC sa: 00:0c:29:8f:2a:41 Jul 14 09:52:10 sw-access-03 %DHCP_SNOOPING-5-DHCP_SNOOPING_UNTRUSTED_PORT: interface GigabitEthernet1/0/24, VLAN 20 Jul 14 09:52:11 sw-access-03 %DHCP_SNOOPING-5-DHCP_SNOOPING_MATCH_MAC_FAIL: DHCP_SNOOPING drop message because the chaddr doesn't match source mac
An offer arriving on an access port is definitionally a rogue server. The 00:0c:29 prefix belongs to VMware, so this is a virtual machine, likely on a laptop plugged into port Gi1/0/24.

Windows: Unauthorised Server Blocked

ID,Date,Time,Description,IP Address,Host Name,MAC Address 54,07/14/25,09:52:14,Authorization failed,10.30.7.88,ROGUE-SRV,000C298F2A41 50,07/14/25,09:52:14,Unreachable domain,,, 56,07/14/25,09:52:44,Authorization failure stopped servicing,10.30.7.88,ROGUE-SRV,
Event 54 followed by 56 shows a domain-joined Windows server attempting to start DHCP without authorisation and shutting itself down. Note that this control does nothing against non-Windows rogue servers.

Pool Starvation Attack

Jul 14 10:02:44 dhcp01 dhcpd[1284]: DHCPDISCOVER from 3a:1f:7c:04:9e:22 via eth0 Jul 14 10:02:44 dhcp01 dhcpd[1284]: DHCPDISCOVER from 6e:88:2b:f1:04:c7 via eth0 Jul 14 10:02:44 dhcp01 dhcpd[1284]: DHCPDISCOVER from a2:41:9d:3e:77:10 via eth0 Jul 14 10:02:45 dhcp01 dhcpd[1284]: DHCPDISCOVER from ee:03:b4:2a:81:5f via eth0 Jul 14 10:03:19 dhcp01 dhcpd[1284]: no free leases on subnet 10.30.2.0/24
Randomised hardware addresses arriving in the same second, all locally administered (second character 2, 6, A, or E). The pool exhausts in 35 seconds, clearing the way for a rogue server.

MAC Spoofing: One Address, Two Identities

10,07/14/25,08:14:02,Assign,10.30.2.61,WKS-FIN-014,00155D8A4C12,,1874203911,0 12,07/14/25,09:38:41,Release,10.30.2.61,WKS-FIN-014,00155D8A4C12,,1874203911,0 10,07/14/25,09:39:02,Assign,10.30.2.61,kali,00155D8A4C12,,1874204882,0
The same hardware address releases a lease as WKS-FIN-014 and reclaims it 21 seconds later as kali. The MAC was cloned to inherit the legitimate workstation's network access.

Unmanaged Device Joining the Network

Jul 14 10:18:12 dhcp01 dhcpd[1284]: DHCPACK on 10.30.2.184 to 8a:3f:2c:91:0e:44 (raspberrypi) via eth0 vendor-class-identifier = "dhcpcd-9.4.1:Linux-6.1.21-v8+:aarch64:BCM2835" Jul 14 10:18:12 dhcp01 dhcpd[1284]: COMMIT lease=10.30.2.184 mac=8a:3f:2c:91:0e:44 host=raspberrypi vendor=dhcpcd-9.4.1:Linux-6.1.21-v8+
The vendor class identifies a Raspberry Pi running Linux on ARM. No asset record exists for this device, and single-board computers are a common drop-box for persistent network access.
