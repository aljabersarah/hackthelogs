IDS and IPS Logs

IDS and IPS Log Overview

An Intrusion Detection System observes traffic and reports what it recognises. An Intrusion Prevention System sits inline and can drop the traffic instead. The distinction is a deployment decision rather than a product one, and it matters enormously when reading the logs: an IDS alert means something was seen, while an IPS alert with a drop action means something was stopped. Confusing the two leads analysts to chase attacks that never landed, or worse, to assume an attack was blocked when the sensor was only watching.

Detection engines fall into two broad families. Signature based engines match traffic against rules describing known attack patterns, a model shared by open source engines such as Suricata and Snort and by commercial platforms from Palo Alto Networks, Cisco, Fortinet, Check Point, and Trellix. Anomaly and behaviour based engines instead build a baseline of normal traffic and alert on deviation from it. Whatever the vendor, a detection event carries the same core elements: a rule or threat identifier, a classification, a severity, the five-tuple of the connection, the action taken, and often the payload that triggered it. The field names differ between platforms, the meaning does not, and the mapping table further down this page lines the common ones up.

Most sensors emit far more than alerts. Protocol transaction records document every observed HTTP request, DNS query, TLS handshake, and file transfer regardless of whether a rule matched. Suricata calls this EVE JSON, Zeek writes one log per protocol, and commercial platforms expose the same data as traffic, URL, application, or connection events. That protocol metadata is frequently more valuable than the alerts themselves, because it provides context for events no signature covers.

The persistent operational problem with these systems is signal to noise. A default ruleset on a busy link will generate tens of thousands of alerts a day, the overwhelming majority of them informational or irrelevant to the environment. Tuning is not optional maintenance, it is the difference between a functioning detection capability and an ignored console. Equally important is placement: a sensor that cannot see traffic cannot alert on it, and in networks where most traffic is encrypted, an IDS without TLS inspection or JA3 fingerprinting is blind to the payloads it was bought to inspect.

Key IDS and IPS Log Types

Modern sensors produce far more than alerts. Understanding each output stream determines how much value you extract from the deployment:

Log Type Description
Alert Log The core output. One record per rule match, containing the signature identifier, revision, message, classification, priority, and the connection five-tuple. In IPS mode it also carries the action taken, which is what tells you whether the traffic was blocked or merely observed.
Unified Event Stream A single structured stream carrying alerts plus protocol transaction records under one schema. Suricata calls this EVE JSON, commercial platforms deliver the equivalent over syslog in CEF, LEEF, or JSON. Always the preferred output for SIEM integration because every event type shares a common set of fields.
Protocol Transaction Logs Records of every observed HTTP request, TLS handshake, DNS query, and SMB session, regardless of whether any rule matched. Invaluable for hunting and for reconstructing an intrusion whose technique had no signature at the time.
File Transaction and Extraction Log Metadata for files observed crossing the sensor, including name, size, MIME type, and hash. With file store enabled the file itself is written to disk, allowing retrospective analysis against threat intelligence.
Flow and NetFlow Records Connection summaries with byte and packet counts in each direction plus duration. The basis for detecting beaconing, long-lived sessions, and asymmetric transfers that indicate exfiltration.
Packet Capture (PCAP) The raw packets that triggered an alert, either the single triggering packet or a full session capture. The definitive evidence for confirming a detection but expensive to retain at scale.
Engine and Statistics Log Sensor health output including packet drop counters, rule load errors, and memory usage. Critical and routinely ignored: a sensor dropping 40 percent of packets is missing 40 percent of attacks silently.
Pro Tip: Collect the statistics log and alert on the drop counter, whatever your platform calls it: capture.kernel_drops on Suricata, dataplane packet descriptors on Palo Alto, snort instance drops on Firepower, IPS engine bypass on FortiGate. A sensor under-provisioned for its link produces fewer alerts, which looks exactly like a quiet network. Packet loss is the most common cause of an IDS missing an intrusion it had a valid signature for.

Log File Locations

Software sensors write to the local filesystem, while appliances and managed services expose logs through a console, an API, or syslog forwarding rather than a path you can read directly. Know which model you are dealing with before planning collection.

Platform Log Location or Access Method
Suricata Unified JSON, text alerts, engine, statistics /var/log/suricata/eve.json, fast.log, suricata.log, stats.log. Config at /etc/suricata/suricata.yaml, rules under /var/lib/suricata/rules/
Snort Alert log and configuration /var/log/snort/alert or alert_fast.txt. Config at /etc/snort/snort.conf (Snort 2) or snort.lua (Snort 3)
Zeek Per protocol transaction logs /opt/zeek/logs/current/ with notice.log, conn.log, http.log, dns.log, ssl.log, files.log
Palo Alto Networks Threat, traffic, and WildFire logs Monitor tab in the web interface, show log threat in the CLI, or syslog forwarding via a Log Forwarding Profile. Panorama for aggregated retention
Cisco Secure Firewall (Firepower, FTD) Intrusion events FMC under Analysis then Intrusions then Events. Export by eStreamer or syslog. Local troubleshooting via /var/log/messages and /ngfw/var/log/
Fortinet FortiGate IPS attack log Log and Report then Intrusion Prevention, execute log filter category ips in the CLI, or forwarding to FortiAnalyzer and syslog
Check Point Threat Prevention logs SmartConsole under Logs and Monitor. On the management server $FWDIR/log/*.log, readable with fw log or exported by LEA and syslog
Cloud and managed services Managed detection findings AWS GuardDuty and Network Firewall to CloudWatch Logs, S3, or EventBridge. Azure Firewall Premium IDPS to Azure Monitor. Retrieved by API rather than file
Extracted files and packet capture Evidence artefacts /var/log/suricata/filestore/ on Suricata, packet capture attached to the event record on commercial platforms and downloaded from the console
Pro Tip: For any software sensor, give the log directory its own volume. Full protocol logging on a busy link produces tens of gigabytes per day, and filling the root filesystem takes the sensor down along with everything else on the host. For appliances the same risk appears as silent log rollover, where the console shows only a few hours of history and older events are gone before anyone investigates.

Configuring IDS and IPS Logging

Every platform exposes the same six decisions through different interfaces. The principle in each step below applies regardless of engine, and the snippet shows one concrete implementation alongside the equivalent on other platforms.

Step 1: Emit Structured Output Rather Than Text

# Suricata: structured JSON covering alerts and protocol records outputs: - eve-log: enabled: yes filename: eve.json community-id: true # portable flow hash for correlation types: - alert: payload: yes metadata: yes - http: extended: yes - dns: version: 2 - tls: extended: yes - files: force-hash: [md5, sha256] - flow # Palo Alto: Device > Log Settings, or a Log Forwarding Profile per rule # forward Threat and Traffic logs to syslog, format set to JSON or CEF # Cisco FTD: Policies > Intrusion > Logging, or stream events by eStreamer # FortiGate: config log syslogd setting, then set format cef # Check Point: SmartConsole log exporter, target format syslog or CEF
Text alert formats drop most of the context the engine already has. Always choose the structured option, and where the platform supports a portable flow identifier such as community ID, enable it so sensor events join cleanly to firewall and proxy records.

Step 2: Define What Counts as Internal

# Suricata and Snort: named address and port variables vars: address-groups: HOME_NET: "[10.0.0.0/8,192.168.0.0/16,172.16.0.0/12]" EXTERNAL_NET: "!$HOME_NET" HTTP_SERVERS: "[10.20.5.0/24]" DNS_SERVERS: "[10.10.0.10,10.10.0.11]" port-groups: HTTP_PORTS: "[80,81,8000,8080,8443]" # Palo Alto, FortiGate, Check Point: the same concept is expressed as # security zones and address objects applied to each policy rule # Cisco FTD: Objects > Variable Set, per intrusion policy
Rules are written in terms of internal versus external. Whether your platform calls it HOME_NET, a trusted zone, or a variable set, defining it incorrectly is the single most common serious misconfiguration and silently breaks directionality across the whole ruleset.

Step 3: Keep the Ruleset Current

# Suricata: manage sources and reload without dropping traffic suricata-update list-sources suricata-update enable-source et/open suricata-update suricatasc -c reload-rules # Snort: PulledPork or the Talos subscription feed # Palo Alto: Device > Dynamic Updates, schedule Applications and Threats # Cisco FTD: System > Updates > Rule Updates, then redeploy the policy # FortiGate: FortiGuard IPS definitions, verify with # diagnose autoupdate versions | grep -A2 IPS
Apply updates to a running sensor without a restart wherever the platform allows it, because restarting an inline sensor means a network outage. On commercial platforms a downloaded update does nothing until the policy is redeployed, which is a routinely missed step.

Step 4: Tune Noisy Signatures Rather Than Deleting Them

# Suricata: rate limit rather than remove # /etc/suricata/threshold.config threshold gen_id 1, sig_id 2001219, type limit, track by_src, count 1, seconds 60 suppress gen_id 1, sig_id 2001219, track by_src, ip 10.50.9.14 # /etc/suricata/disable.conf (last resort) 2013028 # expected User-Agent from internal monitoring # Palo Alto: Objects > Security Profiles > Anti-Spyware or Vulnerability, # add a Threat Exception scoped to a specific source or destination # Cisco FTD: set the rule state to Disabled, or add an event threshold # and a suppression entry scoped by source # FortiGate: IPS sensor filters with an exempt-ip entry
Prefer thresholding and scoped exceptions over disabling. Thresholding keeps the detection alive at reduced volume, whereas disabling removes coverage permanently and silently. Record every tuning decision with the reason so a future analyst knows why a signature is quiet.

Step 5: Move from Detection to Prevention Deliberately

# Suricata: place the sensor inline, then convert selected rules iptables -I FORWARD -j NFQUEUE --queue-num 0 suricata -c /etc/suricata/suricata.yaml -q 0 # /etc/suricata/modify.conf 2010935 "alert" "drop" # Palo Alto: profile action set to reset-both, drop, or block-ip # Cisco FTD: intrusion policy in Drop when Inline mode, rule state # set to Drop and Generate Events # FortiGate: IPS sensor action set to block or reset # Then audit what is actually being enforced jq -r 'select(.event_type=="alert") | .alert.action' /var/log/suricata/eve.json | sort | uniq -c
Inline deployment does not by itself mean prevention. Most rules ship in an alerting state on every platform, so traffic is only stopped once a rule is explicitly set to drop or block. Teams regularly discover during an incident that a sensor they believed was preventing had been watching all along.

Step 6: Monitor Sensor Health

# Suricata: periodic statistics with drop counters outputs: - stats: enabled: yes interval: 30 suricatasc -c "dump-counters" | jq '.message.capture' # Palo Alto: show running resource-monitor ingress-backlogs # Cisco FTD: show snort statistics, plus FMC Health Monitor # FortiGate: diagnose ips status, watch for fail-open events # Check Point: fw ctl multik stat and cpview
Any sustained drop rate above roughly one percent means the sensor is losing visibility. Treat it as an availability incident rather than a performance tuning task, because the resulting gap is invisible in the alert stream.
Security Note: Enabling payload: yes writes the triggering packet contents into your logs. For rules that match on authentication traffic or personal data this means credentials and regulated data land in the SIEM. Scope payload logging to the rule categories that genuinely need it.

Anatomy of a Detection Rule

Reading the detection logic is what lets an analyst decide whether an alert is a true positive. Signature based engines are built from the same components whether the rule is written in open syntax you can edit, shipped as a vendor threat signature, or exposed read only in a management console.

Action

What the engine did: alert, drop, reject, or pass in open syntax, and allow, block, reset, or sinkhole on commercial platforms. In passive deployment every action behaves as alert. Only an inline sensor makes blocking meaningful, which is the first thing to check when triaging.
Read First Critical

Header

Protocol, source, source port, direction, destination, destination port. Expressed in terms of internal and external address groups or security zones, so direction tells you whether this is inbound attack or outbound compromise.
Read First Critical

Signature ID and Revision

The stable identifier for the detection and its revision number. Called sid and rev in open rule syntax, Threat ID on Palo Alto, and GID:SID on Snort based engines including Firepower. This is the key for tuning, suppression, and tracking a detection over time, so always record it in your case notes.
Read First High Risk

Classification and Severity

Categorises the alert and ranks it. Open rule syntax uses classtype with priority 1 (highest) to 4, while commercial platforms use named tiers such as critical, high, medium, low, and informational. Malware and privilege gain categories warrant immediate attention, policy and informational categories usually do not.
Triage High Risk

Match Conditions

The actual detection logic: byte sequences and regular expressions applied to the payload or to protocol fields such as the HTTP URI. Open engines expose this as content and pcre options. Commercial platforms usually hide it, in which case the vendor threat encyclopedia entry is the substitute.
Verify Medium Risk

metadata and reference

Links the signature to CVE identifiers, MITRE ATT&CK techniques, malware families, and creation dates. The fastest route from an alert to understanding what it actually detects.
Enrich Medium Risk
Security Note: Direction matters more than severity. A high severity alert for an exploit aimed at a service you do not run is noise, while a low severity outbound alert from a workstation to an unknown host can be the first sign of an active compromise.

Alert Classifications and Priority

Classification drives triage on every platform. The names below are the open engine classtypes, which are the most widely documented set. Commercial products use their own vocabulary for the same tiers: Palo Alto splits detections into vulnerability, spyware, and virus subtypes, Cisco uses impact flags from 0 to 4, and Fortinet groups by attack category. Map yours onto this hierarchy once and the triage logic transfers unchanged.

Classification Priority Triage Guidance
trojan-activity 1 Known malware traffic, usually outbound command and control. Treat as active compromise and investigate the source host immediately
attempted-admin 1 Attempted administrator privilege gain. If the target runs the affected service, escalate at once
successful-admin 1 Successful privilege gain observed. Among the highest confidence alerts any sensor produces
shellcode-detect 1 Executable code detected in a payload. High value but prone to false positives on binary file transfers
web-application-attack 1 Injection, traversal, or deserialisation against a web application. Correlate with the WAF and web server logs to confirm the response code
attempted-recon 2 Scanning and enumeration. Low individual value, high value in aggregate as an early indicator of targeting
policy-violation 2 Acceptable use rather than security, such as cleartext credentials or unapproved tooling. Route to IT rather than the SOC
protocol-command-decode 3 Unusual but not inherently malicious protocol usage. Almost always noise on its own
misc-activity 3 Catch-all informational category. Suppress aggressively unless a specific signature has proven value in your environment
not-suspicious 3 Explicitly benign traffic recorded for context. Should never generate a ticket
Pro Tip: Alert on the combination rather than the classification alone. A single attempted-recon event is noise, but attempted-recon followed by web-application-attack followed by trojan-activity from the same source within an hour is an intrusion narrated in three lines.

IDS and IPS Log Analysis Queries

These queries are written against the normalised field names from the mapping table above, so substitute your platform's equivalents. Where a query can only run on the sensor itself the prompt shows bash and the example uses open engine tooling.

Top Firing Signatures
SIEM> event_type="alert" | stats count, dc(src_ip) as sources, dc(dest_ip) as targets by signature_id, signature | sort - count | head 25
The starting point for every tuning exercise on any platform. The top ten signatures usually account for most of the volume and almost none of the value. A signature with high count but only one or two distinct sources is a tuning candidate rather than a campaign.
Highest Severity Alerts Only
SIEM> event_type="alert" severity IN ("1","critical","high") | table _time, src_ip, dest_ip, category, signature, action | sort - _time
Strips the stream down to what the ruleset authors considered critical, the correct default view for a triage queue. Match the severity values to your platform, remembering that open engines count down from 1 while most commercial products count up.
Outbound Malware and C2 by Internal Host
SIEM> event_type="alert" category IN ("*Trojan*","*Malware*","*Command and Control*","spyware") src_ip IN (10.0.0.0/8,192.168.0.0/16) | stats count, values(signature), dc(dest_ip) by src_ip | sort - count
Filtering to internal sources turns a noisy category into a list of probably compromised hosts. Outbound direction is what makes this high confidence, and the wildcards absorb the naming differences between vendors.
Blocked Versus Allowed
SIEM> event_type="alert" | stats count by action, signature | eventstats sum(count) as total by signature | eval enforced=round(count/total*100,1) | where action IN ("blocked","drop","reset","deny")
Confirms which rules are actually preventing traffic rather than observing it. Run this on any inline deployment, because most rules ship in alerting state on every platform and are only enforced once explicitly changed.
Sensor Packet Loss
bash> jq -r 'select(.event_type=="stats") | [.timestamp, .stats.capture.kernel_packets, .stats.capture.kernel_drops] | @tsv' eve.json | tail -10 # PAN: show running resource-monitor | FTD: show snort statistics | FortiGate: diagnose ips status
Drops divided by packets is your blind spot percentage. Anything sustained above one percent means the sensor is missing attacks it has signatures for. Every platform exposes this counter somewhere, and on all of them it is the single most under-monitored metric.
Rare TLS Fingerprints and Destinations
SIEM> event_type="tls" OR event_type="ssl" | stats count, dc(src_ip) as hosts, values(sni) by ja3_hash, dest_ip | where hosts <= 2 AND count > 50 | sort - count
Client TLS fingerprints identify malware families inside encrypted traffic without decryption. Where your platform does not expose JA3, substitute the certificate subject and SNI, which are available on every product that inspects TLS metadata.
Executable Downloads
SIEM> event_type IN ("fileinfo","file","wildfire") file_type IN ("*executable*","PE32","ELF","*msdownload*") | table _time, src_ip, dest_ip, filename, sha256, verdict | sort - _time
Every executable observed crossing the sensor with its hash, ready to check against threat intelligence. Platforms with a sandbox attach a verdict to the same record, which turns this from a hunting query into a detection.
Full Session Context for an Alert
SIEM> session_id="1874203911402318" OR community_id="1:LQU9qZlK+B5F3KDmev6m5PMibrg=" | table _time, event_type, signature, url, sni, filename, action | sort _time
Pivoting on the session identifier reconstructs every record for one connection: the alert, the HTTP request, the TLS handshake, and the file transfer. Community ID is the better key when the connection crosses several products, because it is computed identically by each of them.
Attack Chain by Source
SIEM> event_type="alert" | stats dc(category) as stages, values(category), min(_time) as first, max(_time) as last by src_ip | where stages >= 3 | sort - stages
Sources triggering three or more distinct alert categories are progressing through an attack rather than generating incidental noise.
Verify the Ruleset Actually Loaded
bash> suricatasc -c "ruleset-stats" # PAN: show system info | match threat-version | FTD: show snort counters | FortiGate: diagnose autoupdate versions
Rules that fail to load are reported once at startup and never mentioned again. Check the loaded count and the installed content version after every update, and on managed platforms confirm the policy was redeployed, since a downloaded update that was never pushed changes nothing.

Best Practices for IDS and IPS Logging

Apply these practices to keep a sensor deployment useful rather than ignored:

01

Define Your Internal Boundary Correctly

Nearly every rule is written in terms of internal versus external. Whether the platform calls it HOME_NET, a trusted zone, or a variable set, a wrong or default value silently breaks directionality across the entire ruleset. This is the most common serious misconfiguration in the field.

02

Monitor Packet Drop as an Outage

A saturated sensor produces fewer alerts, which resembles a quiet network. Alert on whichever drop counter your platform exposes and treat sustained loss with the same urgency as a sensor being offline.

03

Threshold Before You Disable

Thresholding keeps a detection alive at lower volume while disabling removes coverage permanently. Record every tuning decision so future analysts know why a signature is quiet.

04

Keep the Protocol Logs, Not Just Alerts

HTTP, DNS, TLS, and file records let you investigate techniques no signature covers. Most successful hunts use this metadata rather than the alerts.

05

Normalise Fields at Ingestion

Map every sensor onto one schema for rule identifier, severity, action, and direction, and enable a portable flow identifier such as community ID where the platform supports it. Detection content written once then works across every sensor you own, including the one you replace this vendor with.

06

Verify That Blocking Is Actually Blocking

Inline deployment does not mean prevention. Rules ship with the alert action, so audit the ratio of drop to alert actions regularly and confirm it matches your intent.

07

Place Sensors Where They Can See

A sensor on the perimeter misses all lateral movement. Internal segments, the data centre core, and the VPN concentrator are where post-compromise activity is visible.

08

Plan for Encryption

Most traffic is TLS, so payload signatures see nothing. Compensate with JA3 fingerprinting, SNI logging, certificate metadata, and flow analysis rather than assuming content inspection still works.

Common IDS and IPS Log Examples

Sensor output from reconnaissance through to command and control. The same detection is shown first in the three formats you will meet in practice, plain text alert, structured JSON, and syslog CEF from a commercial appliance, so you can recognise it whichever product produced it.

Text Alert Format: Exploit Attempt Against SMB

07/14/2025-09:41:22.481203 [**] [1:2024897:3] ET EXPLOIT SMB Remote Code Execution Attempt (EternalBlue) [**] [Classification: Attempted Administrator Privilege Gain] [Priority: 1] {TCP} 203.0.113.44:52144 -> 10.20.5.40:445
The compact format: sid 2024897 revision 3, priority 1, external source to an internal host on SMB. Priority 1 plus attempted-admin means this goes to the top of the queue.

Structured JSON: The Same Alert with Full Context

{"timestamp":"2025-07-14T09:41:22.481203+0000","flow_id":1874203911402318,"event_type":"alert", "src_ip":"203.0.113.44","src_port":52144,"dest_ip":"10.20.5.40","dest_port":445,"proto":"TCP", "community_id":"1:LQU9qZlK+B5F3KDmev6m5PMibrg=", "alert":{"action":"blocked","gid":1,"signature_id":2024897,"rev":3, "signature":"ET EXPLOIT SMB Remote Code Execution Attempt (EternalBlue)", "category":"Attempted Administrator Privilege Gain","severity":1, "metadata":{"attack_target":["Server"],"mitre_technique_id":["T1210"],"cve":["CVE-2017-0144"]}}, "flow":{"pkts_toserver":14,"pkts_toclient":9,"bytes_toserver":4218,"bytes_toclient":1902}}
The action field confirms the traffic was blocked, and the metadata maps directly to CVE-2017-0144 and MITRE technique T1210. This is why the structured format is always preferred over the text one.

Syslog CEF: The Same Detection From a Commercial Appliance

CEF:0|Palo Alto Networks|PAN-OS|10.2|vulnerability|Microsoft SMB Remote Code Execution|9| rt=Jul 14 2025 09:41:22 src=203.0.113.44 spt=52144 dst=10.20.5.40 dpt=445 proto=tcp act=reset-both cs1Label=Rule cs1=Inbound-DC-Access cn1Label=ThreatID cn1=51234 cat=vulnerability cs2Label=Severity cs2=critical cs3Label=Direction cs3=client-to-server externalId=7714029183 cs4Label=CVE cs4=CVE-2017-0144
The same event, different vocabulary. threatid replaces signature_id, act replaces action, and severity is a word rather than a number. Everything an analyst needs is present, which is why normalising these three fields at ingestion lets one detection rule cover every sensor in the estate.

Reconnaissance: Port Scan Detected

07/14/2025-09:38:02.117441 [**] [1:2010935:3] ET SCAN Suspicious inbound to MSSQL port 1433 [**] [Classification: Potentially Bad Traffic] [Priority: 2] {TCP} 198.51.100.203:44120 -> 10.40.1.15:1433 07/14/2025-09:38:02.119882 [**] [1:2010936:3] ET SCAN Suspicious inbound to mySQL port 3306 [**] [Classification: Potentially Bad Traffic] [Priority: 2] {TCP} 198.51.100.203:44121 -> 10.40.1.15:3306 07/14/2025-09:38:02.124019 [**] [1:2002910:5] ET SCAN Potential VNC Scan 5900-5920 [**] [Classification: Attempted Information Leak] [Priority: 2] {TCP} 198.51.100.203:44122 -> 10.40.1.15:5900
Three database and remote access ports probed within seven milliseconds from one source. Individually priority 2 noise, together an unmistakable service sweep.

Web Application Attack: Path Traversal

{"timestamp":"2025-07-14T09:47:33.221004+0000","event_type":"alert", "src_ip":"203.0.113.44","dest_ip":"10.20.5.40","dest_port":443, "alert":{"action":"allowed","signature_id":2006445,"signature":"ET WEB_SERVER Possible Directory Traversal Attempt", "category":"Web Application Attack","severity":1}, "http":{"hostname":"portal.example.com","url":"/download?file=../../../../etc/passwd", "http_user_agent":"python-requests/2.31.0","http_method":"GET","status":200,"length":2841}, "payload_printable":"GET /download?file=../../../../etc/passwd HTTP/1.1"}
Status 200 with 2841 bytes returned means the traversal succeeded. The action field says allowed, so the sensor watched this happen without stopping it.

Command and Control: Outbound Beacon

{"timestamp":"2025-07-14T10:02:44.881229+0000","event_type":"alert", "src_ip":"10.30.2.61","src_port":52190,"dest_ip":"203.0.113.44","dest_port":443, "alert":{"action":"allowed","signature_id":2033102, "signature":"ET MALWARE Cobalt Strike Beacon Observed","category":"A Network Trojan was detected","severity":1, "metadata":{"mitre_technique_id":["T1071.001"],"malware_family":["CobaltStrike"]}}, "tls":{"sni":"cdn-assets.badinfra.top","ja3":{"hash":"a0e9f5d64349fb13191bc781f81f42e1"}, "subject":"CN=cdn-assets.badinfra.top","issuerdn":"CN=R3, O=Let's Encrypt"}}
The direction is what matters: an internal workstation initiating this. The JA3 hash identified Cobalt Strike inside TLS without any decryption, and the certificate is a free one issued days ago.

Sensor Health: Packet Loss

{"timestamp":"2025-07-14T10:05:00.000000+0000","event_type":"stats", "stats":{"uptime":86402, "capture":{"kernel_packets":1842119004,"kernel_drops":412887221}, "decoder":{"pkts":1429231783,"bytes":1102847119228}, "detect":{"alert":18442}}}
