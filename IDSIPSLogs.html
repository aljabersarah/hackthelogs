IDS and IPS Logs

IDS and IPS Log Overview

An Intrusion Detection System observes traffic and reports what it recognises. An Intrusion Prevention System sits inline and can drop the traffic instead. The distinction is a deployment decision rather than a product one, and it matters enormously when reading the logs: an IDS alert means something was seen, while an IPS alert with a drop action means something was stopped. Confusing the two leads analysts to chase attacks that never landed, or worse, to assume an attack was blocked when the sensor was only watching.

The dominant open source engines are Suricata and Snort, and commercial platforms from Cisco, Palo Alto, and Trellix are built on the same signature model. A rule describes traffic to match on, and when a packet or stream matches, the engine emits an alert carrying the rule identifier, a classification, a priority, the five-tuple of the connection, and often the packet payload that triggered it. Suricata additionally produces EVE JSON, a unified structured output that carries not just alerts but protocol transaction records for HTTP, DNS, TLS, SMB, and file transfers. That protocol metadata is frequently more valuable than the alerts themselves, because it provides context for events no signature covers.

The persistent operational problem with these systems is signal to noise. A default ruleset on a busy link will generate tens of thousands of alerts a day, the overwhelming majority of them informational or irrelevant to the environment. Tuning is not optional maintenance, it is the difference between a functioning detection capability and an ignored console. Equally important is placement: a sensor that cannot see traffic cannot alert on it, and in networks where most traffic is encrypted, an IDS without TLS inspection or JA3 fingerprinting is blind to the payloads it was bought to inspect.

Key IDS and IPS Log Types

Modern sensors produce far more than alerts. Understanding each output stream determines how much value you extract from the deployment:

Log Type Description
Alert Log The core output. One record per rule match, containing the signature identifier, revision, message, classification, priority, and the connection five-tuple. In IPS mode it also carries the action taken, which is what tells you whether the traffic was blocked or merely observed.
EVE JSON Suricata's unified structured output. A single newline-delimited JSON stream carrying alerts plus protocol transaction records for HTTP, DNS, TLS, SSH, SMB, and more. The recommended output for any SIEM integration because every event type shares a common schema.
Protocol Transaction Logs Records of every observed HTTP request, TLS handshake, DNS query, and SMB session, regardless of whether any rule matched. Invaluable for hunting and for reconstructing an intrusion whose technique had no signature at the time.
File Transaction and Extraction Log Metadata for files observed crossing the sensor, including name, size, MIME type, and hash. With file store enabled the file itself is written to disk, allowing retrospective analysis against threat intelligence.
Flow and NetFlow Records Connection summaries with byte and packet counts in each direction plus duration. The basis for detecting beaconing, long-lived sessions, and asymmetric transfers that indicate exfiltration.
Packet Capture (PCAP) The raw packets that triggered an alert, either the single triggering packet or a full session capture. The definitive evidence for confirming a detection but expensive to retain at scale.
Engine and Statistics Log Sensor health output including packet drop counters, rule load errors, and memory usage. Critical and routinely ignored: a sensor dropping 40 percent of packets is missing 40 percent of attacks silently.
Pro Tip: Collect the statistics log and alert on capture.kernel_drops. A sensor under-provisioned for its link produces fewer alerts, which looks exactly like a quiet network. Packet loss is the most common cause of an IDS missing an intrusion it had a valid signature for.

Log File Locations

Paths follow each engine's packaging conventions. Suricata concentrates almost everything into a single log directory.

Log Default Location
Suricata EVE JSON /var/log/suricata/eve.json
Suricata Fast Alert Log /var/log/suricata/fast.log
Suricata Engine Log /var/log/suricata/suricata.log
Suricata Statistics /var/log/suricata/stats.log
Suricata Configuration /etc/suricata/suricata.yaml
Snort Alert Log /var/log/snort/alert or /var/log/snort/alert_fast.txt
Snort Configuration /etc/snort/snort.conf (Snort 2) or /etc/snort/snort.lua (Snort 3)
Rule Files /etc/suricata/rules/ or /etc/snort/rules/, managed by suricata-update or PulledPork
Extracted Files /var/log/suricata/filestore/
Pro Tip: Give /var/log/suricata its own volume. EVE JSON with protocol logging enabled on a busy link can produce tens of gigabytes per day, and filling the root filesystem takes the sensor down along with everything else on the host.

Configuring IDS and IPS Logging

Suricata's logging is configured in the outputs section of suricata.yaml. These settings produce a stream suitable for SIEM ingestion without overwhelming storage.

Step 1: Configure EVE JSON Output

outputs: - eve-log: enabled: yes filetype: regular filename: eve.json community-id: true # correlate with Zeek and other tools community-id-seed: 0 types: - alert: payload: yes payload-printable: yes http-body: yes metadata: yes tagged-packets: yes - http: extended: yes - dns: version: 2 - tls: extended: yes - files: force-magic: yes force-hash: [md5, sha256] - flow - ssh - smb
The community-id field is the single most valuable setting here. It produces a hash of the connection five-tuple that matches Zeek and other tools, making cross-source correlation trivial.

Step 2: Define Your Network Variables

vars: address-groups: HOME_NET: "[10.0.0.0/8,192.168.0.0/16,172.16.0.0/12]" EXTERNAL_NET: "!$HOME_NET" HTTP_SERVERS: "[10.20.5.0/24]" SQL_SERVERS: "[10.40.1.0/24]" DNS_SERVERS: "[10.10.0.10,10.10.0.11]" port-groups: HTTP_PORTS: "[80,81,8000,8080,8443]" SHELLCODE_PORTS: "!80"
Rules are written in terms of these variables. An incorrect HOME_NET is the most common cause of a sensor generating either no alerts at all or alerting on every internal connection.

Step 3: Manage Rules with suricata-update

# List and enable rule sources suricata-update list-sources suricata-update enable-source et/open suricata-update enable-source oisf/trafficid # Fetch, build, and reload without dropping traffic suricata-update suricatasc -c reload-rules # Verify what loaded grep -c "" /var/lib/suricata/rules/suricata.rules tail -20 /var/log/suricata/suricata.log
reload-rules applies new signatures to a running sensor without a restart, which matters when the sensor is inline and a restart means a network outage.

Step 4: Tune Out Noisy Signatures

# /etc/suricata/disable.conf 2013028 # ET POLICY curl User-Agent, expected from monitoring re:.*Dshield.* # disable an entire family by regex # /etc/suricata/threshold.config # Alert once per 60 seconds per source rather than per packet threshold gen_id 1, sig_id 2001219, type limit, track by_src, count 1, seconds 60 # Suppress a known-good scanner entirely suppress gen_id 1, sig_id 2001219, track by_src, ip 10.50.9.14
Prefer threshold over disable. Thresholding keeps the detection alive at reduced volume, whereas disabling removes coverage permanently and silently.

Step 5: Switch from IDS to IPS Mode

# Inline via NFQUEUE on Linux iptables -I FORWARD -j NFQUEUE --queue-num 0 suricata -c /etc/suricata/suricata.yaml -q 0 # Then convert selected alert rules to drop rules # /etc/suricata/modify.conf 2010935 "alert" "drop" # Verify actions are being applied jq -r 'select(.event_type=="alert") | .alert.action' /var/log/suricata/eve.json | sort | uniq -c
Rules ship with the alert action even in inline mode. Traffic is only blocked once a rule is explicitly converted to drop, which surprises many teams who assume inline deployment means prevention.

Step 6: Monitor Sensor Health

outputs: - stats: enabled: yes filename: stats.log interval: 30 # Check drop rate on a running sensor suricatasc -c "dump-counters" | jq '.message.capture' grep -E "kernel_drops|kernel_packets" /var/log/suricata/stats.log | tail -4
Any sustained kernel_drops value above roughly one percent means the sensor is losing visibility. Treat it as an availability incident, not a performance tuning task.
Security Note: Enabling payload: yes writes the triggering packet contents into your logs. For rules that match on authentication traffic or personal data this means credentials and regulated data land in the SIEM. Scope payload logging to the rule categories that genuinely need it.

Anatomy of a Detection Rule

Reading a signature is what lets an analyst decide whether an alert is a true positive. Every Suricata and Snort rule is built from the same components.

Action

alert, drop, reject, or pass. In IDS mode every action behaves as alert. Only inline deployment makes drop and reject meaningful, which is the first thing to check when triaging.
Read First Critical

Header

Protocol, source, source port, direction, destination, destination port. Written using HOME_NET and EXTERNAL_NET variables, so direction tells you whether this is inbound attack or outbound compromise.
Read First Critical

sid and rev

The signature identifier and its revision number. sid is the stable key for tuning, suppression, and tracking a detection over time. Always record it in your case notes.
Read First High Risk

classtype and priority

Categorises the alert and assigns severity from 1 (highest) to 4. trojan-activity and attempted-admin warrant immediate attention, while policy-violation and misc-activity usually do not.
Triage High Risk

content and pcre

The actual match conditions: byte sequences and regular expressions applied to the payload or to protocol buffers such as http.uri. Reading these tells you exactly what the sensor saw.
Verify Medium Risk

metadata and reference

Links the signature to CVE identifiers, MITRE ATT&CK techniques, malware families, and creation dates. The fastest route from an alert to understanding what it actually detects.
Enrich Medium Risk
Security Note: Direction matters more than severity. A high severity alert for an exploit aimed at a service you do not run is noise, while a low severity outbound alert from a workstation to an unknown host can be the first sign of an active compromise.

Alert Classifications and Priority

Classtype drives triage. These are the classifications that justify immediate response and those that rarely do.

Classification Priority Triage Guidance
trojan-activity 1 Known malware traffic, usually outbound command and control. Treat as active compromise and investigate the source host immediately
attempted-admin 1 Attempted administrator privilege gain. If the target runs the affected service, escalate at once
successful-admin 1 Successful privilege gain observed. Among the highest confidence alerts any sensor produces
shellcode-detect 1 Executable code detected in a payload. High value but prone to false positives on binary file transfers
web-application-attack 1 Injection, traversal, or deserialisation against a web application. Correlate with the WAF and web server logs to confirm the response code
attempted-recon 2 Scanning and enumeration. Low individual value, high value in aggregate as an early indicator of targeting
policy-violation 2 Acceptable use rather than security, such as cleartext credentials or unapproved tooling. Route to IT rather than the SOC
protocol-command-decode 3 Unusual but not inherently malicious protocol usage. Almost always noise on its own
misc-activity 3 Catch-all informational category. Suppress aggressively unless a specific signature has proven value in your environment
not-suspicious 3 Explicitly benign traffic recorded for context. Should never generate a ticket
Pro Tip: Alert on the combination rather than the classification alone. A single attempted-recon event is noise, but attempted-recon followed by web-application-attack followed by trojan-activity from the same source within an hour is an intrusion narrated in three lines.

IDS and IPS Log Analysis Queries

Use these jq and SIEM queries to triage alert volume, confirm blocking, and find the alerts that actually matter.

Top Firing Signatures
bash> jq -r 'select(.event_type=="alert") | "\(.alert.signature_id) \(.alert.signature)"' /var/log/suricata/eve.json | sort | uniq -c | sort -rn | head -25
The starting point for every tuning exercise. The top ten signatures usually account for most of the volume and almost none of the value.
Priority 1 Alerts Only
bash> jq -r 'select(.event_type=="alert" and .alert.severity==1) | [.timestamp, .src_ip, .dest_ip, .alert.category, .alert.signature] | @tsv' /var/log/suricata/eve.json
Strips the stream down to the alerts the ruleset authors considered critical. The correct default view for a triage queue.
Outbound Trojan Activity
SIEM> source="suricata" event_type="alert" alert.category="A Network Trojan was detected" src_ip IN (10.0.0.0/8) | stats count, values(alert.signature), dc(dest_ip) by src_ip | sort - count
Filtering to internal sources turns a noisy category into a list of probably-compromised hosts. Outbound direction is what makes this high confidence.
Blocked Versus Allowed
bash> jq -r 'select(.event_type=="alert") | "\(.alert.action) \(.alert.signature)"' /var/log/suricata/eve.json | sort | uniq -c | sort -rn | head -20
Confirms which rules are actually preventing traffic. In inline deployments most rules still run in alert mode unless explicitly converted to drop.
Sensor Packet Loss
bash> jq -r 'select(.event_type=="stats") | [.timestamp, .stats.capture.kernel_packets, .stats.capture.kernel_drops] | @tsv' /var/log/suricata/eve.json | tail -10
Drops divided by packets is your blind spot percentage. Anything sustained above one percent means the sensor is missing attacks it has signatures for.
Suspicious TLS Fingerprints
bash> jq -r 'select(.event_type=="tls") | [.tls.ja3.hash, .tls.sni, .dest_ip] | @tsv' /var/log/suricata/eve.json | sort | uniq -c | sort -rn | head -30
JA3 hashes fingerprint the client TLS stack, identifying malware families inside encrypted traffic without decryption.
Executable Downloads
bash> jq -r 'select(.event_type=="fileinfo" and (.fileinfo.magic // "" | test("executable|PE32|ELF"))) | [.timestamp, .src_ip, .dest_ip, .fileinfo.filename, .fileinfo.sha256] | @tsv' /var/log/suricata/eve.json
Every executable observed crossing the sensor with its hash, ready to check against threat intelligence.
Full Flow Context for an Alert
bash> jq -r 'select(.flow_id==1874203911402318) | [.timestamp, .event_type, (.alert.signature // .http.url // .tls.sni // "")] | @tsv' /var/log/suricata/eve.json
Pivoting on flow_id reconstructs every record for a single connection: the alert, the HTTP request, the TLS handshake, and the file transfer.
Attack Chain by Source
SIEM> source="suricata" event_type="alert" | stats dc(alert.category) as stages, values(alert.category), min(_time) as first, max(_time) as last by src_ip | where stages >= 3 | sort - stages
Sources triggering three or more distinct alert categories are progressing through an attack rather than generating incidental noise.
Verify Loaded Rule Count
bash> suricatasc -c "ruleset-stats" ; grep -E "rules successfully loaded|rules failed" /var/log/suricata/suricata.log | tail -3
Rules that fail to load are reported once at startup and never mentioned again. Check this after every ruleset update.

Best Practices for IDS and IPS Logging

Apply these practices to keep a sensor deployment useful rather than ignored:

01

Set HOME_NET Correctly

Nearly every rule is written in terms of HOME_NET and EXTERNAL_NET. A wrong or default value silently breaks directionality across the entire ruleset, which is the most common serious misconfiguration in the field.

02

Monitor Packet Drop as an Outage

A saturated sensor produces fewer alerts, which resembles a quiet network. Alert on kernel_drops and treat sustained loss with the same urgency as a sensor being offline.

03

Threshold Before You Disable

Thresholding keeps a detection alive at lower volume while disabling removes coverage permanently. Record every tuning decision so future analysts know why a signature is quiet.

04

Keep the Protocol Logs, Not Just Alerts

HTTP, DNS, TLS, and file records let you investigate techniques no signature covers. Most successful hunts use this metadata rather than the alerts.

05

Enable community_id

A single field that makes Suricata, Zeek, and firewall records join on the same connection. It costs nothing and removes most of the pain from network correlation.

06

Verify That Blocking Is Actually Blocking

Inline deployment does not mean prevention. Rules ship with the alert action, so audit the ratio of drop to alert actions regularly and confirm it matches your intent.

07

Place Sensors Where They Can See

A sensor on the perimeter misses all lateral movement. Internal segments, the data centre core, and the VPN concentrator are where post-compromise activity is visible.

08

Plan for Encryption

Most traffic is TLS, so payload signatures see nothing. Compensate with JA3 fingerprinting, SNI logging, certificate metadata, and flow analysis rather than assuming content inspection still works.

Common IDS and IPS Log Examples

Real sensor output from reconnaissance through to command and control, in both fast log and EVE JSON form.

Fast Log: Exploit Attempt Against SMB

07/14/2025-09:41:22.481203 [**] [1:2024897:3] ET EXPLOIT SMB Remote Code Execution Attempt (EternalBlue) [**] [Classification: Attempted Administrator Privilege Gain] [Priority: 1] {TCP} 203.0.113.44:52144 -> 10.20.5.40:445
The compact format: sid 2024897 revision 3, priority 1, external source to an internal host on SMB. Priority 1 plus attempted-admin means this goes to the top of the queue.

EVE JSON: The Same Alert with Full Context

{"timestamp":"2025-07-14T09:41:22.481203+0000","flow_id":1874203911402318,"event_type":"alert", "src_ip":"203.0.113.44","src_port":52144,"dest_ip":"10.20.5.40","dest_port":445,"proto":"TCP", "community_id":"1:LQU9qZlK+B5F3KDmev6m5PMibrg=", "alert":{"action":"blocked","gid":1,"signature_id":2024897,"rev":3, "signature":"ET EXPLOIT SMB Remote Code Execution Attempt (EternalBlue)", "category":"Attempted Administrator Privilege Gain","severity":1, "metadata":{"attack_target":["Server"],"mitre_technique_id":["T1210"],"cve":["CVE-2017-0144"]}}, "flow":{"pkts_toserver":14,"pkts_toclient":9,"bytes_toserver":4218,"bytes_toclient":1902}}
The action field confirms the traffic was blocked, and the metadata maps directly to CVE-2017-0144 and MITRE technique T1210. This is why EVE JSON is preferred over the fast log.

Reconnaissance: Port Scan Detected

07/14/2025-09:38:02.117441 [**] [1:2010935:3] ET SCAN Suspicious inbound to MSSQL port 1433 [**] [Classification: Potentially Bad Traffic] [Priority: 2] {TCP} 198.51.100.203:44120 -> 10.40.1.15:1433 07/14/2025-09:38:02.119882 [**] [1:2010936:3] ET SCAN Suspicious inbound to mySQL port 3306 [**] [Classification: Potentially Bad Traffic] [Priority: 2] {TCP} 198.51.100.203:44121 -> 10.40.1.15:3306 07/14/2025-09:38:02.124019 [**] [1:2002910:5] ET SCAN Potential VNC Scan 5900-5920 [**] [Classification: Attempted Information Leak] [Priority: 2] {TCP} 198.51.100.203:44122 -> 10.40.1.15:5900
Three database and remote access ports probed within seven milliseconds from one source. Individually priority 2 noise, together an unmistakable service sweep.

Web Application Attack: Path Traversal

{"timestamp":"2025-07-14T09:47:33.221004+0000","event_type":"alert", "src_ip":"203.0.113.44","dest_ip":"10.20.5.40","dest_port":443, "alert":{"action":"allowed","signature_id":2006445,"signature":"ET WEB_SERVER Possible Directory Traversal Attempt", "category":"Web Application Attack","severity":1}, "http":{"hostname":"portal.example.com","url":"/download?file=../../../../etc/passwd", "http_user_agent":"python-requests/2.31.0","http_method":"GET","status":200,"length":2841}, "payload_printable":"GET /download?file=../../../../etc/passwd HTTP/1.1"}
Status 200 with 2841 bytes returned means the traversal succeeded. The action field says allowed, so the sensor watched this happen without stopping it.

Command and Control: Outbound Beacon

{"timestamp":"2025-07-14T10:02:44.881229+0000","event_type":"alert", "src_ip":"10.30.2.61","src_port":52190,"dest_ip":"203.0.113.44","dest_port":443, "alert":{"action":"allowed","signature_id":2033102, "signature":"ET MALWARE Cobalt Strike Beacon Observed","category":"A Network Trojan was detected","severity":1, "metadata":{"mitre_technique_id":["T1071.001"],"malware_family":["CobaltStrike"]}}, "tls":{"sni":"cdn-assets.badinfra.top","ja3":{"hash":"a0e9f5d64349fb13191bc781f81f42e1"}, "subject":"CN=cdn-assets.badinfra.top","issuerdn":"CN=R3, O=Let's Encrypt"}}
The direction is what matters: an internal workstation initiating this. The JA3 hash identified Cobalt Strike inside TLS without any decryption, and the certificate is a free one issued days ago.

Sensor Health: Packet Loss

{"timestamp":"2025-07-14T10:05:00.000000+0000","event_type":"stats", "stats":{"uptime":86402, "capture":{"kernel_packets":1842119004,"kernel_drops":412887221}, "decoder":{"pkts":1429231783,"bytes":1102847119228}, "detect":{"alert":18442}}}
412 million drops against 1.84 billion packets is a 22 percent loss rate. Roughly one in five packets was never inspected, so any conclusion drawn from these alerts is unreliable.

Data Exfiltration: Asymmetric Flow

{"timestamp":"2025-07-14T10:18:12.774119+0000","event_type":"flow", "src_ip":"10.30.2.61","src_port":52240,"dest_ip":"203.0.113.91","dest_port":443,"proto":"TCP", "flow":{"pkts_toserver":1284119,"pkts_toclient":42881, "bytes_toserver":1884221904,"bytes_toclient":3218844, "start":"2025-07-14T02:11:04.221000+0000","end":"2025-07-14T10:18:12.774000+0000","age":29228, "state":"established","reason":"timeout"}}
1.88 GB uploaded against 3.2 MB downloaded over an eight hour session. No rule fired at all, yet the flow record alone describes bulk exfiltration. This is why flow logging matters.
