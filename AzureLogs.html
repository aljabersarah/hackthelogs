Microsoft Azure Logs

Azure Log Overview

Azure logging divides along a line that does not exist in other clouds: the control plane for Azure resources and the identity plane managed by Microsoft Entra ID, formerly Azure Active Directory. The Activity Log records operations against subscriptions and resources, while Entra ID sign-in and audit logs record authentication and directory changes. Because Entra ID also underpins Microsoft 365, an attacker who compromises an identity gains access to mail, files, and Teams alongside Azure infrastructure. That coupling is why identity logs, not resource logs, are where most Azure investigations begin and end.

The default retention is the trap that catches most organisations. Activity Log entries are kept for 90 days, Entra ID sign-in and audit logs for 30 days on paid tiers and only 7 days on the free tier, and resource logs are not collected at all until a diagnostic setting is created. Every one of those defaults is shorter than the average time to detect an intrusion. Exporting to a Log Analytics workspace or a storage account is not an optimisation, it is the difference between having evidence and not.

Modern attacks against Azure rarely involve exploiting infrastructure. They target tokens and consent. Device code phishing tricks a user into authorising an attacker's session, illicit consent grants give a malicious application standing access to mailboxes without any password, and primary refresh token theft lets an attacker replay authentication from their own machine while satisfying multi-factor requirements. None of these produce a failed login. They produce clean, successful sign-ins with unusual properties, which means detection depends on scrutinising successes rather than counting failures.

Key Azure Log Types

Azure separates its telemetry into several distinct streams, each enabled and retained independently:

Log Type Description
Entra ID Sign-in Logs Every authentication attempt with the user, application, source address, device, conditional access outcome, and risk assessment. Split into interactive, non-interactive, service principal, and managed identity sign-ins, each collected separately. The most important log in the tenant.
Entra ID Audit Logs Directory changes including role assignments, group membership, application registration, consent grants, and conditional access policy modification. Where privilege escalation and persistence become visible.
Azure Activity Log Control plane operations against subscriptions and resources: creation, deletion, configuration change, and role assignment at the Azure RBAC level. Equivalent in role to AWS CloudTrail management events.
Resource Logs Data plane operations inside individual services such as Key Vault secret retrieval, storage account access, and SQL auditing. Not collected at all until a diagnostic setting is configured per resource.
Microsoft 365 Unified Audit Log Activity across Exchange, SharePoint, OneDrive, and Teams. Shares the Entra ID identity plane, so a compromised account appears here and in Azure logs simultaneously. Searched through Purview or the Office 365 Management API.
Identity Protection Risk Events Managed risk detections such as anonymous IP address use, impossible travel, leaked credentials, and anomalous token issuance. Requires Entra ID P2 licensing for full detail.
NSG Flow Logs Network metadata for traffic through network security groups, comparable to VPC Flow Logs. Being superseded by virtual network flow logs, which offer better coverage.
Defender for Cloud Alerts Threat detections across Azure workloads, containers, databases, and storage, correlated into incidents. The fastest path to noticing well-known attack patterns without writing detections.
Pro Tip: Non-interactive sign-ins are a separate log category and are excluded from the default sign-in view. Token refreshes, service principal authentication, and most automated access appear only there, which is precisely where token replay attacks hide.

Log Destinations and Retention

Default retention is short across the board. These are the built-in limits and where each stream can be exported.

Log Default Retention and Destination
Entra ID Sign-in Logs 30 days with P1 or P2, only 7 days on the free tier. Export to Log Analytics, storage, or Event Hub
Entra ID Audit Logs 30 days with P1 or P2, 7 days on free. Same export options
Azure Activity Log 90 days in the platform, not configurable. Export required for anything longer
Resource Logs Not collected at all by default. Requires a diagnostic setting on each resource
Microsoft 365 Unified Audit Log 180 days on E3, one year on E5 or with an audit add-on. Searchable via Purview
Log Analytics Workspace Configurable from 30 days to 2 years interactive, with archive up to 12 years
Microsoft Sentinel Built on Log Analytics with the same retention model plus security analytics
Storage Account Export Indefinite retention at the lowest cost, but not directly queryable
Pro Tip: Diagnostic settings are configured per resource, not per subscription. A new storage account or Key Vault created next week collects nothing unless Azure Policy applies a setting automatically. Deploy that policy before you need the logs.

Configuring Azure Logging

These commands export the critical streams to a Log Analytics workspace and ensure new resources are covered automatically.

Step 1: Export Entra ID Logs to Log Analytics

az monitor diagnostic-settings create \ --name htl-entra-export \ --resource /providers/Microsoft.AadIam/diagnosticSettings \ --workspace /subscriptions/<sub>/resourceGroups/rg-sec/providers/Microsoft.OperationalInsights/workspaces/htl-sec-law \ --logs '[{"category":"SignInLogs","enabled":true}, {"category":"AuditLogs","enabled":true}, {"category":"NonInteractiveUserSignInLogs","enabled":true}, {"category":"ServicePrincipalSignInLogs","enabled":true}, {"category":"ManagedIdentitySignInLogs","enabled":true}, {"category":"RiskyUsers","enabled":true}, {"category":"UserRiskEvents","enabled":true}]'
All five sign-in categories must be listed individually. Enabling only SignInLogs captures interactive logons and misses service principal abuse and token refresh entirely.

Step 2: Export the Activity Log

az monitor diagnostic-settings subscription create \ --name htl-activity-export \ --location me-central-1 \ --workspace <workspace-resource-id> \ --logs '[{"category":"Administrative","enabled":true}, {"category":"Security","enabled":true}, {"category":"ServiceHealth","enabled":true}, {"category":"Alert","enabled":true}, {"category":"Policy","enabled":true}, {"category":"Autoscale","enabled":false}, {"category":"ResourceHealth","enabled":true}]'
The Administrative and Policy categories carry role assignments and policy changes, which is where Azure privilege escalation appears.

Step 3: Enforce Diagnostic Settings with Azure Policy

az policy assignment create \ --name htl-require-diagnostics \ --policy-set-definition "Enable allLogs category group resource logging for supported resources to Log Analytics" \ --scope /subscriptions/<sub> \ --location me-central-1 \ --mi-system-assigned \ --role Contributor \ --identity-scope /subscriptions/<sub> \ --params '{"logAnalytics":{"value":"<workspace-resource-id>"}}' az policy remediation create --name fix-existing \ --policy-assignment htl-require-diagnostics
DeployIfNotExists policy applies diagnostic settings to resources as they are created. Without it, coverage decays continuously as the estate grows.

Step 4: Enable Key Vault and Storage Data Plane Logging

# Key Vault: record every secret and key retrieval az monitor diagnostic-settings create --name kv-audit \ --resource <keyvault-resource-id> \ --workspace <workspace-resource-id> \ --logs '[{"category":"AuditEvent","enabled":true}, {"category":"AzurePolicyEvaluationDetails","enabled":true}]' # Storage: record blob read and write operations az monitor diagnostic-settings create --name storage-audit \ --resource <storage-id>/blobServices/default \ --workspace <workspace-resource-id> \ --logs '[{"category":"StorageRead","enabled":true}, {"category":"StorageWrite","enabled":true}, {"category":"StorageDelete","enabled":true}]'
Key Vault AuditEvent is the Azure equivalent of AWS S3 data events: without it you can prove a vault was accessed but not which secrets were read.

Step 5: Enable the Microsoft 365 Unified Audit Log

Connect-ExchangeOnline Set-AdminAuditLogConfig -UnifiedAuditLogIngestionEnabled $true Get-AdminAuditLogConfig | Select-Object UnifiedAuditLogIngestionEnabled # Enable mailbox auditing for all mailboxes including owner actions Set-OrganizationConfig -AuditDisabled $false Get-Mailbox -ResultSize Unlimited | Set-Mailbox -AuditEnabled $true -AuditOwner @{Add="MailItemsAccessed","Send","SoftDelete","HardDelete"}
MailItemsAccessed is the only record proving an attacker actually read mail rather than merely having access. It requires E5 or an equivalent add-on licence.

Step 6: Extend Retention Beyond the Defaults

az monitor log-analytics workspace update \ --resource-group rg-sec --workspace-name htl-sec-law \ --retention-time 365 # Per-table retention with cheaper long term archive az monitor log-analytics workspace table update \ --resource-group rg-sec --workspace-name htl-sec-law \ --name SigninLogs --retention-time 365 --total-retention-time 2555
Interactive retention is queryable immediately, archive retention is cheaper but requires a restore job. Keeping sign-in logs for a year is the practical minimum for identity investigations.
Security Note: Entra ID free tier keeps sign-in logs for seven days. Given that the median dwell time for identity compromise is measured in weeks, a tenant on the free tier will have destroyed the evidence of the initial compromise long before anyone notices it happened.

Azure Identity Threat Patterns

Azure attacks target identity rather than infrastructure. These patterns dominate real incidents and most of them produce successful sign-ins, not failures.

Password Spraying

One password tried against many accounts to avoid lockout. Signature: result code 50126 across dozens of distinct users from one address, often targeting legacy authentication endpoints.
Detect Critical

Illicit Consent Grant

A user is tricked into consenting to a malicious application, granting it standing access to mail and files. Requires no password and survives password reset entirely.
Detect Critical

Device Code Phishing

The attacker initiates a device code flow and persuades the victim to enter the code. The resulting token belongs to the attacker and satisfies MFA. Signature: device code authentication from an unexpected client.
Detect Critical

Token and PRT Theft

Stolen refresh tokens replayed from attacker infrastructure. Produces successful non-interactive sign-ins with a mismatch between the device identity and the source address.
Detect Critical

Privileged Role Assignment

Adding an account to Global Administrator, Privileged Role Administrator, or Application Administrator. The last two allow escalation to full tenant control indirectly.
Detect Critical

Conditional Access Tampering

Disabling a policy, adding an exclusion for a compromised account, or switching to report-only mode. Silently removes MFA enforcement while the policy still appears to exist.
Detect Critical
Security Note: Adding a credential to an existing service principal, through Update application: Certificates and secrets management, is one of the stealthiest persistence techniques in Entra ID. The application continues to work normally, no user is involved, and the attacker holds a credential that no password reset affects.

Critical Sign-in Result Codes

Entra ID result codes are stable and precise, which makes them excellent detection anchors. These are the ones that matter most.

Code Meaning Why It Matters
0 Sign-in succeeded Token theft, consent abuse, and device code phishing all produce this. Successes need scrutiny, not just failures
50126 Invalid username or password The core failure code. Many distinct users from one address is password spraying
50053 Account locked by smart lockout Confirms sustained guessing reached the threshold, or an attacker locking a user out deliberately
50055 / 50057 Password expired or account disabled Attempts against dormant accounts, a common sign that a stale credential list is being tested
50074 / 50076 Strong authentication required MFA was demanded. A burst followed by a success is the shape of an MFA fatigue attack
50140 Keep me signed in interrupt Normal in interactive flows, but useful for distinguishing genuine browser sessions from scripted ones
53003 Blocked by conditional access policy Policy enforcement working. Repeated blocks for one account from an unusual location is an attacker being stopped
530032 Blocked by security defaults or policy Similar enforcement signal, frequently seen when legacy authentication is attempted
50158 External security challenge not satisfied A third party MFA or risk challenge failed, often during token replay from an unexpected location
65001 User or administrator has not consented Precedes consent grant activity. A burst can indicate an application probing for what it can obtain
Pro Tip: ConditionalAccessStatus of notApplied on a successful sign-in means no policy evaluated that request at all. On a privileged account that is a policy gap worth fixing immediately, because MFA was never actually required.

Azure Log Analysis Queries

These KQL queries run in Log Analytics or Microsoft Sentinel and cover the dominant Azure attack paths.

Password Spraying
KQL> SigninLogs | where ResultType == 50126 | summarize Targets=dcount(UserPrincipalName), Attempts=count() by IPAddress, bin(TimeGenerated, 1h) | where Targets > 20 and Attempts/Targets < 3
Many users with few attempts each is the spray signature, deliberately staying below smart lockout thresholds.
Illicit Consent Grant
KQL> AuditLogs | where OperationName has_any ("Consent to application","Add delegated permission grant","Add app role assignment to service principal") | extend perms=tostring(TargetResources[0].modifiedProperties) | where perms has_any ("Mail.Read","Mail.ReadWrite","Files.ReadWrite.All","Directory.ReadWrite.All")
Consent granting mailbox or directory-wide permissions. Survives password reset entirely, so it must be revoked explicitly.
Device Code Phishing
KQL> SigninLogs | where AuthenticationProtocol == "deviceCode" | summarize Apps=make_set(AppDisplayName), IPs=make_set(IPAddress), count() by UserPrincipalName, Location
Device code flow is legitimate only for input-constrained devices. On a normal workstation account it almost always means phishing.
Privileged Role Assignment
KQL> AuditLogs | where OperationName == "Add member to role" | extend Role=tostring(TargetResources[0].modifiedProperties[1].newValue) | where Role has_any ("Global Administrator","Privileged Role Administrator","Application Administrator","Cloud Application Administrator") | project TimeGenerated, InitiatedBy, Role, TargetResources
Assignment to any of these four roles is effectively full tenant compromise. Application Administrator escalates indirectly by adding credentials to privileged service principals.
Service Principal Credential Added
KQL> AuditLogs | where OperationName in ("Update application - Certificates and secrets management","Add service principal credentials") | project TimeGenerated, InitiatedBy, TargetResources, Result
One of the stealthiest persistence techniques in Entra ID. The application keeps working, no user is involved, and no password reset affects it.
Conditional Access Tampering
KQL> AuditLogs | where Category == "Policy" and OperationName has_any ("Update conditional access policy","Delete conditional access policy","Add conditional access policy") | project TimeGenerated, InitiatedBy, OperationName, TargetResources
Adding an exclusion or switching a policy to report-only silently removes MFA enforcement while the policy still appears to exist.
Impossible Travel
KQL> SigninLogs | where ResultType == 0 | sort by UserPrincipalName asc, TimeGenerated asc | extend prevCountry=prev(Location), prevTime=prev(TimeGenerated), prevUser=prev(UserPrincipalName) | where prevUser == UserPrincipalName and prevCountry != Location and datetime_diff("minute", TimeGenerated, prevTime) < 240
Two successful sign-ins from different countries within four hours. Whitelist VPN egress points and adjacent-country commuting before deploying.
Legacy Authentication
KQL> SigninLogs | where ClientAppUsed in ("Other clients","IMAP4","POP3","SMTP","Exchange ActiveSync","Authenticated SMTP") | summarize count(), Users=dcount(UserPrincipalName) by ClientAppUsed, IPAddress | order by count_ desc
Legacy protocols cannot enforce MFA, which is exactly why attackers target them. Any remaining usage is both a finding and an attack surface.
Token Replay Indicators
KQL> AADNonInteractiveUserSignInLogs | where ResultType == 0 | where isempty(tostring(DeviceDetail.deviceId)) | summarize IPs=dcount(IPAddress), Countries=dcount(tostring(LocationDetails.countryOrRegion)) by UserPrincipalName | where Countries > 1
Non-interactive successes from an unregistered device across multiple countries is the shape of a stolen refresh token being replayed.
Key Vault Secret Harvesting
KQL> AzureDiagnostics | where ResourceType == "VAULTS" and OperationName in ("SecretGet","KeyGet","CertificateGet") | summarize Secrets=dcount(id_s), count() by identity_claim_upn_s, CallerIPAddress | where Secrets > 10
One identity pulling many distinct secrets in a short window is credential harvesting, not normal application behaviour.
Azure RBAC Role Assignments
KQL> AzureActivity | where OperationNameValue == "MICROSOFT.AUTHORIZATION/ROLEASSIGNMENTS/WRITE" and ActivityStatusValue == "Success" | project TimeGenerated, Caller, CallerIpAddress, Properties
Azure RBAC is separate from Entra ID directory roles. Owner or Contributor at subscription scope grants control of every resource beneath it.
Mailbox Access and Forwarding
KQL> OfficeActivity | where Operation in ("New-InboxRule","Set-InboxRule","Set-Mailbox","Add-MailboxPermission") | where Parameters has_any ("ForwardTo","RedirectTo","DeleteMessage") | project TimeGenerated, UserId, Operation, Parameters
Inbox rules that forward externally or delete messages are the classic business email compromise persistence and concealment technique.

Best Practices for Azure Logging

Apply these practices so identity evidence still exists when you finally go looking for it:

01

Export Entra ID Logs Immediately

Seven days on the free tier and thirty on paid tiers are both shorter than typical dwell time. Exporting to Log Analytics is the single highest value logging change in any Azure tenant.

02

Enable All Five Sign-in Categories

Interactive sign-ins are only one category. Non-interactive, service principal, and managed identity sign-ins are where token replay and automation abuse appear, and they are excluded by default.

03

Enforce Diagnostic Settings with Policy

Settings are per resource. Without a DeployIfNotExists policy, every new Key Vault and storage account arrives with no logging, and coverage silently erodes as the estate grows.

04

Monitor Successful Sign-ins, Not Only Failures

Consent abuse, device code phishing, and token theft all produce clean successes. Failure-based monitoring is blind to the techniques that dominate real Azure intrusions.

05

Alert on Consent and Service Principal Credentials

Both create access that no password reset revokes. They are low volume and high fidelity, making them ideal candidates for real-time alerting.

06

Watch Conditional Access Changes Closely

An exclusion added for one account removes MFA for that account while the policy still shows as enabled. Treat every policy modification as a security event requiring review.

07

Enable Mailbox Auditing Including Owner Actions

MailItemsAccessed is the only evidence proving an attacker actually read mail. Without it you can show access was possible but not what was taken.

08

Eliminate Legacy Authentication

Legacy protocols bypass conditional access and cannot enforce MFA. Block them outright, then treat any remaining attempts as attack traffic rather than misconfiguration.

Common Azure Log Examples

An Entra ID account takeover, from spraying through consent abuse to mailbox exfiltration.

Password Spraying Against Legacy Authentication

TimeGenerated: 2025-07-14T09:12:04Z UserPrincipalName: a.alqahtani@corp.com ResultType: 50126 IPAddress: 203.0.113.44 ClientAppUsed: Other clients AppDisplayName: Exchange ActiveSync ConditionalAccessStatus: notApplied AuthenticationRequirement: singleFactorAuthentication TimeGenerated: 2025-07-14T09:12:09Z UserPrincipalName: m.alharbi@corp.com ResultType: 50126 IPAddress: 203.0.113.44 ClientAppUsed: Other clients TimeGenerated: 2025-07-14T09:12:14Z UserPrincipalName: r.almutairi@corp.com ResultType: 50126 IPAddress: 203.0.113.44 ClientAppUsed: Other clients
Legacy authentication was targeted deliberately: ConditionalAccessStatus is notApplied, meaning no policy evaluated these attempts and MFA could never have been enforced.

Successful Sign-in from an Unmanaged Device

TimeGenerated: 2025-07-14T09:40:53Z UserPrincipalName: r.almutairi@corp.com ResultType: 0 IPAddress: 203.0.113.44 LocationDetails: {"city":"Amsterdam","countryOrRegion":"NL"} AppDisplayName: Microsoft Office 365 Portal ClientAppUsed: Browser DeviceDetail: {"deviceId":"","operatingSystem":"Linux","browser":"Chrome 126.0"} RiskLevelDuringSignIn: high RiskEventTypesV2: ["unfamiliarFeatures","anonymizedIPAddress"] ConditionalAccessStatus: success AuthenticationRequirement: multiFactorAuthentication
ResultType 0 means this succeeded, and MFA was satisfied. The empty deviceId shows an unmanaged Linux machine, and Identity Protection scored it high risk. A success can still be an intrusion.

Device Code Phishing

TimeGenerated: 2025-07-14T09:38:02Z UserPrincipalName: r.almutairi@corp.com ResultType: 0 AuthenticationProtocol: deviceCode AppDisplayName: Microsoft Office ResourceDisplayName: Microsoft Graph IPAddress: 203.0.113.44 LocationDetails: {"city":"Amsterdam","countryOrRegion":"NL"} DeviceDetail: {"deviceId":"","operatingSystem":"","browser":""} IncomingTokenType: none AuthenticationRequirement: multiFactorAuthentication
Device code flow exists for devices without a keyboard, such as smart TVs. On a finance user's account it means they entered a code an attacker generated, handing over a fully MFA-satisfied token.

Illicit Consent Grant

OperationName: Consent to application InitiatedBy: {"user":{"userPrincipalName":"r.almutairi@corp.com","ipAddress":"203.0.113.44"}} TargetResources: [{"displayName":"Office365 Document Sync","type":"ServicePrincipal", "modifiedProperties":[{"displayName":"ConsentAction.Permissions", "newValue":"Scope: Mail.Read Mail.ReadWrite Files.ReadWrite.All User.Read offline_access"}]}] Result: success
A plausibly named application granted persistent mailbox and file access. The offline_access scope gives it a refresh token, so it retains access indefinitely and a password reset changes nothing.

Privilege Escalation via Role Assignment

OperationName: Add member to role InitiatedBy: {"user":{"userPrincipalName":"r.almutairi@corp.com","ipAddress":"203.0.113.44"}} TargetResources: [{"userPrincipalName":"svc-sync@corp.com","type":"User", "modifiedProperties":[{"displayName":"Role.DisplayName","newValue":"Global Administrator"}]}] Result: success Category: RoleManagement
The compromised user adding a service account to Global Administrator. That account now controls the entire tenant, including Microsoft 365 and every Azure subscription beneath it.

Persistence via Service Principal Credential

OperationName: Update application - Certificates and secrets management InitiatedBy: {"user":{"userPrincipalName":"svc-sync@corp.com","ipAddress":"203.0.113.44"}} TargetResources: [{"displayName":"Corp HR Integration","type":"Application", "modifiedProperties":[{"displayName":"KeyDescription", "newValue":"[KeyIdentifier=8f2a1c04,KeyType=Password,KeyUsage=Verify]"}]}] Result: success
A new client secret added to an existing privileged application. The application continues functioning normally, no user is involved, and the attacker now holds a credential unaffected by any password reset.

Conditional Access Policy Weakened

OperationName: Update conditional access policy InitiatedBy: {"user":{"userPrincipalName":"svc-sync@corp.com","ipAddress":"203.0.113.44"}} TargetResources: [{"displayName":"CA001-Require MFA for All Users","type":"Policy", "modifiedProperties":[{"displayName":"ConditionalAccessPolicy", "oldValue":"{state:enabled, users:{excludeUsers:[]}}", "newValue":"{state:enabled, users:{excludeUsers:[r.almutairi@corp.com]}}"}]}]
The policy remains enabled and looks healthy in the portal, but the compromised account is now excluded from MFA entirely. Only the audit log reveals this.

Mailbox Exfiltration and Concealment

Operation: New-InboxRule UserId: r.almutairi@corp.com ClientIP: 203.0.113.44 Parameters: [{"Name":"Name","Value":"."},{"Name":"ForwardTo","Value":"archive@badinfra.top"}, {"Name":"DeleteMessage","Value":"True"},{"Name":"From","Value":"finance@corp.com"}] Operation: MailItemsAccessed UserId: r.almutairi@corp.com ClientIP: 203.0.113.44 OperationProperties: [{"Name":"MailAccessType","Value":"Bind"},{"Name":"IsThrottled","Value":"True"}] Folders: [{"Path":"\Inbox","FolderItems":[{"InternetMessageId":"..."}]}]
An inbox rule named with a single dot, forwarding finance mail externally and deleting the local copy. The MailItemsAccessed record with IsThrottled true means so much mail was read that Microsoft rate limited the auditing.
