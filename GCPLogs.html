Google Cloud Logs

Google Cloud Log Overview

Google Cloud records administrative activity through Cloud Audit Logs, which are organised into four distinct streams with very different default behaviour. Admin Activity logs capture every operation that modifies configuration or metadata, are always enabled, cannot be disabled, and are retained for 400 days at no charge. System Event logs record Google-initiated actions such as automatic instance migration and are equally unavoidable. Those two guarantees are genuinely useful: unlike AWS CloudTrail, which can be stopped, the core Google Cloud audit trail cannot be turned off by an attacker.

The other two streams are where the gaps appear. Data Access logs record reads of user data and non-modifying API calls, and they are disabled by default for every service except BigQuery. Enabling them is a deliberate decision with real cost implications, and the consequence of skipping it is the same as skipping CloudTrail data events in AWS: you can prove a bucket permission changed but not which objects were subsequently downloaded. Policy Denied logs capture requests blocked by VPC Service Controls or organisation policy, and they are generated automatically but charged, which leads some organisations to filter them out.

What distinguishes Google Cloud operationally is the centrality of service accounts and impersonation. Rather than long-lived keys, the recommended pattern is short-lived token generation through generateAccessToken, granted by the Service Account Token Creator role. This is better security practice, but it creates impersonation chains that are genuinely difficult to follow: principal A impersonates service account B which impersonates C, and only the authenticationInfo.serviceAccountDelegationInfo field records the full path. Attackers exploit exactly this, and detections that only look at the immediate caller will attribute their actions to a legitimate service account.

Key Google Cloud Log Types

Four audit log streams plus several supporting sources, each with its own default state and cost model:

Log Type Description
Admin Activity Audit Logs Every API call that modifies configuration or metadata: IAM policy changes, resource creation and deletion, service account key creation. Always enabled, cannot be disabled, free, and retained 400 days. The backbone of Google Cloud investigation.
Data Access Audit Logs Reads of user data and non-modifying API calls such as storage.objects.get and bigquery data reads. Disabled by default for all services except BigQuery. Without these you cannot determine what data an attacker actually accessed.
System Event Audit Logs Google-initiated actions taken without user involvement, such as automatic live migration of an instance or automatic instance termination. Always enabled and free.
Policy Denied Audit Logs Requests rejected by VPC Service Controls, organisation policy, or context-aware access. Generated automatically but billed. Extremely useful because a denied request often reveals an attacker probing a boundary.
VPC Flow Logs Network metadata sampled from virtual machine interfaces, including source, destination, ports, bytes, and geographic annotation. Enabled per subnet with a configurable sampling rate.
Firewall Rules Logging Records connections allowed or denied by individual firewall rules. Enabled per rule rather than globally, so coverage is easy to leave incomplete.
Security Command Center Findings Managed detection across misconfiguration, vulnerabilities, and threats, including Event Threat Detection which analyses audit logs directly. The Premium tier adds behavioural detections such as anomalous IAM grants.
Access Transparency Logs Records actions taken by Google personnel on your content, available on eligible support tiers. Rarely relevant to attack detection but frequently required for regulatory assurance.
Pro Tip: The guarantee that Admin Activity logs cannot be disabled applies to the log generation, not to your copy of it. An attacker with sufficient permissions can still delete a log sink, stopping delivery to your SIEM while the logs continue accumulating in the platform bucket where nobody is watching.

Log Storage and Retention

Cloud Logging routes entries through the Log Router into buckets and sinks. Understanding the default buckets prevents both surprise costs and surprise gaps.

Destination Characteristics
_Required Bucket Holds Admin Activity, System Event, and Access Transparency logs. Retention fixed at 400 days, cannot be changed or deleted, and incurs no charge
_Default Bucket Holds everything else including Data Access logs. Default retention 30 days, configurable up to 3650 days, and billed on ingestion
Custom Log Buckets User-created buckets with independent retention and optional Log Analytics for SQL querying
BigQuery Sink Streams logs into datasets for SQL analysis and long term retention. The standard approach for security analytics at scale
Cloud Storage Sink Archives logs as JSON files to a bucket. Cheapest long term retention, supports Bucket Lock for immutability
Pub/Sub Sink Streams to an external SIEM in near real time. The standard integration path for Splunk, Chronicle, and similar platforms
Aggregated Sink Configured at organisation or folder level to capture logs from every project beneath, including projects created later
Pro Tip: The _Default bucket keeps Data Access logs for only 30 days. If you enable Data Access logging without also extending retention or configuring a sink, you gain visibility that expires before most breaches are even discovered.

Configuring Google Cloud Logging

These commands enable the streams that are off by default and route everything to a location an attacker in a member project cannot reach.

Step 1: Enable Data Access Audit Logs

# Fetch the current organisation IAM policy gcloud organizations get-iam-policy 123456789012 --format=json > policy.json # Add an auditConfigs block covering all services cat <<'JSON' > audit.json { "auditConfigs": [ { "service": "allServices", "auditLogConfigs": [ { "logType": "ADMIN_READ" }, { "logType": "DATA_READ", "exemptedMembers": ["serviceAccount:noisy-etl@proj.iam.gserviceaccount.com"] }, { "logType": "DATA_WRITE" } ] } ] } JSON gcloud organizations set-iam-policy 123456789012 policy-with-audit.json
ADMIN_READ, DATA_READ, and DATA_WRITE must each be listed. Setting this at organisation level covers every current and future project, which is the only way to keep coverage complete as the estate grows.

Step 2: Create an Aggregated Sink to BigQuery

gcloud logging sinks create htl-org-security-sink \ bigquery.googleapis.com/projects/htl-security/datasets/cloud_audit \ --organization=123456789012 \ --include-children \ --use-partitioned-tables \ --log-filter='logName:"cloudaudit.googleapis.com" OR logName:"compute.googleapis.com%2Fvpc_flows"' # Grant the sink writer identity permission on the destination gcloud projects add-iam-policy-binding htl-security \ --member="$(gcloud logging sinks describe htl-org-security-sink \ --organization=123456789012 --format='value(writerIdentity)')" \ --role=roles/bigquery.dataEditor
The include-children flag captures every project under the organisation, including ones created tomorrow. Without an aggregated sink, each new project starts unmonitored.

Step 3: Extend Default Bucket Retention

gcloud logging buckets update _Default \ --location=global \ --retention-days=365 \ --project=htl-production # Confirm both buckets gcloud logging buckets list --project=htl-production \ --format="table(name, retentionDays, lifecycleState, locked)"
The _Default bucket keeps Data Access logs for only 30 days. Enabling data access logging without extending retention produces visibility that expires before most breaches are discovered.

Step 4: Lock the Archive Against Tampering

# Cloud Storage sink with Bucket Lock for immutable retention gsutil retention set 400d gs://htl-audit-archive gsutil retention lock gs://htl-audit-archive # Restrict who can modify the Log Router itself gcloud organizations add-iam-policy-binding 123456789012 \ --member="group:cloud-security@corp.com" \ --role=roles/logging.configWriter
Bucket Lock is irreversible once applied, which is exactly the property that makes it valuable. Nobody, including an organisation administrator, can shorten the retention afterwards.

Step 5: Enable VPC Flow Logs and Firewall Logging

gcloud compute networks subnets update prod-subnet-me1 \ --region=me-central1 \ --enable-flow-logs \ --logging-aggregation-interval=interval-30-sec \ --logging-flow-sampling=1.0 \ --logging-metadata=include-all # Firewall logging is enabled per rule, not globally gcloud compute firewall-rules update allow-internal \ --enable-logging --logging-metadata=include-all
Flow sampling defaults to 0.5, meaning half of all flows are discarded. Set it to 1.0 on sensitive subnets, because a sampled log cannot prove a connection did not happen.

Step 6: Alert on Sink and Audit Config Changes

gcloud logging metrics create sink_tampering \ --description="Log Router or audit config modified" \ --log-filter='protoPayload.methodName=( "google.logging.v2.ConfigServiceV2.DeleteSink" OR "google.logging.v2.ConfigServiceV2.UpdateSink" OR "google.logging.v2.ConfigServiceV2.UpdateBucket" OR "SetIamPolicy") AND protoPayload.serviceData.policyDelta.auditConfigDeltas:*' gcloud alpha monitoring policies create --policy-from-file=sink-alert.yaml
The auditConfigDeltas filter is the important part: it fires when someone disables audit logging for a service, which is otherwise a quiet change buried inside a routine IAM policy update.
Security Note: Admin Activity logs cannot be disabled, but the delivery of your copy can be. Deleting a sink stops the flow to your SIEM while logs continue accumulating in the platform bucket that nobody monitors. Alert on sink deletion with the same urgency as AWS StopLogging.

Google Cloud Threat Patterns

Google Cloud attacks centre on service accounts and IAM. These are the patterns that account for most real incidents.

Service Account Key Creation

Creating a long-lived JSON key for a privileged service account. The key never expires, works from anywhere, and is unaffected by any password or session policy. The most common Google Cloud persistence technique.
Detect Critical

Impersonation Chains

Using Service Account Token Creator to generate tokens for progressively more privileged accounts. Only serviceAccountDelegationInfo reveals the true origin, so naive detections blame the final service account.
Detect Critical

Public IAM Binding

Granting a role to allUsers or allAuthenticatedUsers on a bucket, dataset, or function. Exposes the resource to the entire internet in a single API call.
Detect Critical

IAM Privilege Escalation

Self-granting roles/owner or roles/iam.securityAdmin through setIamPolicy. Also achievable indirectly through actAs on a privileged service account attached to a compute instance.
Detect Critical

Data Exfiltration

Bulk object reads, BigQuery extract jobs to external buckets, or Cloud SQL exports. Visible only if Data Access logging is enabled for the relevant service.
Detect High Risk

Logging Evasion

Deleting a log sink, disabling audit configs for a service, or operating in a project outside the aggregated sink scope. Stops your visibility without stopping log generation.
Detect Critical
Security Note: The roles/iam.serviceAccountUser and roles/iam.serviceAccountTokenCreator roles are frequently granted casually because they sound benign. Either one lets a principal act as a service account, inheriting all of its permissions, which makes them among the most dangerous grants in Google Cloud.

Audit Log Entry Format

Every Cloud Audit Log entry shares the AuditLog protobuf structure. These are the fields that carry detection value.

Field Description Category Example Value
timestamp UTC time the request was received Timestamp 2025-07-14T09:41:22.481Z
protoPayload.methodName The API method invoked Action google.iam.admin.v1.CreateServiceAccountKey
protoPayload.serviceName Service that handled the request Target iam.googleapis.com
authenticationInfo.principalEmail Identity that made the call Identity svc-deploy@proj.iam.gserviceaccount.com
serviceAccountDelegationInfo Full impersonation chain when present Identity firstPartyPrincipal: r.almutairi@corp.com
requestMetadata.callerIp Source address of the caller Source 203.0.113.44
callerSuppliedUserAgent Client library or tool used Source google-cloud-sdk gcloud/470.0.0
resourceName Full path of the resource acted upon Target projects/htl-prod/buckets/customer-data
authorizationInfo.permission IAM permission checked Authorization storage.buckets.setIamPolicy
authorizationInfo.granted Whether the permission was allowed Result true
status.code gRPC status, absent or 0 on success Result 7 (PERMISSION_DENIED)
serviceData.policyDelta Exact IAM bindings added or removed Action ADD roles/owner to user:...
logName Which audit stream produced the entry Metadata cloudaudit.googleapis.com%2Factivity
Pro Tip: Always read serviceAccountDelegationInfo alongside principalEmail. When impersonation is used, principalEmail shows the service account being impersonated, not the human or key that initiated the chain. Detections built on principalEmail alone attribute attacker actions to legitimate automation.

Critical Methods to Monitor

A short list of API methods accounts for most Google Cloud compromise. These belong on a real-time watchlist.

Method Stage Why It Matters
CreateServiceAccountKey Persistence Produces a non-expiring credential usable from anywhere. Should be rare in a mature environment that uses workload identity federation
SetIamPolicy Escalation The universal permission change method. Inspect serviceData.policyDelta to see exactly which binding was added and to whom
GenerateAccessToken / SignJwt Lateral Movement Service account impersonation. Legitimate in many pipelines, so baseline the normal chains and alert on new combinations
DeleteSink / UpdateSink Evasion Stops log delivery to your SIEM. The Google Cloud equivalent of StopLogging and equally urgent
storage.setIamPolicy Exfiltration Granting allUsers on a bucket exposes it publicly. The mechanism behind most Google Cloud data exposure incidents
CreateServiceAccount Persistence New service accounts created outside the provisioning pipeline are attacker infrastructure
compute.instances.setMetadata Execution Adding an SSH key or startup script to a running instance gives code execution as root without touching the guest OS
bigquery.jobs.insert (extract) Exfiltration Exporting a dataset to a bucket the attacker controls copies an entire warehouse in one job
SetOrgPolicy Evasion Removing constraints such as the one forbidding service account key creation weakens guardrails across the whole organisation
cloudfunctions.functions.create Persistence A function with a privileged service account and an unauthenticated trigger is a durable backdoor reachable from the internet

Google Cloud Log Analysis Queries

These Logging query language and BigQuery statements cover the dominant Google Cloud attack paths.

Service Account Key Created
gcloud> gcloud logging read 'protoPayload.methodName="google.iam.admin.v1.CreateServiceAccountKey"' --organization=123456789012 --format="table(timestamp, protoPayload.authenticationInfo.principalEmail, protoPayload.resourceName, protoPayload.requestMetadata.callerIp)" --freshness=7d
Long-lived keys should be rare. Every one is a credential that never expires and works from any address on the internet.
Privileged Role Granted
SQL> SELECT timestamp, protopayload_auditlog.authenticationInfo.principalEmail AS actor, binding.role, member FROM cloud_audit.cloudaudit_googleapis_com_activity, UNNEST(protopayload_auditlog.servicedata_v1_iam.policyDelta.bindingDeltas) AS binding, UNNEST([binding.member]) AS member WHERE binding.action = 'ADD' AND binding.role IN ('roles/owner','roles/editor','roles/iam.securityAdmin','roles/iam.serviceAccountTokenCreator')
Unpacking bindingDeltas is what reveals the exact role and recipient. The role name alone in methodName is not enough.
Resource Made Public
gcloud> gcloud logging read 'protoPayload.methodName:"setIamPolicy" AND (protoPayload.serviceData.policyDelta.bindingDeltas.member="allUsers" OR protoPayload.serviceData.policyDelta.bindingDeltas.member="allAuthenticatedUsers")' --organization=123456789012 --freshness=30d
allUsers means the entire internet. This single query catches the mechanism behind most Google Cloud data exposure incidents.
Impersonation Chains
SQL> SELECT timestamp, protopayload_auditlog.authenticationInfo.principalEmail AS impersonated, delegate.principalEmail AS origin, protopayload_auditlog.methodName FROM cloud_audit.cloudaudit_googleapis_com_activity, UNNEST(protopayload_auditlog.authenticationInfo.serviceAccountDelegationInfo) AS d, UNNEST([d.firstPartyPrincipal]) AS delegate WHERE delegate.principalEmail IS NOT NULL
Reveals the human or key behind an impersonated service account. Without this join, attacker activity is attributed to legitimate automation.
Logging Tampering
gcloud> gcloud logging read 'protoPayload.methodName=("google.logging.v2.ConfigServiceV2.DeleteSink" OR "google.logging.v2.ConfigServiceV2.UpdateSink" OR "google.logging.v2.ConfigServiceV2.UpdateBucket")' --organization=123456789012 --freshness=30d
Sink deletion stops delivery to your SIEM while logs keep accumulating unwatched in the platform bucket. Page on this.
Permission Enumeration
SQL> SELECT protopayload_auditlog.authenticationInfo.principalEmail AS actor, protopayload_auditlog.requestMetadata.callerIp AS ip, COUNT(*) AS denials, COUNT(DISTINCT protopayload_auditlog.serviceName) AS services FROM cloud_audit.cloudaudit_googleapis_com_activity WHERE protopayload_auditlog.status.code = 7 GROUP BY 1,2 HAVING denials > 25
Status code 7 is PERMISSION_DENIED. Many denials across many services is an attacker mapping what a stolen identity can reach.
Instance Metadata Modified
gcloud> gcloud logging read 'protoPayload.methodName="v1.compute.instances.setMetadata" OR protoPayload.methodName="v1.compute.projects.setCommonInstanceMetadata"' --organization=123456789012 --freshness=7d
Adding an SSH key or startup script through metadata grants root on the instance without ever touching the guest operating system.
BigQuery Data Extraction
SQL> SELECT timestamp, protopayload_auditlog.authenticationInfo.principalEmail, protopayload_auditlog.servicedata_v1_bigquery.jobCompletedEvent.job.jobConfiguration.extract FROM cloud_audit.cloudaudit_googleapis_com_data_access WHERE protopayload_auditlog.servicedata_v1_bigquery.jobCompletedEvent.job.jobConfiguration.extract IS NOT NULL
Extract jobs write dataset contents to Cloud Storage. Check whether the destination bucket belongs to your organisation at all.
Verify Audit Config Coverage
gcloud> gcloud organizations get-iam-policy 123456789012 --format="json(auditConfigs)"
Run this as a scheduled control check. An empty result means Data Access logging is off everywhere and you cannot prove what was read.
Outbound Volume from Flow Logs
SQL> SELECT jsonPayload.connection.src_ip, jsonPayload.connection.dest_ip, SUM(CAST(jsonPayload.bytes_sent AS INT64))/1073741824 AS gb FROM vpc_flows.compute_googleapis_com_vpc_flows WHERE jsonPayload.reporter = 'SRC' GROUP BY 1,2 HAVING gb > 10 ORDER BY gb DESC
Finds instances shipping large volumes outbound, catching exfiltration that never involves a storage API call.

Best Practices for Google Cloud Logging

Apply these practices so Google Cloud logs stay complete, durable, and attributable:

01

Enable Data Access Logs at Organisation Level

They are off by default everywhere except BigQuery. Setting them once on the organisation policy covers every current and future project rather than leaving each one to be configured individually.

02

Use an Aggregated Sink with include-children

Project-level sinks leave every newly created project unmonitored. An organisation-level aggregated sink captures projects that do not exist yet.

03

Extend _Default Bucket Retention

Thirty days is shorter than typical time to detection. Raise it or route to BigQuery, otherwise Data Access logs expire before anyone thinks to look at them.

04

Always Resolve Impersonation Chains

Read serviceAccountDelegationInfo alongside principalEmail. Without it every impersonated action is attributed to the service account rather than the identity that initiated it.

05

Alert on Sink Deletion

Admin Activity logs cannot be disabled, but their delivery to you can be. Sink tampering is the Google Cloud equivalent of stopping CloudTrail and deserves the same response.

06

Ban Service Account Keys by Policy

Apply the constraints/iam.disableServiceAccountKeyCreation organisation policy and use workload identity federation instead. This removes the most common persistence mechanism outright.

07

Raise Flow Log Sampling on Sensitive Subnets

The default samples half of all flows. A sampled log can never prove a connection did not occur, which matters when the question is whether data left.

08

Lock the Archive Bucket

Cloud Storage Bucket Lock makes retention irreversible. Once applied, no principal at any level can shorten it, which is what makes the archive genuinely tamper-proof.

Common Google Cloud Log Examples

A Google Cloud intrusion from compromised pipeline credential to exported dataset.

Compromised Service Account Enumerating Permissions

timestamp: 2025-07-14T09:41:22.481Z protoPayload.methodName: google.iam.admin.v1.ListServiceAccounts protoPayload.authenticationInfo.principalEmail: svc-deploy@htl-prod.iam.gserviceaccount.com protoPayload.requestMetadata.callerIp: 203.0.113.44 protoPayload.requestMetadata.callerSuppliedUserAgent: google-cloud-sdk gcloud/470.0.0 linux/6.1.0 protoPayload.status.code: 7 protoPayload.status.message: PERMISSION_DENIED logName: projects/htl-prod/logs/cloudaudit.googleapis.com%2Factivity
A deployment service account calling from an external address with the gcloud CLI rather than its usual CI user agent. Status 7 shows the call was denied, but the attempt itself reveals the enumeration.

Impersonation Chain in Action

timestamp: 2025-07-14T09:47:33.221Z protoPayload.methodName: google.iam.credentials.v1.GenerateAccessToken protoPayload.authenticationInfo.principalEmail: svc-admin@htl-prod.iam.gserviceaccount.com protoPayload.authenticationInfo.serviceAccountDelegationInfo: [ { firstPartyPrincipal: { principalEmail: "svc-deploy@htl-prod.iam.gserviceaccount.com" } } ] protoPayload.resourceName: projects/-/serviceAccounts/svc-admin@htl-prod.iam.gserviceaccount.com protoPayload.requestMetadata.callerIp: 203.0.113.44
principalEmail shows svc-admin, but the delegation info reveals svc-deploy initiated it. Every subsequent action will appear to come from svc-admin unless you follow this chain.

Privilege Escalation via SetIamPolicy

timestamp: 2025-07-14T09:52:10.774Z protoPayload.methodName: SetIamPolicy protoPayload.authenticationInfo.principalEmail: svc-admin@htl-prod.iam.gserviceaccount.com protoPayload.resourceName: projects/htl-prod protoPayload.serviceData.policyDelta.bindingDeltas: [ { action: "ADD", role: "roles/owner", member: "serviceAccount:svc-deploy@htl-prod.iam.gserviceaccount.com" } ] protoPayload.authorizationInfo: [ { permission: "resourcemanager.projects.setIamPolicy", granted: true } ]
The impersonated admin account grants roles/owner back to the originally compromised account. The bindingDeltas array is what makes the exact change visible.

Persistence: Long-Lived Service Account Key

timestamp: 2025-07-14T09:55:41.118Z protoPayload.methodName: google.iam.admin.v1.CreateServiceAccountKey protoPayload.authenticationInfo.principalEmail: svc-deploy@htl-prod.iam.gserviceaccount.com protoPayload.resourceName: projects/htl-prod/serviceAccounts/svc-admin@htl-prod.iam.gserviceaccount.com protoPayload.response.name: projects/htl-prod/serviceAccounts/svc-admin@.../keys/8f2a1c04e91b7d2 protoPayload.response.validAfterTime: 2025-07-14T09:55:41Z protoPayload.response.validBeforeTime: 9999-12-31T23:59:59Z
The validBeforeTime of year 9999 is the point: this credential never expires, works from any address, and is unaffected by session or password policy.

Bucket Exposed to the Internet

timestamp: 2025-07-14T10:02:44.229Z protoPayload.methodName: storage.setIamPermissions protoPayload.authenticationInfo.principalEmail: svc-deploy@htl-prod.iam.gserviceaccount.com protoPayload.resourceName: projects/_/buckets/htl-customer-data protoPayload.serviceData.policyDelta.bindingDeltas: [ { action: "ADD", role: "roles/storage.objectViewer", member: "allUsers" } ]
allUsers grants read access to every anonymous caller on the internet. One API call, and the bucket is public.

Data Exfiltration via BigQuery Extract

timestamp: 2025-07-14T10:11:03.441Z protoPayload.methodName: jobservice.jobcompleted protoPayload.authenticationInfo.principalEmail: svc-admin@htl-prod.iam.gserviceaccount.com protoPayload.serviceData.jobCompletedEvent.job.jobConfiguration.extract: { sourceTable: { datasetId: "customers", tableId: "pii_master" }, destinationUris: [ "gs://exfil-staging-9f2a/customers-*.csv" ], destinationFormat: "CSV" } protoPayload.serviceData.jobCompletedEvent.job.jobStatistics.totalProcessedBytes: 41882219043
A 41 GB extract of a table named pii_master written to a bucket outside the organisation. This appears only in Data Access logs, so an environment without them sees nothing at all.

Code Execution via Instance Metadata

timestamp: 2025-07-14T10:14:22.008Z protoPayload.methodName: v1.compute.instances.setMetadata protoPayload.authenticationInfo.principalEmail: svc-deploy@htl-prod.iam.gserviceaccount.com protoPayload.resourceName: projects/htl-prod/zones/me-central1-a/instances/prod-app-04 protoPayload.request.metadata.items: [ { key: "ssh-keys", value: "attacker:ssh-rsa AAAAB3NzaC1yc2EAAA... attacker@kali" } ]
An SSH key injected through the metadata service. The guest operating system logs will show a successful key-based login with no preceding failed attempts, because the key was placed by the control plane.

Logging Evasion: Sink Deleted

timestamp: 2025-07-14T10:18:12.774Z protoPayload.methodName: google.logging.v2.ConfigServiceV2.DeleteSink protoPayload.authenticationInfo.principalEmail: svc-deploy@htl-prod.iam.gserviceaccount.com protoPayload.resourceName: projects/htl-prod/sinks/htl-org-security-sink protoPayload.requestMetadata.callerIp: 203.0.113.44 protoPayload.authorizationInfo: [ { permission: "logging.sinks.delete", granted: true } ]
The sink is gone, so nothing further reaches the SIEM. Admin Activity logs keep accumulating in the _Required bucket, which is why this record still exists and why that bucket matters.

Policy Denied: Attacker Blocked by VPC Service Controls

timestamp: 2025-07-14T10:22:04.118Z protoPayload.methodName: storage.objects.get protoPayload.authenticationInfo.principalEmail: svc-admin@htl-prod.iam.gserviceaccount.com protoPayload.requestMetadata.callerIp: 203.0.113.44 protoPayload.status.code: 7 protoPayload.status.details: [ { violations: [ { type: "VPC_SERVICE_CONTROLS", description: "Request is prohibited by organization's policy" } ] } ] logName: projects/htl-prod/logs/cloudaudit.googleapis.com%2Fpolicy
The perimeter held. Policy Denied logs are billed and therefore sometimes filtered out, yet they are among the clearest evidence of an attacker probing a boundary and being stopped.
