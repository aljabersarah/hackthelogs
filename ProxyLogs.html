Proxy Logs

Proxy Log Overview

A web proxy sits between users and the internet, and because every outbound request passes through it, the access log becomes the most detailed record of user and malware behaviour available on the network. Where a firewall log records that a host contacted an address on port 443, the proxy log records the full URL, the authenticated username, the site category, the user agent, the referrer, the exact byte counts in each direction, and whether the request was allowed or blocked. That difference in richness is why proxy logs are usually the first place an analyst looks when investigating a suspected compromise.

The dominant deployments are Squid in open source environments, Zscaler and Netskope as cloud-delivered secure web gateways, and Symantec Blue Coat ProxySG in traditional enterprises. They differ in format but log the same fundamental transaction. Squid writes a compact native format by default that omits the user agent and referrer entirely, which is a significant gap: the combined log format must be configured explicitly to capture them, and without them a large fraction of proxy-based detection simply does not work.

The critical architectural question is whether the proxy performs TLS inspection. Without it, an HTTPS request appears only as a CONNECT to a hostname and port, with byte counts but no URL path, no response content, and no file visibility. With inspection enabled the proxy sees the full request as if it were cleartext. Most organisations run a hybrid, inspecting general browsing while bypassing banking, healthcare, and government categories for privacy and legal reasons. Knowing which categories are bypassed is essential context, because those are precisely the categories attackers prefer to hide behind.

Key Proxy Log Types

Proxies produce several streams. Only the first carries most of the security value, but the others matter during troubleshooting and incident response:

Log Type Description
Access Log One record per client request. Contains the timestamp, client address, authenticated user, request method, full URL, HTTP status, bytes transferred, result code, content type, and the policy decision. This is the primary security log and the one that should always be forwarded to a SIEM.
Policy and Block Log Records requests denied by category filtering, threat intelligence, or acceptable use policy, with the rule that caused the denial. On Squid these appear in the access log as TCP_DENIED, while commercial gateways often separate them into their own stream.
TLS Inspection Log Details of intercepted HTTPS sessions including the server certificate subject and issuer, negotiated cipher, SNI value, and any validation failures. Certificate errors logged here frequently reveal command and control infrastructure using self-signed certificates.
Cache Log The proxy's own operational log covering startup, configuration reload, upstream failures, and errors. Squid writes this to cache.log. Not a security source, but it explains gaps in the access log.
Malware Scanning Log Verdicts from inline antivirus or sandbox detonation performed on downloaded content, typically including the file hash, name, and detection name. The link between a web request and a delivered payload.
Authentication Log Records how each session was attributed to a user, whether by Kerberos, NTLM, or captive portal. Authentication failures here can indicate credential problems or attempts to evade user attribution.
Store Log Squid-specific record of objects entering and leaving the cache. Rarely enabled and of limited security value, but occasionally useful for proving what content was served from cache rather than fetched fresh.
Pro Tip: Squid's default squid log format contains no user agent and no referrer. Switch to the combined format or define a custom logformat before you need those fields, because they cannot be recovered retrospectively.

Log File Locations

Cloud proxies deliver logs through a streaming connector rather than a file, which changes how collection is architected.

Log Default Location

Blue Coat ProxySG Uploaded by FTP or HTTP to a configured server, commonly in the bcreportermain_v1 or W3C ELFF format

Pro Tip: Cloud proxy feeds are delivered from the vendor's infrastructure, not from your network. If the streaming connector stops, log flow ends silently while browsing continues to work normally. Monitor event volume per hour and alert when it drops.

Configuring Proxy Logging

These Squid directives produce an access log with the fields security analysis actually requires, rather than the sparse default.

Step 1: Define a Security-Focused Log Format

# /etc/squid/squid.conf logformat htlsec %ts.%03tu %6tr %>a %Ss/%03>Hs %<st %rm %ru %[un %Sh/%<a %mt "%{Referer}>h" "%{User-Agent}>h" %>st %<st access_log /var/log/squid/access.log htlsec # Field reference: # %ts.%03tu epoch seconds and milliseconds %rm request method # %6tr response time in milliseconds %ru full request URL # %>a client address %[un authenticated username # %Ss/%03>Hs squid result code / HTTP status %Sh hierarchy code # %<st bytes delivered to client %mt MIME content type # %>st bytes received from client
Logging both %>st and %<st is what makes upload detection possible. The default format records only the response size, so large outbound POSTs are invisible.

Step 2: Log Human Readable Timestamps

# Squid logs epoch time by default, which is unreadable during triage logformat htlsec_iso %{%Y-%m-%dT%H:%M:%S%z}tl %6tr %>a %Ss/%03>Hs %<st %rm %ru %[un %Sh/%<a %mt # Or convert an existing log on the fly perl -pe 's/^(\d+)\.\d+/localtime($1)/e' /var/log/squid/access.log | head
If your SIEM handles epoch parsing correctly, keep the native format for precision. If analysts read raw files, ISO timestamps save time on every investigation.

Step 3: Require Authentication for User Attribution

auth_param negotiate program /usr/lib/squid/negotiate_kerberos_auth -k /etc/squid/HTTP.keytab -s GSS_C_NO_NAME auth_param negotiate children 20 startup=5 idle=2 auth_param negotiate keep_alive on acl authenticated proxy_auth REQUIRED http_access deny !authenticated http_access allow authenticated
Without authentication the log attributes activity to an IP address only. On shared or DHCP-assigned addresses that makes user attribution guesswork rather than evidence.

Step 4: Enable TLS Inspection Selectively

http_port 3128 ssl-bump generate-host-certificates=on \ dynamic_cert_mem_cache_size=8MB tls-cert=/etc/squid/proxyCA.pem acl step1 at_step SslBump1 acl no_inspect ssl::server_name_regex "/etc/squid/bypass_domains.txt" ssl_bump peek step1 ssl_bump splice no_inspect # bypass banking, health, government ssl_bump bump all # inspect everything else
Spliced connections are logged as CONNECT with a hostname and byte counts only. Keep the bypass list short and reviewed, because every entry is a blind spot an attacker can use.

Step 5: Configure Rotation and Retention

logfile_rotate 30 debug_options ALL,1 # /etc/logrotate.d/squid /var/log/squid/*.log { daily rotate 90 compress delaycompress missingok postrotate /usr/sbin/squid -k rotate endscript }
The postrotate hook signalling Squid is essential. Rotating the file without it leaves Squid writing to a deleted inode, and logging stops silently until the service restarts.

Step 6: Forward to a SIEM in Real Time

# Squid can write directly to syslog access_log syslog:local4.info htlsec # /etc/rsyslog.d/49-squid.conf local4.* @@siem-collector.corp.local:6514
Streaming over TCP with TLS avoids the loss inherent in reading rotated files and ensures logs survive compromise of the proxy host itself.
Security Note: Full URL logging captures query strings, which routinely contain session tokens, password reset links, and personal data. Proxy logs inherit the sensitivity of everything your users browse. Restrict access to them accordingly and define a retention period that reflects that, not just storage cost.

Proxy Threat Patterns

Proxy logs expose a distinctive set of attacker behaviours. These are the patterns worth building detections around.

Command and Control Beaconing

Regular polling of a controller over HTTP or HTTPS. Signature: highly consistent intervals, small consistent response sizes, few distinct URLs, and a single internal client.
Detect Critical

Data Exfiltration

Large outbound transfers to file sharing services or unknown hosts. Signature: request bytes vastly exceeding response bytes, sustained POST or PUT activity, uncategorised destination.
Detect Critical

Non-Browser User Agents

Requests from curl, wget, python-requests, PowerShell, or empty user agent strings. On a user workstation these almost always indicate scripted activity rather than browsing.
Detect Critical

Uncategorised Destinations

Sites the categorisation engine does not recognise, which correlates strongly with newly registered attacker infrastructure. Low volume in most environments and therefore highly reviewable.
Detect High Risk

Direct IP Requests

URLs containing an address instead of a hostname. Legitimate browsing almost never does this, while malware frequently hardcodes addresses to avoid DNS-based blocking.
Detect High Risk

Suspicious Downloads

Executables, scripts, and archives fetched from uncategorised sites, or content whose MIME type contradicts its file extension. The delivery stage of most intrusions.
Detect Medium Risk
Security Note: Attackers increasingly host command and control on legitimate, well-categorised platforms such as cloud storage, code repositories, and collaboration tools. Category-based detection alone will not catch this. Behaviour, specifically timing regularity and byte ratios, remains effective where reputation fails.

Squid Result and Hierarchy Codes

Squid encodes both the cache outcome and the policy decision into a single result code. Reading it correctly is essential to interpreting the log.

Code Meaning Security Relevance
TCP_DENIED Request refused by an access control rule The policy block record. Repeated denials to one destination from one host indicate malware retrying against a blocked controller
TCP_MISS Object not cached, fetched from the origin The normal case for dynamic content and the majority of security-relevant traffic
TCP_HIT Served from cache without contacting the origin Confirms the client received content but the origin was never contacted for this request
TCP_TUNNEL CONNECT tunnel established, contents not inspected An uninspected HTTPS session. Byte counts are still recorded, which is often enough to spot exfiltration
TCP_REFRESH_MODIFIED Cached object revalidated and found changed Rapid repeated revalidation of one object can indicate polling behaviour
TCP_MISS_ABORTED Client disconnected before the transfer completed Common in interrupted downloads, but bursts can indicate scripted activity or a failing tunnel
HIER_DIRECT Fetched directly from the origin server The standard hierarchy code, showing no upstream parent proxy was involved
HIER_NONE No upstream connection was made Accompanies denials and cache hits. Confirms the request never left the network
NONE/503 Upstream unreachable or DNS failure Bursts of these to random hostnames can reveal domain generation algorithm activity reaching the proxy
Pro Tip: TCP_DENIED entries are a detection opportunity, not just a compliance record. Malware does not know a domain is blocked, so it retries. A host generating dozens of denials to the same uncategorised domain is infected regardless of the fact that the traffic was stopped.

Proxy Log Analysis Queries

These commands surface beaconing, exfiltration, scripted clients, and blocked malware retries from proxy logs.

Large Outbound Transfers
SIEM> source="proxy" method IN ("POST","PUT") | stats sum(bytes_sent) as uploaded, sum(bytes_received) as downloaded, dc(url) by client_ip, dest_host | where uploaded > 100000000 AND uploaded > downloaded*10
Finds hosts uploading far more than they download. The ratio matters more than the absolute volume for distinguishing exfiltration from normal use.
Scripted User Agents
bash> awk '{print $12}' /var/log/squid/access.log | grep -iE "curl|wget|python|powershell|go-http|libwww|^\"-\"$" | sort | uniq -c | sort -rn
Non-browser agents on a workstation are scripted activity. Baseline the legitimate ones from monitoring tools, then alert on everything else.
Beacon Detection
SIEM> source="proxy" | sort client_ip, dest_host, _time | streamstats current=f last(_time) as prev by client_ip, dest_host | eval gap=_time-prev | stats count, stdev(gap) as jitter, avg(gap) as interval, avg(bytes_received) as avg_size by client_ip, dest_host | where count > 30 AND jitter < 10
Consistent intervals with consistent small response sizes is machine behaviour. This finds command and control that no reputation feed has flagged.
Repeated Blocks (Infected Host)
bash> grep TCP_DENIED /var/log/squid/access.log | awk '{print $3, $7}' | sort | uniq -c | sort -rn | head -25
A host repeatedly hitting the same blocked destination is not a user browsing, it is malware retrying. The block worked, the infection remains.
Direct IP Requests
bash> grep -oP 'https?://\K(\d{1,3}\.){3}\d{1,3}[^ ]*' /var/log/squid/access.log | sort | uniq -c | sort -rn | head -20
Browsers use hostnames. URLs containing a raw address are typically hardcoded malware destinations designed to survive DNS blocking.
Uncategorised Destinations
SIEM> source="proxy" category IN ("Uncategorized","Unknown","Newly Registered Domain") | stats count, sum(bytes_sent) as up, dc(client_ip) as hosts by dest_host | where hosts <= 2 | sort - up
Uncategorised domains visited by only one or two hosts are the highest yield review queue on the proxy.
Executable and Script Downloads
bash> grep -iE "\.(exe|dll|ps1|hta|scr|jar|vbs|bat|iso|img)(\?|$| )" /var/log/squid/access.log | awk '$4 ~ /200/ {print $3, $7, $11}' | sort | uniq -c | sort -rn
Successful executable downloads, filtered to status 200. Cross-reference the destination against category and domain age.
Off-Hours Browsing
SIEM> source="proxy" | eval hr=strftime(_time,"%H") | where hr<6 OR hr>21 | stats count, dc(dest_host) as sites by username, client_ip | sort - count
Automated malware browses at 3am. Compare each user's off-hours volume against their own baseline rather than a global threshold.
Certificate Anomalies
SIEM> source="proxy" event="tls_inspection" (cert_validation="failed" OR cert_self_signed="true") | stats count, values(cert_subject) by dest_host, client_ip | sort - count
Self-signed and invalid certificates on outbound connections frequently mark command and control servers set up in a hurry.
Log Flow Health
SIEM> source="proxy" | timechart span=1h count | where count < 1000
Cloud proxy feeds fail silently while browsing continues. An unexplained volume drop means you have lost visibility, not that the network went quiet.

Best Practices for Proxy Logging

Follow these practices to get investigation-grade evidence out of a web proxy:

01

Log the User Agent and Referrer

Squid's default format omits both. They are among the most useful fields for detecting scripted clients and reconstructing how a user reached a malicious page, and they cannot be recovered later.

02

Record Bytes in Both Directions

Response size alone hides exfiltration completely. Logging request bytes as well is what turns the proxy into a data loss detection source.

03

Authenticate Every Session

An IP address is not an identity. Kerberos or NTLM attribution converts every proxy record into evidence tied to a named person.

04

Keep the TLS Bypass List Short

Every bypassed category is a blind spot. Review the list regularly and document the legal or privacy justification for each entry.

05

Retain Blocked Requests

Denied requests are frequently more valuable than allowed ones, because they identify infected hosts that policy successfully contained. Never filter TCP_DENIED out to save storage.

06

Signal Squid on Rotation

Rotating the access log without running squid -k rotate leaves the daemon writing to a deleted file. Logging stops silently and nothing alerts you.

07

Monitor Feed Continuity

Cloud gateway connectors fail without affecting user browsing. Alert on hourly event volume so a broken feed is detected in an hour rather than during an investigation.

08

Treat Proxy Logs as Sensitive Data

Full URLs contain session tokens, reset links, and personal browsing history. Apply access controls and a defined retention period that reflect that sensitivity.
