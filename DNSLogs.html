DNS Logs

DNS Log Overview

Almost every action on a network begins with a DNS lookup. Before malware reaches its command and control server, before a user lands on a phishing page, and before data leaves through a tunnel, something has to resolve a name. That property makes DNS the broadest single source of visibility available to a SOC: one log stream that observes nearly every host, every application, and every outbound connection attempt, including the ones that fail.

DNS produces two very different kinds of log. Query logging records the questions clients ask and the answers they receive, which is the security-relevant stream. Debug or diagnostic logging records protocol level detail intended for troubleshooting and is far too verbose to keep running. On Windows, the modern approach is the DNS Server Analytical log delivered through Event Tracing for Windows, which replaced the old text-based debug log and can sustain production query rates. On BIND, query logging is a channel configured in named.conf. On endpoints, Sysmon event ID 22 captures the resolving process, which is the one thing server-side DNS logs can never tell you.

The gap that matters most in modern environments is encrypted DNS. DNS over HTTPS and DNS over TLS move resolution off port 53 and out of the view of your internal resolver entirely, and every major browser now supports it. A host configured to use a public DoH resolver produces no useful DNS log at all. Blocking outbound port 53 to anything other than approved resolvers, disabling browser DoH through policy, and monitoring for connections to known DoH endpoints are prerequisites for DNS logging to remain meaningful.

Key DNS Log Types

DNS visibility can be collected at the server, at the endpoint, or on the wire. Each vantage point answers a different question, and a mature deployment uses more than one:

Log Type Description
Windows DNS Analytical Log An ETW-based channel introduced in Windows Server 2012 R2 that records every query, response, recursion, and dynamic update handled by the server. Designed for production use with roughly 5 percent overhead at 100,000 queries per second, and the correct replacement for the legacy debug log.
Windows DNS Audit Log Enabled by default on Windows Server 2012 R2 and later. Records administrative changes such as zone creation and deletion, record additions and removals, and configuration changes. This is the tamper-detection stream, distinct from query activity.
BIND Query Log Configured as a logging channel with the queries category in named.conf. Records the client address, query name, class, type, and flags for every request. The response is logged separately through the querylog and resolver categories.
Sysmon Event ID 22 DNSEvent, generated on the endpoint rather than the server. Uniquely records the process image that performed the lookup, which is the difference between knowing a host resolved a malicious domain and knowing which binary did it.
Passive DNS Resolution data captured from network traffic and stored historically, either by a sensor such as Zeek or by a commercial feed. Enables retrospective questions such as which internal hosts ever resolved a domain that has only now been identified as malicious.
Zeek dns.log Protocol-aware network monitoring output containing the query, response, record types, response code, and round-trip time for every DNS transaction observed on the wire. Independent of server configuration, so it captures lookups sent to unauthorised resolvers.
Windows DNS Debug Log The legacy text-based packet log configured through the DNS Manager console. Extremely verbose and a significant performance cost. Superseded by the analytical log and generally only appropriate for short troubleshooting windows.
Pro Tip: Server-side DNS logs attribute a query to an IP address, not to a process or a user. Pair them with Sysmon event 22 for process attribution and with DHCP leases for device attribution, otherwise an alert on a malicious domain leaves you with an address and no owner.

Log File Locations

DNS log destinations differ substantially between platforms, and on Windows the analytical channel is written as an ETL file rather than a normal event log.

Log Default Location
Windows Analytical Log %SystemRoot%\System32\Winevt\Logs\Microsoft-Windows-DNSServer%4Analytical.etl
Windows Audit Log %SystemRoot%\System32\Winevt\Logs\Microsoft-Windows-DNSServer%4Audit.evtx
Windows Debug Log %SystemRoot%\System32\dns\dns.log (path configurable in DNS Manager)
BIND Query Log /var/log/named/query.log or /var/named/data/named.run, set by the channel definition
BIND Configuration /etc/named.conf (RHEL) or /etc/bind/named.conf.options (Debian)
Zeek DNS Log /opt/zeek/logs/current/dns.log
Sysmon Event 22 Microsoft-Windows-Sysmon/Operational channel on each endpoint
dnsmasq /var/log/dnsmasq.log or the system journal when no log-facility is set
Pro Tip: The Windows analytical log is an ETL trace, not an EVTX file, so it cannot be opened directly in Event Viewer while the trace is running. Stop the channel first, or read it with Get-WinEvent -Path ... -Oldest, which handles ETL correctly.

Enabling DNS Logging

Query logging is disabled by default on every major DNS platform because of its volume. These are the correct commands to turn it on in a way production can sustain.

Step 1: Enable the Windows DNS Analytical Log

# Confirm the channel exists and check its current state Get-WinEvent -ListLog "Microsoft-Windows-DNSServer/Analytical" | Format-List * # Enable it with a bounded file size $log = New-Object System.Diagnostics.Eventing.Reader.EventLogConfiguration ` "Microsoft-Windows-DNSServer/Analytical" $log.LogFilePath = "C:\DNSLogs\Analytical.etl" $log.MaximumSizeInBytes = 2GB $log.IsEnabled = $true $log.SaveChanges()
The analytical channel must be disabled before its properties can be changed. Setting IsEnabled last is what actually starts the trace.

Step 2: Verify Windows DNS Audit Logging

# Audit logging is on by default, but confirm it Get-WinEvent -ListLog "Microsoft-Windows-DNSServer/Audit" | Select-Object LogName, IsEnabled, MaximumSizeInBytes, LogMode # Raise retention so a busy server does not overwrite weeks of changes wevtutil sl "Microsoft-Windows-DNSServer/Audit" /ms:1073741824 /rt:false
The audit channel records zone and record modifications. Because it is low volume and high value, it should be sized generously and forwarded without filtering.

Step 3: Configure BIND Query Logging

// /etc/named.conf logging { channel query_channel { file "/var/log/named/query.log" versions 30 size 500m; severity info; print-time yes; print-category yes; print-severity yes; }; category queries { query_channel; }; category query-errors { query_channel; }; category security { query_channel; }; category client { query_channel; }; };
The versions and size arguments give BIND its own rotation, retaining 30 files of 500 MB. Without them the log grows until the filesystem fills.

Step 4: Toggle BIND Query Logging at Runtime

# Turn query logging on or off without restarting named rndc querylog on rndc querylog off # Check the current state rndc status | grep -i querylog
rndc querylog is a runtime toggle, useful for enabling full query capture during an investigation without a service restart or configuration change.

Step 5: Enable Sysmon DNS Logging on Endpoints

<Sysmon schemaversion="4.90"> <EventFiltering> <RuleGroup name="DNS" groupRelation="or"> <DnsQuery onmatch="exclude"> <!-- Exclude high volume, low value internal noise --> <QueryName condition="end with">.corp.local</QueryName> <QueryName condition="end with">.in-addr.arpa</QueryName> <Image condition="is">C:\Windows\System32\svchost.exe</Image> </DnsQuery> </RuleGroup> </EventFiltering> </Sysmon>
Sysmon event 22 is the only DNS source that names the resolving process. Use exclude rules rather than include rules so that unexpected lookups are captured by default.

Step 6: Close the Encrypted DNS Bypass

# Block outbound DNS to anything except approved resolvers (firewall policy) deny udp any any eq 53 unless dst in {10.10.0.10, 10.10.0.11} deny tcp any any eq 853 # DNS over TLS # Disable DoH in Microsoft Edge and Chrome via Group Policy HKLM\Software\Policies\Microsoft\Edge\DnsOverHttpsMode = "off" HKLM\Software\Policies\Google\Chrome\DnsOverHttpsMode = "off"
Without these controls a single browser setting removes a host from DNS monitoring entirely, and the absence of logs looks identical to a quiet endpoint.
Security Note: Never enable the legacy Windows DNS debug log on a busy domain controller as a monitoring solution. It writes synchronously to a text file and has been documented to cause noticeable query latency. The analytical channel exists specifically to solve this problem.

DNS Threat Patterns

DNS abuse follows a small number of recognisable shapes. Each has a distinct statistical signature, which is what makes DNS such a productive detection surface.

DNS Tunnelling

Data encoded into subdomain labels and carried out through TXT or NULL records. Signature: very long query names, high entropy, huge query volume to one parent domain, and TXT records dominating.
Detect Critical

Domain Generation Algorithms

Malware algorithmically generates candidate domains until one resolves. Signature: a burst of NXDOMAIN responses for random-looking names from a single host, followed by one successful resolution.
Detect Critical

Command and Control Beaconing

Regular check-in intervals to a controller. Signature: highly consistent timing between lookups of the same domain, often with very low TTL values and few distinct clients.
Detect Critical

Newly Registered Domains

Phishing and malware infrastructure is typically used within days of registration. Any lookup of a domain registered in the last 30 days is disproportionately likely to be malicious.
Detect High Risk

Fast Flux

A single domain rotating rapidly through many IP addresses to resist takedown. Signature: very low TTL combined with a high count of distinct answers over a short window.
Detect High Risk

Resolver Bypass

Hosts querying external resolvers directly, or using DoH and DoT. Signature: outbound port 53 or 853 to non-approved addresses, or TLS connections to known DoH providers.
Detect High Risk
Security Note: A sudden drop in DNS log volume from a host is itself a detection. It usually means the host has switched to an external or encrypted resolver, which is exactly what an attacker wants before starting command and control traffic.

Record Types and Response Codes

Certain record types and response codes carry far more security weight than their share of traffic would suggest.

Type / Code Meaning Why It Matters
TXT Arbitrary text record The preferred carrier for DNS tunnelling and for staged payload delivery, because it holds arbitrary data. Normal TXT volume is low, so spikes stand out
NULL Undefined record type Almost never used legitimately. Its presence is a strong tunnelling indicator, notably used by Iodine
CNAME Canonical name alias Long CNAME chains are used for tunnelling and for cloaking the true destination of phishing infrastructure
ANY Request for all records Deprecated for normal use. Appears in reconnaissance and in DNS amplification reflection attacks
AXFR Full zone transfer An unauthorised AXFR hands an attacker a complete map of internal hostnames and addresses in one request
NXDOMAIN Name does not exist Bursts of NXDOMAIN from one host is the defining signature of domain generation algorithm malware searching for its controller
SERVFAIL Server failure Can indicate DNSSEC validation failure, which may mean tampering, or a poorly configured attacker-controlled zone
REFUSED Server refused to answer Frequently the response to an attempted zone transfer or to recursion requested by an unauthorised client
SRV Service location record Queries for _ldap._tcp and _kerberos._tcp are how an attacker locates domain controllers immediately after landing on a network
Pro Tip: Baseline your normal NXDOMAIN rate per host before alerting on it. Misconfigured applications and search-domain suffixes generate steady background NXDOMAIN traffic, so a static threshold produces constant false positives while a per-host deviation does not.

DNS Log Analysis Queries

These queries surface tunnelling, algorithmic domains, beaconing, and resolver bypass from DNS logs in a SIEM or directly on disk.

Long Query Names (Tunnelling)
SIEM> source="dns" | eval qlen=len(query_name) | where qlen > 100 | stats count, avg(qlen) as avg_len, dc(query_name) as unique by client_ip, parent_domain | sort - count
Normal DNS names are short. Sustained queries over 100 characters to one parent domain is tunnelling until proven otherwise.
NXDOMAIN Burst (DGA)
SIEM> source="dns" response_code="NXDOMAIN" | bucket _time span=5m | stats dc(query_name) as failed_domains by client_ip, _time | where failed_domains > 50
Fifty or more distinct failed lookups in five minutes from one host is the classic domain generation algorithm pattern.
Excessive TXT Queries
SIEM> source="dns" query_type IN ("TXT","NULL") | stats count by client_ip, parent_domain | where count > 100 | sort - count
TXT is normally a trickle used for SPF and domain verification. High volume to a single domain is data transfer, not lookups.
Beacon Interval Detection
SIEM> source="dns" | sort client_ip, query_name, _time | streamstats current=f last(_time) as prev by client_ip, query_name | eval gap=_time-prev | stats count, stdev(gap) as jitter, avg(gap) as interval by client_ip, query_name | where count > 20 AND jitter < 5
Very low jitter across many lookups means a machine, not a human. This is the single most reliable beacon detection available from DNS.
Fast Flux and Low TTL
SIEM> source="dns" ttl<120 | stats dc(answers) as distinct_ips, values(answers) by query_name | where distinct_ips > 10
A domain resolving to more than ten addresses with a TTL under two minutes is either a large CDN or fast flux infrastructure. Whitelist the former.
Zone Transfer Attempts
bash> grep -iE "AXFR|IXFR" /var/log/named/query.log | grep -v "10.10.0.1[01]" | awk '{print $6, $8}' | sort | uniq -c | sort -rn
Any zone transfer request from an address other than your authorised secondaries is reconnaissance against your internal namespace.
Resolver Bypass
SIEM> source="firewall" dest_port IN (53,853) NOT dest_ip IN ("10.10.0.10","10.10.0.11") action="allowed" | stats count by src_ip, dest_ip, dest_port
Detects hosts talking DNS directly to the internet, bypassing your logging and filtering entirely.
Read the Windows Analytical Log
PS> Get-WinEvent -Path "C:\DNSLogs\Analytical.etl" -Oldest | Where-Object { $_.Id -eq 257 } | Select-Object TimeCreated, @{n='Query';e={$_.Properties[6].Value}}, @{n='Client';e={$_.Properties[1].Value}} | Select-Object -First 50
Event ID 257 is RESPONSE_SUCCESS in the analytical channel. The -Oldest switch is mandatory when reading ETL files.
Process Attribution via Sysmon
SIEM> source="WinEventLog:Microsoft-Windows-Sysmon/Operational" EventCode=22 | stats dc(QueryName) as domains by Image, Computer | where NOT Image IN ("*\chrome.exe","*\msedge.exe","*\svchost.exe") | sort - domains
Reveals which binaries resolve names. A process in a user profile or temp directory performing many lookups is malware.
Domain Controller Discovery
SIEM> source="dns" query_type="SRV" query_name IN ("_ldap._tcp*","_kerberos._tcp*","_gc._tcp*") | stats count by client_ip | sort - count
Domain-joined machines do this at boot. A non-domain host or a server that never normally does it is performing Active Directory reconnaissance.

Best Practices for DNS Logging

Apply these practices to turn DNS from a high volume nuisance into the most productive detection source you have:

01

Log at the Internal Resolver

Collect on the server your clients actually query, not at the forwarder. Once queries leave your recursive resolver they are aggregated and the originating client address is lost forever.

02

Force All DNS Through Approved Resolvers

Block outbound port 53 and 853 at the perimeter except from your resolvers, and disable browser DoH by policy. Logging is worthless if a host can simply opt out of it.

03

Use the Analytical Channel on Windows

The legacy debug log writes synchronously to text and measurably slows a domain controller. The ETW analytical channel was built for production query rates and is the supported approach.

04

Add Process Attribution

Deploy Sysmon event 22 alongside server logging. Knowing that a host resolved a malicious domain is useful, knowing which executable did it turns an alert into an investigation.

05

Enrich with Domain Age and Reputation

Join lookups against newly registered domain feeds and threat intelligence at ingest. Domain age alone is one of the strongest single predictors of maliciousness available.

06

Filter at Collection, Not at Detection

Exclude reverse lookups, internal zones, and known-good telemetry domains before they reach the SIEM. DNS volume is the main reason teams abandon DNS logging, and most of it carries no signal.

07

Retain Long Enough to Look Backwards

Threat intelligence arrives after the fact. Ninety days of DNS history lets you answer which hosts contacted a domain that was only identified as malicious last week.

08

Alert on Missing Logs

Monitor query volume per host. A machine that stops producing DNS logs has usually switched resolvers or been taken off the corporate path, and both warrant investigation.

Common DNS Log Examples

The same intrusion viewed through BIND, Windows, Sysmon, and Zeek, showing what each source contributes.

BIND Query Log: Normal Activity

14-Jul-2025 09:38:02.117 queries: info: client @0x7f2a1c0 10.30.2.61#51422 (portal.corp.local): query: portal.corp.local IN A + (10.10.0.10) 14-Jul-2025 09:38:02.119 queries: info: client @0x7f2a1c0 10.30.2.61#51423 (www.example.com): query: www.example.com IN A +E(0) (10.10.0.10)
A baseline query pair. The plus sign indicates recursion desired, and the trailing address in parentheses is the resolver interface that answered.

DNS Tunnelling via TXT Records

14-Jul-2025 09:41:22.481 queries: info: client 10.30.2.61#52144 (a7f3c19e4b2d8f01.tunnel.example.com): query: a7f3c19e4b2d8f01.tunnel.example.com IN TXT + (10.10.0.10) 14-Jul-2025 09:41:22.902 queries: info: client 10.30.2.61#52145 (b8e4d20af5c391a2.tunnel.example.com): query: b8e4d20af5c391a2.tunnel.example.com IN TXT + (10.10.0.10) 14-Jul-2025 09:41:23.334 queries: info: client 10.30.2.61#52146 (c9f5e31bg6d4a2b3.tunnel.example.com): query: c9f5e31bg6d4a2b3.tunnel.example.com IN TXT + (10.10.0.10)
Hex-like subdomains of constant length, all TXT, all to one parent domain, hundreds of milliseconds apart. This is encoded data leaving the network, not name resolution.

Domain Generation Algorithm Activity

14-Jul-2025 09:44:07.229 queries: info: client 10.30.2.61#52190 (kjhsdfuiwer.biz): query: kjhsdfuiwer.biz IN A + (10.10.0.10) 14-Jul-2025 09:44:07.244 query-errors: info: client 10.30.2.61#52190: query failed (NXDOMAIN) for kjhsdfuiwer.biz/IN/A 14-Jul-2025 09:44:07.301 queries: info: client 10.30.2.61#52191 (pqwoeirutyx.info): query: pqwoeirutyx.info IN A + (10.10.0.10) 14-Jul-2025 09:44:07.318 query-errors: info: client 10.30.2.61#52191: query failed (NXDOMAIN) for pqwoeirutyx.info/IN/A 14-Jul-2025 09:44:09.882 queries: info: client 10.30.2.61#52204 (zmxncbvlkjh.top): query: zmxncbvlkjh.top IN A + (10.10.0.10)
Consonant-heavy random names across cheap TLDs, resolved milliseconds apart, nearly all returning NXDOMAIN. The one that eventually resolves is the live controller.

Windows Analytical Log: Query Received

Log Name: Microsoft-Windows-DNSServer/Analytical Source: Microsoft-Windows-DNSServer Event ID: 257 Task Category: RESPONSE_SUCCESS Description: TCP=0; InterfaceIP=10.10.0.10; Destination=10.30.2.61; AA=0; AD=0; QNAME=tunnel.example.com; QTYPE=16; XID=45182; DNSSEC=0; RCODE=0; Port=52144; Flags=33152
QTYPE 16 is TXT and RCODE 0 is NOERROR, so this tunnelling query succeeded. Event 258 would indicate a failure and 259 a dropped query.

Sysmon Event 22: Process Attribution

EventID: 22 UtcTime: 2025-07-14 09:41:22.481 ProcessGuid: {a1b2c3d4-1122-6874-0000-0010f4e21b00} ProcessId: 7412 QueryName: a7f3c19e4b2d8f01.tunnel.example.com QueryStatus: 0 QueryResults: type: 16 dnstunnel-payload-response; Image: C:\Users\Public\Libraries\update_svc.exe User: CORP\r.almutairi
This is the record the server-side log cannot produce. An unsigned binary in a public library folder is performing the tunnelling, and it is running as a named user.

Attempted Zone Transfer

14-Jul-2025 09:52:10.774 security: info: client 198.51.100.203#44120: zone transfer 'corp.local/AXFR/IN' denied 14-Jul-2025 09:52:11.008 security: info: client 198.51.100.203#44121: zone transfer 'corp.local/IXFR/IN' denied
An external address attempting both a full and an incremental zone transfer. Denied here, but a successful AXFR would have handed over every internal hostname and address.

Zeek dns.log: Fast Flux Infrastructure

#fields ts uid id.orig_h id.resp_h query qtype_name rcode_name answers TTLs 1752486721.883 CxT1 10.30.2.61 10.10.0.10 cdn-node.badinfra.top A NOERROR 203.0.113.44,198.51.100.7,203.0.113.91 60,60,60 1752486781.114 CxT2 10.30.2.61 10.10.0.10 cdn-node.badinfra.top A NOERROR 192.0.2.55,203.0.113.12,198.51.100.44 60,60,60
The same name returning a completely different address set sixty seconds later, with a sixty second TTL. Legitimate CDNs return stable pools, this does not.

DNS Audit Log: Record Tampering

Log Name: Microsoft-Windows-DNSServer/Audit Event ID: 516 Task Category: RECORD_DELETE Description: A record was deleted from zone corp.local. Zone=corp.local; Node=fileserver01; Type=1 (A); RDATA=10.20.5.40; User=CORP\svc_backup; ClientIP=10.30.2.61
Event 515 is record creation and 516 is deletion. A service account deleting or repointing an A record for a file server is a redirection attack, sending clients to an attacker-controlled host.
