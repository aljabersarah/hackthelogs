MongoDB Logs

MongoDB Log Overview

Since version 4.4 MongoDB writes its diagnostic log as structured JSON rather than free text, which makes it one of the easiest database logs to ingest into a SIEM without custom parsing. Every line is a complete JSON object carrying a timestamp, severity, component, connection context, and message. The mongod log records startup configuration, connection accept and end events, authentication successes and failures, replication state changes, index builds, and any operation exceeding the slow operation threshold.

What the diagnostic log does not provide is auditing. Recording who read which collection, who created a user, or who granted a role requires the separate audit log, available in MongoDB Enterprise, Percona Server for MongoDB, and Atlas. The audit log is configured independently, writes to its own destination, and supports a filter expression so you can capture authentication and authorisation events without recording every CRUD operation on a high-traffic cluster. The third source, the database profiler, writes operation detail into a capped system.profile collection per database, useful for targeted investigation but not a durable audit trail, since it lives inside the database an attacker controls.

MongoDB deserves particular attention because of its exposure history. Tens of thousands of instances have been compromised through the same pattern: a deployment bound to 0.0.0.0 with authorisation disabled, discovered by internet-wide scanning, then emptied and replaced with a ransom note. That entire attack is visible in the diagnostic log (connections from unfamiliar addresses, no authentication events, then dropDatabase commands), but only if the log is being read. Enabling authorisation, binding to a private interface, and forwarding the JSON log off the host addresses the overwhelming majority of real-world MongoDB incidents.

Key MongoDB Log Types

MongoDB separates diagnostics, auditing, and profiling into three independent mechanisms with very different durability and licensing:

Log Type Description
mongod Diagnostic Log The primary server log, written as structured JSON since MongoDB 4.4. Records startup options, connection accept and end, authentication results, replication events, index builds, and slow operations. Available in every edition and enabled by default.
Audit Log The dedicated security audit trail in MongoDB Enterprise, Percona Server for MongoDB, and Atlas. Records authentication, authorisation checks, user and role management, and optionally CRUD operations. Supports a filter expression and writes to file, syslog, or the console.
mongos Log In sharded clusters, the router process maintains its own log. Client connections terminate at mongos, so client source addresses appear there rather than on the shards. Collecting only shard logs loses the true client origin.
Database Profiler Writes operation detail including the full query shape, execution time, and originating client into the capped system.profile collection per database. Powerful for investigation but stored inside the database, so an attacker with write access can destroy it.
Oplog The capped replication log in local.oplog.rs containing every write applied to the data set. Not a security log, but it can reconstruct exactly what documents were inserted, updated, or deleted within its retention window.
FTDC Diagnostic Data Full Time Diagnostic Data Capture, a compressed binary metrics stream in the diagnostic.data directory. Primarily a support artifact, but valuable in forensics for establishing resource and connection patterns over time.
Pro Tip: On a sharded cluster always collect mongos logs. Operations forwarded to shards carry the mongos as their source, so shard logs alone will attribute every client action to your own routers.

Log File Locations

Paths follow the distribution packaging. When MongoDB is run in a container, logs go to stdout unless a path is configured explicitly.

Log Default Location
mongod Log (Linux) /var/log/mongodb/mongod.log
mongos Log /var/log/mongodb/mongos.log
Audit Log Defined by auditLog.path, commonly /var/log/mongodb/audit.json
Configuration File /etc/mongod.conf
Data Directory /var/lib/mongodb (Debian) or /var/lib/mongo (RHEL)
FTDC Data <dbPath>/diagnostic.data/
Windows C:\Program Files\MongoDB\Server\7.0\log\mongod.log
Container Deployments stdout by default; retrieve with docker logs or the orchestrator log driver
Pro Tip: Confirm the running configuration rather than reading the file on disk. db.adminCommand({getCmdLineOpts: 1}) shows the options the process actually started with, which is what matters if someone edited the config without restarting.

Configuring MongoDB Auditing

Diagnostic logging is configured in the systemLog section of mongod.conf; auditing lives in auditLog and requires an edition that supports it. Both take effect on restart.

Step 1: Configure the Diagnostic Log

systemLog: destination: file path: /var/log/mongodb/mongod.log logAppend: true # never truncate on restart logRotate: reopen # cooperate with logrotate timeStampFormat: iso8601-utc verbosity: 0 component: accessControl: verbosity: 1 # log authentication detail network: verbosity: 1 # log connection detail
logAppend is critical. Without it a restart overwrites the entire log file, and restarting the service is a trivial way for an attacker to destroy evidence.

Step 2: Enforce Authentication and Network Binding

security: authorization: enabled # the single most important setting net: bindIp: 127.0.0.1,10.40.1.15 # never 0.0.0.0 on an internet-reachable host port: 27017 tls: mode: requireTLS certificateKeyFile: /etc/ssl/mongodb.pem
Without authorization enabled, MongoDB grants every connection full administrative access and produces no authentication events at all. This is the root cause of nearly every mass MongoDB compromise.

Step 3: Enable the Audit Log

auditLog: destination: file format: JSON path: /var/log/mongodb/audit.json
Available in MongoDB Enterprise, Percona Server for MongoDB, and Atlas. Without a filter, every auditable action is recorded, which is appropriate to start with before tuning.

Step 4: Apply an Audit Filter for Security Events

auditLog: destination: file format: JSON path: /var/log/mongodb/audit.json filter: '{ "atype": { "$in": [ "authenticate", "authCheck", "createUser", "dropUser", "updateUser", "createRole", "dropRole", "updateRole", "grantRolesToUser", "revokeRolesFromUser", "grantPrivilegesToRole", "revokePrivilegesFromRole", "createCollection", "dropCollection", "dropDatabase", "shutdown", "replSetReconfig" ] } }'
Captures authentication, the complete user and role lifecycle, destructive DDL, and cluster reconfiguration (the security-relevant subset) while excluding routine CRUD volume.

Step 5: Audit Reads on Sensitive Collections Only

filter: '{ "$or": [ { "atype": { "$in": ["authenticate","createUser","grantRolesToUser","dropDatabase"] } }, { "atype": "authCheck", "param.command": { "$in": ["find","aggregate","count"] }, "param.ns": { "$in": ["hrdb.employees","paydb.cards"] } } ] }'
Combines instance-wide security auditing with read auditing scoped to two named namespaces. This is how you meet sensitive-data monitoring requirements without auditing every find on the cluster.

Step 6: Enable the Profiler for Targeted Investigation

// Log operations slower than 100 ms in the current database db.setProfilingLevel(1, { slowms: 100 }) // Full capture for a short investigation window, then revert db.setProfilingLevel(2) db.setProfilingLevel(1, { slowms: 100 }) // Review recent profiled operations db.system.profile.find().sort({ ts: -1 }).limit(20).pretty()
Profiling level 2 captures every operation and grows the capped collection quickly. Use it for bounded investigation windows, never as a permanent configuration.
Security Note: If your MongoDB edition has no audit log, the diagnostic log plus the profiler is all you have, and the profiler is stored in the database itself. In that case, forwarding the JSON diagnostic log off the host is not an optimisation, it is your only durable evidence.

Recommended Audit Actions

MongoDB audit records are identified by their action type, or atype. These are the atypes that carry the highest security value and belong in any filter you deploy.

authenticate

Records every authentication attempt with the mechanism, user, database, and result code. Result 18 is AuthenticationFailed and is the core brute force signal.
Enable Critical

grantRolesToUser

Fires when roles are assigned to a user. Granting root, dbOwner, or userAdminAnyDatabase is full privilege escalation on the deployment.
Enable Critical

createUser / dropUser

The user lifecycle. Attacker-created accounts in MongoDB frequently carry innocuous names such as backup or admin2 and are granted root immediately.
Enable Critical

dropDatabase / dropCollection

Destructive DDL. In MongoDB ransom campaigns, dropDatabase followed by insertion of a ransom document is the entire attack payload.
Enable Critical

authCheck

Records authorisation decisions for individual commands including the namespace. The mechanism for auditing reads on sensitive collections, but extremely high volume unfiltered.
Filter High Risk

replSetReconfig

Changes to replica set membership. Adding an attacker-controlled node to a replica set is a stealthy way to obtain a continuous copy of all data.
Enable High Risk
Security Note: The audit filter is fixed at startup and cannot be changed at runtime, which is a genuine security advantage: an attacker cannot quietly narrow your auditing. It also means testing a filter requires a restart, so validate it in a non-production deployment first.

MongoDB Log Format

Every diagnostic log line since MongoDB 4.4 is a single JSON object with a consistent set of top-level keys. These are the fields to map when building a SIEM integration.

Field Description Category Example Value
t.$date Event timestamp in ISO 8601 Timestamp 2025-07-14T09:41:22.481+00:00
s Severity: F, E, W, I, or D1-D5 Severity I
c Component that emitted the message Metadata ACCESS
id Stable numeric message identifier Detection 20249
ctx Context, usually the connection thread Session conn8412
msg Human-readable message text Action Authentication failed
attr.remote Client address and port Source 203.0.113.44:52144
attr.user Authenticating user name Identity admin
attr.db Authentication or target database Target admin
attr.mechanism Authentication mechanism used Authorization SCRAM-SHA-256
attr.result MongoDB error code, 0 on success Result 18
attr.ns Namespace in database.collection form Target hrdb.employees
attr.durationMillis Operation duration in milliseconds Performance 38812
attr.docsExamined Documents scanned by the operation Performance 2841776
Pro Tip: The id field is a stable message identifier that does not change when MongoDB rewords a message. Build detections on id rather than on msg text and they will survive version upgrades.

Critical Log Components and Codes

The component field routes each message to a subsystem, and the error code identifies the specific condition. Together they make precise filtering straightforward.

Component / Code Meaning Why It Matters
ACCESS, code 18 AuthenticationFailed The core failed-authentication signal. Repetition from one address is brute force; across many users it is spraying
ACCESS, code 13 Unauthorized An authenticated session attempting an action beyond its role, indicating post-compromise privilege probing
NETWORK, id 22943 Connection accepted Every new client connection with its source address. The baseline for detecting connections from unexpected networks
NETWORK, id 22944 Connection ended Pairs with acceptance to reconstruct session duration and detect very short scanning connections
COMMAND, id 51803 Slow query Any operation over the slow threshold, including docsExamined. Bulk collection scans surface here
CONTROL Startup and shutdown Records the effective startup options, which reveals whether authorization was enabled and what bindIp was in force
STARTUP WARNINGS Insecure configuration MongoDB explicitly warns at startup when access control is disabled and the server is not bound to localhost
REPL Replication state changes Elections and reconfiguration. An unexpected member joining a replica set is a data exfiltration vector
STORAGE, dropDatabase Database dropped Destructive activity. In the ransom campaigns this is the payload itself
Pro Tip: Search any MongoDB log for the string "Access control is not enabled for the database". If it is present, the instance grants full administrative rights to anyone who can reach the port, so treat it as an active incident, not a configuration backlog item.

MongoDB Log Analysis Queries

Use these jq, shell, and mongosh commands to extract authentication attacks, privilege changes, destructive operations, and bulk reads.

Failed Authentication by Source
bash> jq -r 'select(.c=="ACCESS" and .attr.result==18) | .attr.remote' /var/log/mongodb/mongod.log | cut -d: -f1 | sort | uniq -c | sort -rn | head -20
Ranks source addresses by authentication failures. Result code 18 is AuthenticationFailed.
Access Control Disabled
bash> grep -i "access control is not enabled" /var/log/mongodb/mongod.log
A single hit means the instance accepts unauthenticated administrative access. This is the highest severity finding on any MongoDB deployment.
Destructive Operations
bash> jq -r 'select(.atype=="dropDatabase" or .atype=="dropCollection") | [.ts["$date"], .users[0].user, .param.ns, .remote.ip] | @tsv' /var/log/mongodb/audit.json
Extracts every database and collection drop with the responsible user and source address from the audit log.
Role Grants
bash> jq -r 'select(.atype=="grantRolesToUser" or .atype=="createUser") | [.ts["$date"], .users[0].user, .param.user, (.param.roles|tostring), .remote.ip] | @tsv' /var/log/mongodb/audit.json
Shows who granted what to whom. Any grant of root, __system, or userAdminAnyDatabase should be alerted on immediately.
Bulk Collection Scans
bash> jq -r 'select(.attr.docsExamined != null and .attr.docsExamined > 100000) | [.t["$date"], .attr.ns, .attr.docsExamined, .attr.durationMillis, .attr.remote] | @tsv' /var/log/mongodb/mongod.log
Finds operations scanning more than 100,000 documents, the signature of a full collection extraction.
Connections from Unexpected Networks
bash> jq -r 'select(.id==22943) | .attr.remote' /var/log/mongodb/mongod.log | cut -d: -f1 | sort -u | grep -vE "^(10\.|172\.(1[6-9]|2[0-9]|3[01])\.|192\.168\.|127\.)"
Lists every non-RFC1918 address that opened a connection. On an internal database this list should be empty.
Enumerate Privileged Users
mongosh> db.getSiblingDB("admin").system.users.find({ "roles.role": { $in: ["root","userAdminAnyDatabase","dbOwner","__system"] } }, { user:1, db:1, roles:1 })
Lists every account holding a superuser-equivalent role. Baseline this and alert on additions.
Verify Effective Configuration
mongosh> db.adminCommand({ getCmdLineOpts: 1 }).parsed
Returns the options the running process actually started with, including security.authorization and net.bindIp. More trustworthy than the config file on disk.
Profiler Review
mongosh> db.system.profile.find({ ns: /employees|cards/ }).sort({ ts: -1 }).limit(20).pretty()
Reviews recent operations against sensitive collections including the full query shape and originating client.
Replica Set Tampering
SIEM> source="mongodb:audit" atype IN ("replSetReconfig","shutdown","setParameter") | table ts, users{}.user, remote.ip, param
An unplanned replica set reconfiguration can silently add an attacker-controlled node that continuously receives all data.

Best Practices for MongoDB Logging

Apply these practices to make MongoDB logging complete and to close the exposure that drives most real MongoDB incidents:

01

Enable Authorization First

No amount of logging helps an instance that grants everyone administrative access. security.authorization enabled is the prerequisite for every authentication event you would want to detect.

02

Always Set logAppend

Without logAppend, MongoDB truncates the log file on every restart. Restarting the service is a one-command way to destroy the entire diagnostic history.

03

Ingest the JSON Log Natively

MongoDB 4.4 and later emit one JSON object per line. Parse it as JSON rather than with regular expressions, and build detections on the stable numeric id field.

04

Filter the Audit Log Deliberately

Unfiltered auditCheck on a busy cluster produces enormous volume. Filter to authentication, user and role management, destructive DDL, and reads on named sensitive namespaces.

05

Collect mongos Logs in Sharded Clusters

Client sessions terminate at the router. Without mongos logs every operation appears to originate from your own infrastructure and true client attribution is lost.

06

Do Not Rely on the Profiler as an Audit Trail

system.profile is a capped collection inside the database. An attacker with write access can drop it, and it rolls over quickly under load.

07

Alert on Startup Warnings

MongoDB explicitly logs when access control is disabled or the server is bound to all interfaces. Turn those specific startup warnings into alerts rather than ignoring them.

08

Forward Logs Off the Host

Both the diagnostic and audit logs are ordinary files owned by the mongod user. Ship them continuously so a compromise of the database does not also destroy the record of it.

Common MongoDB Log Examples

These entries trace the classic MongoDB compromise: an exposed instance, discovery by scanning, then either exfiltration or a ransom drop.

Startup Warning: Unauthenticated Instance

{"t":{"$date":"2025-07-14T08:02:11.334+00:00"},"s":"W","c":"CONTROL","id":22120,"ctx":"initandlisten","msg":"Access control is not enabled for the database. Read and write access to data and configuration is unrestricted","tags":["startupWarnings"]} {"t":{"$date":"2025-07-14T08:02:11.334+00:00"},"s":"W","c":"CONTROL","id":22140,"ctx":"initandlisten","msg":"This server is bound to localhost. Remote systems will be unable to connect to this server","tags":["startupWarnings"]}
The first warning is the critical one. Combined with a bindIp of 0.0.0.0 instead of localhost, it means anyone who can route to port 27017 has full administrative control.

Authentication Failure (Code 18)

{"t":{"$date":"2025-07-14T09:41:22.481+00:00"},"s":"I","c":"ACCESS","id":20249,"ctx":"conn8412","msg":"Authentication failed","attr":{"mechanism":"SCRAM-SHA-256","speculative":false,"principalName":"admin","authenticationDatabase":"admin","remote":"203.0.113.44:52144","extraInfo":{},"error":"AuthenticationFailed: SCRAM authentication failed, storedKey mismatch"}}
A storedKey mismatch means the account exists and the password was wrong. Repeated at high rate from one address, this is credential guessing against the admin user.

Connection Flood from Scanning Infrastructure

{"t":{"$date":"2025-07-14T09:38:02.117+00:00"},"s":"I","c":"NETWORK","id":22943,"ctx":"listener","msg":"Connection accepted","attr":{"remote":"198.51.100.203:44120","uuid":"5c1f...","connectionId":8390,"connectionCount":41}} {"t":{"$date":"2025-07-14T09:38:02.169+00:00"},"s":"I","c":"NETWORK","id":22944,"ctx":"conn8390","msg":"Connection ended","attr":{"remote":"198.51.100.203:44120","connectionId":8390,"connectionCount":40}}
A connection accepted and closed 52 milliseconds later with no authentication in between. Hundreds of these from consecutive addresses is internet-wide scanning identifying exposed MongoDB instances.

Audit Log: Backdoor Account with Root

{"atype":"createUser","ts":{"$date":"2025-07-14T09:52:10.774+00:00"},"local":{"ip":"10.40.1.15","port":27017},"remote":{"ip":"203.0.113.44","port":52190},"users":[{"user":"admin","db":"admin"}],"roles":[{"role":"root","db":"admin"}],"param":{"user":"mongobackup","db":"admin","roles":[{"role":"root","db":"admin"}]},"result":0}
A new account named to look like a backup service, granted root on the admin database. Result 0 confirms it succeeded.

Bulk Extraction: Full Collection Scan

{"t":{"$date":"2025-07-14T09:58:02.114+00:00"},"s":"I","c":"COMMAND","id":51803,"ctx":"conn8419","msg":"Slow query","attr":{"type":"command","ns":"shopdb.customers","command":{"find":"customers","filter":{},"batchSize":101},"planSummary":"COLLSCAN","keysExamined":0,"docsExamined":2841776,"nreturned":101,"durationMillis":38812,"remote":"203.0.113.44:52190"}}
An empty filter with a COLLSCAN plan examining 2.8 million documents. The batched cursor means the client is paging through the entire customer collection.

Ransom Attack: Database Dropped

{"atype":"dropDatabase","ts":{"$date":"2025-07-14T10:04:55.229+00:00"},"remote":{"ip":"203.0.113.44","port":52190},"users":[],"roles":[],"param":{"ns":"shopdb"},"result":0} {"t":{"$date":"2025-07-14T10:05:01.882+00:00"},"s":"I","c":"COMMAND","id":51803,"ctx":"conn8419","msg":"Slow query","attr":{"type":"command","ns":"READ__ME_TO_RECOVER_YOUR_DATA.Warning","command":{"insert":"Warning"},"remote":"203.0.113.44:52190"}}
An empty users array on the dropDatabase record proves the operation was unauthenticated. The ransom note database created seconds later completes the pattern that has hit tens of thousands of exposed instances.

Unauthorized Access Attempt (Code 13)

{"t":{"$date":"2025-07-14T10:09:14.006+00:00"},"s":"I","c":"ACCESS","id":20436,"ctx":"conn8433","msg":"Checking authorization failed","attr":{"error":{"code":13,"codeName":"Unauthorized","errmsg":"not authorized on hrdb to execute command { find: \"employees\", filter: {} }"},"remote":"10.30.2.61:52240"}}
An authenticated but under-privileged account probing a collection it cannot read. A burst of code 13 events across many namespaces is systematic privilege mapping after a credential compromise.
