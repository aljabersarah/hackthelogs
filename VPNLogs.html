VPN Logs

VPN Log Overview

The VPN concentrator is the front door to the internal network, and it is exposed to the internet by design. That combination makes it one of the most consistently targeted assets in any environment: credential stuffing against the portal, exploitation of the appliance itself, and abuse of valid stolen credentials all converge here. VPN logs are where those attempts become visible, and they are frequently the earliest evidence available in an intrusion timeline, because remote access is where so many intrusions begin.

A VPN log records two distinct things that are easy to conflate. The first is authentication: who attempted to log in, from which public address, using which method, and whether it succeeded. The second is the session: the tunnel that was established, the internal address assigned to the client, how long it lasted, and how much data crossed it. Detection depends on both. Authentication events reveal brute force, password spraying, and multi-factor fatigue, while session events provide the crucial mapping from an assigned internal address to a named user, without which every subsequent internal log entry for that address is unattributable.

Because attackers increasingly use valid credentials rather than exploits, the highest value VPN detections are behavioural rather than signature based. Impossible travel between two logins, a successful authentication from a country where the organisation has no presence, an unusual client version, a session at an hour the user has never worked, or a burst of MFA prompts followed by one acceptance are all patterns that only emerge when VPN logs are enriched with geolocation and compared against a per-user baseline. A successful login is not evidence of legitimacy, and treating it as such is why credential-based intrusions persist undetected for so long.

Key VPN Log Types

Remote access logging spans the concentrator, the identity provider, and the endpoint posture system. A complete picture requires all three:

Log Type Description
Authentication Log Records every login attempt with the username, source public address, authentication method, tunnel group, and result. The primary source for brute force, password spraying, and credential stuffing detection, and the first log to review in any suspected account compromise.
Session Establishment Log Written when a tunnel is created. Contains the assigned internal address, the client software version, the negotiated encryption, and the group policy applied. The assigned address is what links this user to every subsequent internal log entry.
Session Teardown Log Written when a tunnel closes, carrying the session duration, total bytes sent and received, and the reason for disconnection. Byte counts here are the simplest available signal for exfiltration over remote access.
Posture and Compliance Log Results of endpoint health checks performed before access is granted, covering antivirus status, patch level, disk encryption, and certificate presence. Records both which devices failed and which were admitted anyway under a remediation policy.
Multi-Factor Authentication Log Usually produced by the identity provider or RADIUS server rather than the concentrator. Records each factor challenge and its outcome, which is the only way to distinguish a user approving a legitimate prompt from a user approving one under fatigue.
Administrative Access Log Logins to the appliance management interface and configuration changes made there. An attacker who compromises the concentrator itself can create tunnel groups and disable logging, so this stream needs independent monitoring.
Tunnel Traffic Log Connection records for traffic inside the tunnel, subject to the split tunnelling policy. Shows what internal resources the remote user actually reached once connected.
Pro Tip: The mapping between assigned tunnel address and username exists only in the session logs, and pools are reused constantly. Without retaining session establishment and teardown records, an internal alert on a VPN pool address cannot be attributed to a person after the fact.

Log File Locations

Appliances rarely store logs locally in any useful quantity. Syslog forwarding is not an enhancement here, it is the only viable collection method.

Platform Default Location
Cisco ASA / Firepower Internal buffer only, viewed with show logging. Forward via syslog to a collector
Fortinet FortiGate Local disk if fitted, otherwise FortiAnalyzer or syslog. View with execute log display
Palo Alto GlobalProtect System and GlobalProtect log types in the firewall, forwarded via Log Forwarding Profile
OpenVPN /var/log/openvpn.log or /var/log/openvpn/openvpn-status.log
OpenVPN Configuration /etc/openvpn/server.conf
WireGuard Kernel log via journalctl -u wg-quick@wg0, plus wg show for peer handshake times
strongSwan IPsec /var/log/charon.log or the system journal
Windows Always On VPN RAS logs in %SystemRoot%\tracing and NPS accounting in %SystemRoot%\System32\LogFiles\IN*.log
Pro Tip: WireGuard is deliberately minimal and logs almost nothing by design. It records handshake times per peer but no session or authentication events, so deployments need external accounting through wg show polling or a management layer on top.

Configuring VPN Logging

Default logging levels on most concentrators are too low to capture authentication detail. These configurations raise them to a useful level without flooding the collector.

Step 1: Configure Cisco ASA Syslog

logging enable logging timestamp rfc5424 logging host INSIDE 10.50.9.20 6/1514 logging trap informational logging device-id hostname no logging message 302013 ! suppress high volume connection build no logging message 302014 ! Ensure the VPN specific classes are retained logging list VPNLOG message 113004-113020 logging list VPNLOG message 722022-722051 logging list VPNLOG message 716038-716059
Informational level is required: authentication messages such as 113004 and 113005 are severity 6 and are lost entirely at the default warning level.

Step 2: Configure FortiGate SSL VPN Logging

config log syslogd setting set status enable set server "10.50.9.20" set port 514 set facility local7 set format rfc5424 end config vpn ssl settings set log-session-info enable end config log setting set fwpolicy-implicit-log enable set resolve-ip enable end
log-session-info adds the tunnel address assignment and byte counters to session records, which is what makes user attribution and exfiltration detection possible.

Step 3: Configure OpenVPN Verbosely Enough

# /etc/openvpn/server.conf log-append /var/log/openvpn.log status /var/log/openvpn/openvpn-status.log 30 status-version 3 verb 4 # 3 is default, 4 adds authentication detail mute 0 # never suppress repeated messages # Record the real client address and assigned tunnel address push "route 10.0.0.0 255.0.0.0" client-connect /etc/openvpn/scripts/log-connect.sh client-disconnect /etc/openvpn/scripts/log-disconnect.sh
Verbosity 4 exposes certificate common names and authentication outcomes. Setting mute to 0 matters because the default suppresses repeated messages, which hides brute force bursts.

Step 4: Capture the Identity Provider Side

# The concentrator sees "authentication succeeded" but not which factors were used. # Collect the RADIUS or IdP log alongside it: # Microsoft NPS : %SystemRoot%\System32\LogFiles\IN*.log (event IDs 6272/6273) # FreeRADIUS : /var/log/freeradius/radius.log # Entra ID : SignInLogs table, authenticationDetails field # Okta : System Log API, eventType user.authentication.auth_via_mfa # Correlate on username plus timestamp plus source address
MFA fatigue attacks are invisible in concentrator logs, which record only the final successful authentication. The repeated denied prompts that preceded it exist only in the identity provider log.

Step 5: Enrich with Geolocation at Ingest

# Example enrichment pipeline (Logstash) filter { if [event_type] == "vpn_auth" { geoip { source => "src_ip" target => "geo" } if [geo][country_code2] not in ["SA","AE","GB"] { mutate { add_tag => ["vpn_unexpected_country"] } } } }
Geolocation must be applied at ingest, not at query time. Impossible travel detection requires the country and coordinates to already be on the event when correlation runs.

Step 6: Retain Address Assignment Mappings

# Build a lookup of tunnel address to user for the retention period source="vpn" (event="session_established" OR event="session_terminated") | eval end_time=if(event=="session_terminated", _time, now()) | table username, assigned_ip, src_ip, _time, end_time, bytes_sent, bytes_received | outputlookup vpn_session_history.csv
This lookup is what lets an analyst resolve a VPN pool address in an internal alert back to a person weeks later. Pools recycle within hours, so the mapping must be historical.
Security Note: VPN appliances have been among the most heavily exploited enterprise products in recent years, with pre-authentication vulnerabilities affecting every major vendor. Monitor the administrative access log and the appliance's own system log as closely as the user authentication log, because a compromised concentrator can issue itself valid sessions.

VPN Threat Patterns

Remote access attacks follow recognisable shapes. These are the highest value detections to build from VPN telemetry.

Impossible Travel

Two successful authentications for one account from locations too far apart for the elapsed time. Among the highest confidence indicators of credential compromise available.
Detect Critical

MFA Fatigue

Repeated push notifications until the user approves one out of irritation. Signature: many denied or timed out factor challenges followed by a single acceptance, all within minutes.
Detect Critical

Password Spraying

One or two password attempts against many accounts, staying below lockout thresholds. Signature: a single source address failing against dozens of distinct usernames.
Detect Critical

Anomalous Session Timing

Connections at hours a user has never worked, or sessions lasting far longer than their norm. Effective precisely because attackers operate in their own timezone, not the victim's.
Detect High Risk

Exfiltration Over Tunnel

Session teardown records showing bytes received by the client far exceeding the user's baseline. A remote session pulling gigabytes from file shares is bulk data theft.
Detect High Risk

Concurrent Sessions

One account with simultaneous tunnels from different addresses or countries. Either credential sharing or an attacker connected alongside the legitimate user.
Detect Medium Risk
Security Note: Commercial VPN and residential proxy services are widely used to defeat geolocation detections, placing an attacker's apparent source inside the expected country. Maintain a list of known hosting and anonymiser ranges and treat authentications from them as anomalous regardless of the country they resolve to.

Critical VPN Message IDs

Cisco ASA and FortiGate identify events by numeric identifiers that remain stable across software versions, making them reliable detection anchors.

Message ID Meaning Why It Matters
ASA-6-113005 AAA user authentication rejected The core VPN authentication failure. Bursts against one account are brute force, across many accounts is spraying
ASA-6-113004 AAA user authentication successful The baseline for behavioural detection. Every impossible travel and off-hours alert starts here
ASA-6-113015 AAA user authentication rejected, user not found Distinguishes username enumeration from password guessing against real accounts
ASA-6-722022 TCP or SSL connection established Tunnel establishment carrying the assigned internal address, the key to user attribution
ASA-4-113019 Group and user disconnected Session teardown with duration and byte counts, the simplest exfiltration signal available
ASA-6-716039 WebVPN authentication rejected Clientless portal login failure, frequently the target of automated credential stuffing
ASA-6-605005 Login permitted to the management interface Administrative access to the appliance itself. Should be rare, scheduled, and from known addresses only
ASA-3-713061 IKE peer rejected, no matching policy IPsec negotiation failures, often scanning of the VPN endpoint by unauthorised peers
Fortinet 0101039426 SSL VPN login failed FortiGate authentication failure. The action field ssl-login-fail is the equivalent detection anchor
Fortinet 0101039424 SSL VPN tunnel up Tunnel establishment with the assigned address and the user group applied
Pro Tip: Suppressing ASA messages 302013 and 302014 is standard practice for volume control, but be careful not to suppress the 7xxxx range along with them. Those are the VPN session messages, and losing them removes address-to-user attribution entirely.

VPN Log Analysis Queries

These queries surface credential attacks, geographic anomalies, and data theft over remote access.

Impossible Travel
SIEM> source="vpn" result="success" | sort username, _time | streamstats current=f last(src_country) as prev_country, last(_time) as prev_time by username | eval gap_hr=(_time-prev_time)/3600 | where prev_country!=src_country AND gap_hr < 4
Two successful logins from different countries within four hours. Whitelist adjacent-country commuting patterns before deploying this.
Password Spraying
SIEM> source="vpn" result="failed" | bucket _time span=30m | stats dc(username) as targets, count as attempts by src_ip, _time | where targets > 15 AND attempts/targets < 3
Many usernames with few attempts each is the defining spray signature, deliberately staying under account lockout thresholds.
MFA Fatigue
SIEM> source="idp" eventType="*mfa*" | bucket _time span=15m | stats count(eval(result=="denied")) as denied, count(eval(result=="success")) as approved by username, _time | where denied >= 5 AND approved >= 1
Five or more rejected prompts followed by an approval in the same window is a user giving in, not a user authenticating.
Brute Force Then Success
SIEM> source="vpn" | bucket _time span=1h | stats count(eval(result=="failed")) as fails, count(eval(result=="success")) as wins, values(src_ip) by username, _time | where fails > 20 AND wins > 0
The highest priority VPN alert there is: sustained failures against one account followed by a success in the same hour.
Logins from Unexpected Countries
SIEM> source="vpn" result="success" NOT src_country IN ("SA","AE","GB") | stats count, values(src_ip), values(src_country) by username | sort - count
Define the allowed country list from where your workforce actually is, not from where you have offices. Travel exceptions should be temporary and documented.
Exfiltration Over Tunnel
SIEM> source="vpn" event="session_terminated" | stats sum(bytes_sent) as downloaded, avg(duration) as avg_dur by username, session_id | eventstats avg(downloaded) as user_avg by username | where downloaded > user_avg*10 AND downloaded > 1000000000
Compares each session against the user's own baseline rather than a global threshold, which is what makes it usable in practice.
Concurrent Sessions
SIEM> source="vpn" event="session_established" | bucket _time span=1h | stats dc(src_ip) as sources, dc(src_country) as countries, values(src_ip) by username, _time | where sources > 1
One account tunnelled from two addresses at once is either shared credentials or an attacker connected alongside the real user.
Unusual Client Versions
SIEM> source="vpn" event="session_established" | stats count, dc(username) as users by client_version | where users < 3 | sort count
Rare client versions can indicate an attacker using an unmanaged device or an open source client against your corporate concentrator.
Resolve a Tunnel Address to a User
SIEM> source="vpn" assigned_ip="10.99.4.117" | table _time, event, username, src_ip, src_country, session_id | sort _time
The standard pivot when an internal alert names a VPN pool address. Bound the search by the alert time because pools recycle within hours.
Appliance Administrative Access
SIEM> source="vpn" (message_id="605005" OR message_id="111008" OR action="config_change") | table _time, username, src_ip, message | sort - _time
Configuration changes on the concentrator itself. An attacker here can create tunnel groups, disable MFA, and turn logging off.

Best Practices for VPN Logging

Apply these practices to make remote access logging capable of catching credential-based intrusion:

01

Log at Informational Severity

Authentication messages are severity 6 on Cisco platforms. At the default warning level they are never emitted, so the most important VPN events simply do not exist.

02

Retain Address Assignment History

Keep session establishment and teardown records for the full retention period. Without them a VPN pool address in an internal alert can never be traced to a person.

03

Collect the Identity Provider Logs Too

The concentrator records only the final authentication result. MFA fatigue, factor type, and denied prompts exist solely in the RADIUS or identity provider log.

04

Geolocate at Ingest

Impossible travel detection needs country and coordinates already attached to the event. Enriching at query time is too slow and breaks correlation across time windows.

05

Baseline Per User, Not Globally

Working hours, session length, and data volume vary enormously between roles. A per-user baseline finds anomalies that any global threshold either misses or drowns in false positives.

06

Alert on Successful Logins, Not Only Failures

Attackers using stolen credentials generate a clean success. Failure-only monitoring is blind to exactly the attack type that matters most today.

07

Monitor the Appliance Itself

VPN concentrators are among the most exploited enterprise products. Watch administrative logins, configuration changes, and firmware version alongside user authentication.

08

Forward Off the Appliance Immediately

Concentrators hold only a small local buffer that wraps in minutes under load. Syslog forwarding is the only collection method that survives both volume and compromise.

Common VPN Log Examples

An account takeover through the VPN, traced from spraying through to data theft.

Password Spraying Against the Portal

Jul 14 2025 09:12:04 asa-vpn01 : %ASA-6-113015: AAA user authentication Rejected : reason = User was not found : local database : user = a.alqahtani : user IP = 203.0.113.44 Jul 14 2025 09:12:07 asa-vpn01 : %ASA-6-113005: AAA user authentication Rejected : reason = AAA failure : server = 10.50.1.20 : user = m.alharbi : user IP = 203.0.113.44 Jul 14 2025 09:12:11 asa-vpn01 : %ASA-6-113005: AAA user authentication Rejected : reason = AAA failure : server = 10.50.1.20 : user = r.almutairi : user IP = 203.0.113.44 Jul 14 2025 09:12:14 asa-vpn01 : %ASA-6-113005: AAA user authentication Rejected : reason = AAA failure : server = 10.50.1.20 : user = s.aldosari : user IP = 203.0.113.44
One source address, four different accounts, one attempt each, seconds apart. Message 113015 confirms the first username does not exist, so this is a guessed list being tested.

MFA Fatigue in the Identity Provider Log

2025-07-14T09:38:02Z user.mfa.factor.verify result=DENIED user=r.almutairi factor=push client_ip=203.0.113.44 reason=user_rejected 2025-07-14T09:38:31Z user.mfa.factor.verify result=DENIED user=r.almutairi factor=push client_ip=203.0.113.44 reason=user_rejected 2025-07-14T09:39:05Z user.mfa.factor.verify result=TIMEOUT user=r.almutairi factor=push client_ip=203.0.113.44 2025-07-14T09:39:44Z user.mfa.factor.verify result=DENIED user=r.almutairi factor=push client_ip=203.0.113.44 reason=user_rejected 2025-07-14T09:40:52Z user.mfa.factor.verify result=SUCCESS user=r.almutairi factor=push client_ip=203.0.113.44
Four rejections then an approval in under three minutes, all from the same foreign address. The user did not decide this was legitimate, they gave up. The concentrator will record only the final success.

Successful Authentication and Tunnel Establishment

Jul 14 2025 09:40:53 asa-vpn01 : %ASA-6-113004: AAA user authentication Successful : server = 10.50.1.20 : user = r.almutairi Jul 14 2025 09:40:53 asa-vpn01 : %ASA-6-113008: AAA transaction status ACCEPT : user = r.almutairi Jul 14 2025 09:40:54 asa-vpn01 : %ASA-6-722022: Group <CORP-SSLVPN> User <r.almutairi> IP <203.0.113.44> TCP SVC connection established without compression Jul 14 2025 09:40:54 asa-vpn01 : %ASA-6-722051: Group <CORP-SSLVPN> User <r.almutairi> IP <203.0.113.44> IPv4 Address <10.99.4.117> assigned to session
Message 722051 is the critical one: it binds tunnel address 10.99.4.117 to this user. Every internal log entry for that address from now on belongs to this session.

Impossible Travel

Jul 14 2025 08:02:11 asa-vpn01 : %ASA-6-113004: AAA user authentication Successful : server = 10.50.1.20 : user = r.almutairi [enriched] src_ip=94.56.11.204 src_country=SA src_city=Riyadh Jul 14 2025 09:40:53 asa-vpn01 : %ASA-6-113004: AAA user authentication Successful : server = 10.50.1.20 : user = r.almutairi [enriched] src_ip=203.0.113.44 src_country=NL src_city=Amsterdam
Riyadh to Amsterdam in 98 minutes, a journey of roughly 4,500 km. Both authentications succeeded, which is precisely why success events must be monitored.

FortiGate SSL VPN Login Failures

date=2025-07-14 time=09:12:04 devname="fgt-vpn01" devid="FG100E0000000001" logid="0101039426" type="event" subtype="vpn" level="alert" vd="root" action="ssl-login-fail" tunneltype="ssl-web" tunnelid=0 remip=203.0.113.44 user="a.alqahtani" group="N/A" dst_host="N/A" reason="sslvpn_login_permission_denied" msg="SSL user failed to logged in" date=2025-07-14 time=09:40:54 devname="fgt-vpn01" logid="0101039424" type="event" subtype="vpn" level="information" action="tunnel-up" tunneltype="ssl-tunnel" tunnelid=1284119 remip=203.0.113.44 user="r.almutairi" group="corp-vpn-users" assignip=10.99.4.117 duration=0 sentbyte=0 rcvdbyte=0
FortiGate uses action strings rather than numeric severity. The tunnel-up record carries assignip, which serves the same attribution role as Cisco message 722051.

Session Teardown Revealing Exfiltration

Jul 14 2025 17:48:21 asa-vpn01 : %ASA-4-113019: Group = CORP-SSLVPN, Username = r.almutairi, IP = 203.0.113.44, Session disconnected. Session Type: SSL, Duration: 8h:07m:27s, Bytes xmt: 1884221904, Bytes rcv: 3218844, Reason: User Requested
1.88 GB transmitted to the client over eight hours. Compare against this user's baseline of roughly 40 MB per session and the scale of the theft is obvious from one line.

OpenVPN Authentication Failure Burst

Sat Jul 14 09:12:04 2025 203.0.113.44:44120 TLS: Initial packet from [AF_INET]203.0.113.44:44120, sid=8f2a1c04 3e91b7d2 Sat Jul 14 09:12:04 2025 203.0.113.44:44120 VERIFY ERROR: depth=0, error=self signed certificate: CN=client Sat Jul 14 09:12:04 2025 203.0.113.44:44120 TLS_ERROR: BIO read tls_read_plaintext error Sat Jul 14 09:12:04 2025 203.0.113.44:44120 TLS Error: TLS object -> incoming plaintext read error Sat Jul 14 09:12:05 2025 203.0.113.44:44121 TLS: Initial packet from [AF_INET]203.0.113.44:44121, sid=9a3b2d15 4f02c8e3
Repeated TLS handshake failures with a self-signed client certificate, one second apart from sequential ports. This is automated probing of the OpenVPN endpoint, not a misconfigured user.

Appliance Configuration Change

Jul 14 2025 17:52:10 asa-vpn01 : %ASA-6-605005: Login permitted from 10.99.4.117/52190 to inside:10.50.1.1/https for user "r.almutairi" Jul 14 2025 17:53:44 asa-vpn01 : %ASA-5-111008: User 'r.almutairi' executed the 'tunnel-group MAINT-ACCESS type remote-access' command. Jul 14 2025 17:54:02 asa-vpn01 : %ASA-5-111008: User 'r.almutairi' executed the 'no logging host INSIDE 10.50.9.20' command.
The compromised account reaching the management interface from inside its own tunnel, creating a new tunnel group, then removing the syslog destination. That last command is the final entry the collector will ever receive.
