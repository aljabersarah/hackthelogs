Kubernetes and Container Logs

Kubernetes Log Overview

Everything in Kubernetes passes through the API server, which makes the audit log the equivalent of CloudTrail for a cluster. Creating a pod, reading a secret, opening a shell inside a running container, and modifying a role binding are all API requests, and all of them can be recorded with the requesting identity, the source address, the object affected, and the authorisation decision. Without the audit log, a cluster is genuinely opaque: container logs show what applications printed, but nothing shows who instructed the cluster to do what.

The critical fact is that audit logging is off by default in a self-managed cluster. It requires an audit policy file and API server flags, and if either is missing the cluster runs perfectly while recording nothing. Managed platforms differ: EKS control plane logging must be explicitly enabled per log type, AKS requires a diagnostic setting, and GKE enables Admin Activity audit logs automatically while leaving Data Access logging off. In every case the default state leaves at least one significant gap.

The audit policy itself is where most of the value is decided. Each rule assigns a level of None, Metadata, Request, or RequestResponse, controlling how much of the request and response body is captured. Recording RequestResponse for everything produces unusable volume and writes secret contents into the log. Recording only Metadata for everything means you know a secret was read but not which one. A workable policy captures Metadata broadly, escalates to Request for security-relevant resources, and drops the high-volume noise from system components entirely.

Key Kubernetes Log Types

Cluster visibility spans the control plane, the nodes, and the workloads themselves:

Log Type Description
API Server Audit Log The authoritative record of every request to the cluster, including the identity, verb, resource, namespace, source address, user agent, and authorisation decision. Disabled by default in self-managed clusters. The single most important cluster log.
Container and Pod Logs Standard output and error from every container, collected by the kubelet. Application-level visibility rather than cluster-level, but essential for understanding what a compromised workload actually did.
Kubelet Log The node agent, recording pod lifecycle, volume mounts, image pulls, and requests received on the kubelet API. Where node-level compromise and unauthorised kubelet access appear.
Admission Controller Decisions Output from validating and mutating webhooks such as OPA Gatekeeper or Kyverno. Records policy violations that were blocked, which is a direct feed of attempted misconfiguration and attack.
etcd Log The cluster datastore. Direct etcd access bypasses the API server and all of its auditing entirely, so authentication events here are high value and low volume.
Controller Manager and Scheduler Control plane components recording reconciliation and pod placement decisions. Mostly operational, but useful when investigating why a workload landed on a particular node.
Container Runtime Log containerd or CRI-O output covering image pulls, container creation, and runtime errors. Shows images pulled from unexpected registries.
Runtime Security Events Syscall-level detections from Falco, Tetragon, or a commercial sensor. The only source that sees what happens inside a container after it starts, which the audit log never does.
Pro Tip: The audit log records that a shell was opened into a pod through pods/exec, but never what was typed. Commands executed inside the container are visible only to a runtime sensor. Pairing audit logging with a runtime tool closes the largest single gap in container visibility.

Log Locations by Platform

Self-managed clusters write to the filesystem, while managed platforms deliver to the cloud provider's logging service.

Source Location
Audit Log (self-managed) Path set by --audit-log-path, commonly /var/log/kubernetes/audit/audit.log
Audit Policy File /etc/kubernetes/audit-policy.yaml, referenced by --audit-policy-file
API Server Manifest /etc/kubernetes/manifests/kube-apiserver.yaml on control plane nodes
Container Logs /var/log/containers/ (symlinks) and /var/log/pods/<namespace>_<pod>_<uid>/
Kubelet Log journalctl -u kubelet on the node
Amazon EKS CloudWatch log group /aws/eks/<cluster>/cluster, one stream per component
Google GKE Cloud Logging, resource type k8s_cluster with logName cloudaudit.googleapis.com%2Factivity
Azure AKS Log Analytics table AzureDiagnostics with Category kube-audit or kube-audit-admin
etcd Data and Logs /var/lib/etcd/ with logs in the etcd pod or journal
Pro Tip: On AKS, the kube-audit-admin category excludes read-only get and list requests and is typically a fraction of the volume of full kube-audit. It is the pragmatic default when full audit volume is unaffordable, though it loses visibility into reconnaissance.

Configuring Kubernetes Auditing

A self-managed cluster needs both a policy file and API server flags. Managed platforms need their log types enabling explicitly.

Step 1: Write a Practical Audit Policy

apiVersion: audit.k8s.io/v1 kind: Policy omitStages: ["RequestReceived"] rules: # Never log the high volume, low value noise - level: None users: ["system:kube-proxy","system:apiserver"] verbs: ["watch","list"] - level: None nonResourceURLs: ["/healthz*","/readyz*","/livez*","/version","/metrics"] # Full request body for the resources that matter - level: Request resources: - group: "" # core resources: ["pods/exec","pods/attach","pods/portforward","pods/ephemeralcontainers"] - group: "rbac.authorization.k8s.io" resources: ["roles","rolebindings","clusterroles","clusterrolebindings"] # Metadata only for secrets: never write their contents to the log - level: Metadata resources: - group: "" resources: ["secrets","configmaps","serviceaccounts"] # Everything else at metadata level - level: Metadata omitStages: ["RequestReceived"]
Order matters: the first matching rule wins. Secrets are deliberately kept at Metadata level, because Request or RequestResponse would write the secret values themselves into the audit log in cleartext.

Step 2: Enable Auditing on the API Server

# /etc/kubernetes/manifests/kube-apiserver.yaml spec: containers: - command: - kube-apiserver - --audit-policy-file=/etc/kubernetes/audit-policy.yaml - --audit-log-path=/var/log/kubernetes/audit/audit.log - --audit-log-maxage=30 - --audit-log-maxbackup=10 - --audit-log-maxsize=500 - --audit-log-format=json volumeMounts: - name: audit-policy mountPath: /etc/kubernetes/audit-policy.yaml readOnly: true - name: audit-log mountPath: /var/log/kubernetes/audit/
Both the policy file and the log directory must be mounted into the static pod. Forgetting the volume mounts is the most common reason auditing appears configured but produces nothing.

Step 3: Enable Managed Platform Audit Logs

# Amazon EKS aws eks update-cluster-config --name htl-prod \ --logging '{"clusterLogging":[{"types":["api","audit","authenticator","controllerManager","scheduler"],"enabled":true}]}' # Azure AKS az monitor diagnostic-settings create --name aks-audit \ --resource $(az aks show -g rg-prod -n htl-prod --query id -o tsv) \ --workspace <workspace-id> \ --logs '[{"category":"kube-audit","enabled":true}, {"category":"kube-audit-admin","enabled":true}, {"category":"kube-apiserver","enabled":true}, {"category":"guard","enabled":true}]' # Google GKE: Admin Activity is automatic, Data Access must be enabled gcloud container clusters update htl-prod --region me-central1 \ --logging=SYSTEM,WORKLOAD,API_SERVER,CONTROLLER_MANAGER,SCHEDULER
EKS logging is off entirely by default, and the authenticator stream is the one that records IAM identity mapping. Enabling only api and audit leaves that gap open.

Step 4: Deploy a Runtime Security Sensor

helm repo add falcosecurity https://falcosecurity.github.io/charts helm install falco falcosecurity/falco --namespace falco --create-namespace \ --set driver.kind=modern_ebpf \ --set falcosidekick.enabled=true \ --set "falco.json_output=true" # Example rule: shell spawned inside a container # - rule: Terminal shell in container # condition: spawned_process and container and shell_procs and proc.tty != 0 # output: Shell in container (user=%user.name container=%container.name) # priority: WARNING
The audit log records that pods/exec occurred but never the commands typed. A runtime sensor is the only source that observes activity inside a running container.

Step 5: Enforce Policy at Admission

# Pod Security Admission, the built-in baseline kubectl label namespace production \ pod-security.kubernetes.io/enforce=restricted \ pod-security.kubernetes.io/enforce-version=latest \ pod-security.kubernetes.io/audit=restricted \ pod-security.kubernetes.io/warn=restricted # Verify what would be blocked before enforcing kubectl label namespace legacy pod-security.kubernetes.io/warn=restricted --overwrite
The audit and warn labels report violations without blocking, which lets you measure impact before enforcement. Admission denials are themselves a valuable detection feed.

Step 6: Ship Audit Logs Off the Cluster

# Fluent Bit input for the audit log on control plane nodes [INPUT] Name tail Path /var/log/kubernetes/audit/audit.log Parser json Tag k8s.audit Refresh_Interval 5 Mem_Buf_Limit 50MB Skip_Long_Lines On [OUTPUT] Name forward Match k8s.audit Host siem-collector.corp.local Port 24224 tls On
Audit logs live on the control plane nodes, which an attacker with cluster-admin can reach. Shipping them off cluster is what preserves the evidence of the compromise.
Security Note: Never set audit level to Request or RequestResponse for the secrets resource. Doing so writes every secret value into the audit log in cleartext, turning your security log into the highest value credential store in the environment.

Kubernetes Threat Patterns

Container attacks follow a consistent path: get into a pod, escape to the node, then escalate across the cluster.

Exec into Pod

Opening an interactive shell in a running container via pods/exec. Legitimate for debugging but the primary hands-on-keyboard technique. Commands typed are not recorded by the audit log.
Detect Critical

Privileged Pod Escape

Creating a pod with privileged true, hostPID, hostNetwork, or a hostPath mount of the root filesystem. Grants root on the node itself, escaping the container boundary entirely.
Detect Critical

RBAC Escalation

Binding a service account to cluster-admin, or exploiting the escalate and bind verbs. One ClusterRoleBinding is full control of every namespace and workload.
Detect Critical

Secret Harvesting

Listing or reading secrets across namespaces. Kubernetes secrets are base64 encoded, not encrypted, unless encryption at rest is configured, so a list request returns usable credentials.
Detect Critical

Service Account Token Abuse

Using a token mounted into a compromised pod to call the API. Signature: requests from a service account identity originating from a pod address rather than an administrator workstation.
Detect High Risk

Cryptomining Workloads

Deploying pods pulling images from public registries with high resource requests. The most common outcome of an exposed dashboard or unauthenticated API server.
Detect High Risk
Security Note: The system:anonymous user and the system:unauthenticated group appearing in audit logs with successful authorisation decisions means the cluster accepts unauthenticated API requests. This is how exposed clusters are mass-compromised, and it should be treated as an active incident.

Audit Event Format

Every Kubernetes audit event is a JSON object with a stable schema. These are the fields detections are built on.

Field Description Category Example Value
requestReceivedTimestamp Time the API server received the request Timestamp 2025-07-14T09:41:22.481Z
verb Action requested Action create
user.username Authenticated identity Identity system:serviceaccount:default:build-sa
user.groups Groups the identity belongs to Identity ["system:serviceaccounts","system:authenticated"]
impersonatedUser Identity impersonated, when the impersonate verb is used Identity system:admin
sourceIPs Client addresses including proxies Source ["10.244.3.17"]
userAgent Client tool and version Source kubectl/v1.29.3 (linux/amd64)
objectRef.resource Resource type targeted Target secrets
objectRef.subresource Subresource such as exec or portforward Target exec
objectRef.namespace Namespace of the target object Target kube-system
objectRef.name Name of the specific object Target db-credentials
responseStatus.code HTTP status returned Result 201
annotations.authorization.k8s.io/decision allow or forbid, with the reason alongside Authorization allow
stage Point in request handling Metadata ResponseComplete
Pro Tip: The authorization.k8s.io/reason annotation names the exact RBAC binding that permitted a request. When investigating how an identity was able to act, this field answers the question immediately rather than requiring you to reconstruct the role graph.

Critical Verbs and Resources

A short list of verb and resource combinations covers most Kubernetes attack activity.

Verb and Resource Stage Why It Matters
create pods/exec Execution Interactive shell in a running container. The commands typed are not audited, only the fact that a session opened
create pods (privileged) Escape A pod with privileged, hostPID, or a hostPath root mount gives root on the node and escapes the container boundary
create clusterrolebindings Escalation Binding any identity to cluster-admin grants total control of the cluster in a single object
get / list secrets Credential Access Secrets are base64 encoded, not encrypted by default. A list across namespaces returns immediately usable credentials
create pods/portforward Lateral Movement Tunnels traffic from a workstation directly to a pod, bypassing network policy and ingress controls entirely
impersonate users or groups Escalation Acting as another identity. Legitimate for some controllers, but impersonating system:admin is escalation
create serviceaccounts/token Persistence Minting a token for a privileged service account produces a credential that survives pod deletion
patch daemonsets Persistence A DaemonSet runs on every node, including nodes added later. Ideal placement for a persistent implant
delete events Evasion Removing Kubernetes events destroys the cluster's own activity record, though not the audit log
create validatingwebhookconfigurations Evasion A malicious webhook can intercept every API request, and a failurePolicy of Ignore lets an attacker silently drop admission controls
any verb as system:anonymous Initial Access Unauthenticated API access. If this appears with an allow decision, the cluster is open to the world

Kubernetes Log Analysis Queries

These jq and SIEM queries cover the container attack chain from access through escalation to persistence.

Exec into Pods
bash> jq -r 'select(.objectRef.subresource=="exec") | [.requestReceivedTimestamp, .user.username, .objectRef.namespace, .objectRef.name, .sourceIPs[0]] | @tsv' audit.log
Every interactive session opened into a container. In a mature GitOps environment this should be rare enough to review individually.
Privileged Pod Creation
bash> jq -r 'select(.verb=="create" and .objectRef.resource=="pods") | select(.requestObject.spec.containers[]?.securityContext.privileged==true or .requestObject.spec.hostPID==true or .requestObject.spec.hostNetwork==true) | [.requestReceivedTimestamp, .user.username, .objectRef.namespace] | @tsv' audit.log
Requires Request level auditing on pods. A privileged pod is root on the node, so this is container escape by design.
Cluster Admin Binding
bash> jq -r 'select(.objectRef.resource=="clusterrolebindings" and (.verb=="create" or .verb=="update")) | [.requestReceivedTimestamp, .user.username, .objectRef.name, (.requestObject.roleRef.name // "")] | @tsv' audit.log | grep -i "cluster-admin"
One ClusterRoleBinding to cluster-admin is complete cluster takeover. Every occurrence needs a matching change record.
Secret Enumeration
SIEM> source="k8s:audit" objectRef.resource="secrets" verb IN ("get","list") | stats count, dc(objectRef.namespace) as namespaces by user.username, sourceIPs{} | where count > 20 OR namespaces > 3
An identity reading secrets across multiple namespaces is harvesting credentials. Application service accounts should touch only their own namespace.
Anonymous API Access
bash> jq -r 'select(.user.username=="system:anonymous" or (.user.groups[]? == "system:unauthenticated")) | [.requestReceivedTimestamp, .verb, .requestURI, .responseStatus.code, .sourceIPs[0]] | @tsv' audit.log
Any result with a 2xx status means the cluster served an unauthenticated request. This is how exposed clusters are mass-compromised.
Service Account Token Abuse
SIEM> source="k8s:audit" user.username="system:serviceaccount:*" | stats dc(objectRef.resource) as resources, values(verb), count by user.username, sourceIPs{} | where resources > 5
A service account touching many resource types is behaving like an administrator, not an application. Usually means its token was stolen from a pod.
Authorisation Failures
bash> jq -r 'select(.annotations["authorization.k8s.io/decision"]=="forbid") | [.user.username, .verb, .objectRef.resource] | @tsv' audit.log | sort | uniq -c | sort -rn | head -25
Repeated forbidden requests from one identity is permission enumeration, an attacker mapping what a compromised token can reach.
Port Forwarding
bash> jq -r 'select(.objectRef.subresource=="portforward") | [.requestReceivedTimestamp, .user.username, .objectRef.namespace, .objectRef.name] | @tsv' audit.log
Port forwarding tunnels directly to a pod, bypassing network policy, ingress rules, and service mesh controls entirely.
Images from Untrusted Registries
bash> kubectl get pods -A -o jsonpath='{range .items[*]}{.metadata.namespace}{"\t"}{.spec.containers[*].image}{"\n"}{end}' | grep -vE "registry.corp.local|gcr.io/htl-prod"
Workloads pulling from Docker Hub or unknown registries. Cryptomining deployments are almost always public images.
Verify Auditing Is Active
bash> kubectl -n kube-system get pod -l component=kube-apiserver -o yaml | grep -E "audit-policy-file|audit-log-path|audit-log-maxage"
If these flags are absent, the cluster is recording nothing at all while running perfectly. Check this first on any cluster you inherit.

Best Practices for Kubernetes Logging

Apply these practices so a cluster is not opaque at the moment you most need to see into it:

01

Turn Auditing On Before You Need It

Self-managed clusters record nothing by default and give no warning. A cluster without an audit policy file cannot answer a single question about who did what.

02

Never Log Secret Contents

Keep the secrets resource at Metadata level. Request or RequestResponse writes secret values into the audit log, turning it into the richest credential store you own.

03

Drop the Noise in the Policy, Not the SIEM

Health probes, metrics scrapes, and system component watches dominate volume and carry no signal. Filtering them at the policy avoids paying to ingest them at all.

04

Pair Audit Logs with a Runtime Sensor

The audit log stops at the container boundary. It records that a shell was opened but never what was typed, and only a runtime tool closes that gap.

05

Ship Logs Off the Control Plane

Audit logs live on control plane nodes that a cluster-admin can reach. Forwarding them elsewhere is what preserves evidence of the compromise that granted that access.

06

Enable Every Managed Log Type

EKS logging is entirely off by default, and enabling only api and audit misses the authenticator stream that maps IAM identities to cluster users.

07

Treat Admission Denials as Detections

Pod Security Admission and policy engines log every blocked request. That is a direct feed of attempted misconfiguration and attack, already filtered for you.

08

Baseline Service Account Behaviour

Application service accounts should touch a small, predictable set of resources in one namespace. Deviation from that is the clearest sign a pod token has been stolen.

Common Kubernetes Log Examples

A cluster compromise from stolen service account token to node-level persistence.

Permission Enumeration with a Stolen Token

{"kind":"Event","verb":"list","requestReceivedTimestamp":"2025-07-14T09:41:22.481Z", "user":{"username":"system:serviceaccount:default:build-sa", "groups":["system:serviceaccounts","system:authenticated"]}, "sourceIPs":["10.244.3.17"],"userAgent":"kubectl/v1.29.3 (linux/amd64)", "objectRef":{"resource":"secrets","namespace":"kube-system"}, "responseStatus":{"code":403}, "annotations":{"authorization.k8s.io/decision":"forbid", "authorization.k8s.io/reason":"no RBAC policy matched"}}
A build service account using kubectl from a pod address to list kube-system secrets. Build automation does not run kubectl interactively, so the token has been stolen from inside a container.

Successful Secret Harvesting

{"verb":"list","requestReceivedTimestamp":"2025-07-14T09:44:07.229Z", "user":{"username":"system:serviceaccount:default:build-sa"}, "sourceIPs":["10.244.3.17"], "objectRef":{"resource":"secrets","namespace":"default"}, "responseStatus":{"code":200}, "annotations":{"authorization.k8s.io/decision":"allow", "authorization.k8s.io/reason":"RBAC: allowed by RoleBinding \"build-sa-secrets\"/\"default\""}}
The reason annotation names the exact binding that permitted this, which answers the how question immediately. Kubernetes secrets are base64 encoded, so the response contained usable credentials.

Privilege Escalation to Cluster Admin

{"verb":"create","requestReceivedTimestamp":"2025-07-14T09:52:10.774Z", "user":{"username":"system:serviceaccount:default:build-sa"}, "sourceIPs":["10.244.3.17"], "objectRef":{"resource":"clusterrolebindings","name":"debug-access"}, "requestObject":{"roleRef":{"kind":"ClusterRole","name":"cluster-admin"}, "subjects":[{"kind":"ServiceAccount","name":"build-sa","namespace":"default"}]}, "responseStatus":{"code":201}, "annotations":{"authorization.k8s.io/decision":"allow"}}
The service account binds itself to cluster-admin using a benign-sounding binding name. One object, and it now controls every namespace and workload in the cluster.

Container Escape via Privileged Pod

{"verb":"create","requestReceivedTimestamp":"2025-07-14T09:55:41.118Z", "user":{"username":"system:serviceaccount:default:build-sa"}, "objectRef":{"resource":"pods","namespace":"kube-system","name":"node-debug"}, "requestObject":{"spec":{ "hostPID":true,"hostNetwork":true, "containers":[{"name":"shell","image":"alpine:latest", "command":["nsenter","--target","1","--mount","--uts","--ipc","--net","--pid","--","bash"], "securityContext":{"privileged":true}}], "volumes":[{"name":"host","hostPath":{"path":"/"}}]}}, "responseStatus":{"code":201}}
Privileged, hostPID, hostNetwork, and a hostPath mount of the entire root filesystem. The nsenter command enters the host's namespaces directly, giving a root shell on the node itself.

Interactive Shell in a Production Pod

{"verb":"create","requestReceivedTimestamp":"2025-07-14T09:58:02.114Z", "user":{"username":"system:serviceaccount:default:build-sa"}, "sourceIPs":["10.244.3.17"], "objectRef":{"resource":"pods","subresource":"exec", "namespace":"production","name":"payments-api-7d9f4b8c5-x2n4k"}, "requestURI":"/api/v1/namespaces/production/pods/payments-api-7d9f4b8c5-x2n4k/exec?command=%2Fbin%2Fsh&stdin=true&tty=true", "responseStatus":{"code":101}}
Status 101 is the WebSocket upgrade that carries the session. The audit log proves a shell was opened into the payments API, but records nothing of what was typed inside it.

Runtime Sensor Fills the Gap

{"output":"09:58:14.882 Notice Terminal shell in container (user=root container=payments-api pod=payments-api-7d9f4b8c5-x2n4k ns=production shell=sh parent=runc cmdline=sh)", "priority":"Notice","rule":"Terminal shell in container"} {"output":"09:58:41.229 Warning Sensitive file opened for reading (file=/var/run/secrets/kubernetes.io/serviceaccount/token proc=cat container=payments-api)", "priority":"Warning","rule":"Read sensitive file untrusted"}
Falco records what the audit log cannot: a shell spawned inside the container and the service account token being read from the mounted volume, ready to be reused elsewhere.

Persistence via DaemonSet

{"verb":"create","requestReceivedTimestamp":"2025-07-14T10:04:55.229Z", "user":{"username":"system:serviceaccount:default:build-sa"}, "objectRef":{"resource":"daemonsets","namespace":"kube-system","name":"node-metrics-agent"}, "requestObject":{"spec":{"template":{"spec":{ "hostNetwork":true,"tolerations":[{"operator":"Exists"}], "containers":[{"image":"docker.io/xmrig/xmrig:latest", "resources":{"requests":{"cpu":"3500m"}}}]}}}}, "responseStatus":{"code":201}}
A DaemonSet named to look like monitoring runs on every node, including nodes added later. The toleration for all taints ensures it reaches control plane nodes too, and the image name gives the purpose away.

Anonymous Access to an Exposed Cluster

{"verb":"get","requestReceivedTimestamp":"2025-07-14T08:14:02.117Z", "user":{"username":"system:anonymous","groups":["system:unauthenticated"]}, "sourceIPs":["203.0.113.44"],"userAgent":"Go-http-client/2.0", "requestURI":"/api/v1/namespaces/kube-system/secrets", "responseStatus":{"code":200}, "annotations":{"authorization.k8s.io/decision":"allow", "authorization.k8s.io/reason":"RBAC: allowed by ClusterRoleBinding \"anonymous-discovery\""}}
An unauthenticated request from the internet returning 200 for kube-system secrets. A ClusterRoleBinding granting rights to system:unauthenticated is how clusters get mass-compromised within hours of exposure.
